# 쇼핑몰 백엔드·프런트엔드 로직 구현 점검

> 이 문서는 점검 당시 기록이다. 이후 처리 결과와 남은 실검증은 [운영현황](../../01_기획/운영/운영현황.md)의 C-01~C-10에서 추적한다.

점검일: 2026-11-25. 대상은 `04_MVP/seelo`의 스마트스토어·카페24 기능이다. 디자인 완성도는 평가하지 않았다. 실제 파일·API·상태 전이·배포 구성을 대조하고 로컬 검사를 실행했다. 이번 점검에서는 서비스 코드를 수정하거나 실상품을 다시 변경하지 않았다.

## 결론

**백엔드 전체 완료와 프런트엔드 로직 전체 완료로 판단할 수 없다.** 현재는 상품 정비의 기본 경로를 구현한 단계다. 대표 계정에서 새 브라우저 코드의 본문 저장·공개 반영·복구는 검증됐다. 고객 스토어 선택, 운영자 작업 흐름, 쇼핑몰용 AI 노출 측정, 서버 실행·배포 연결은 남아 있다.

프런트엔드의 기본 폼·업무 규칙·통신 계층은 구현됐다. 디자인만 바꾸면 완성되는 상태는 아니다. 실제 브라우저 실행기가 받지 않는 필드를 화면에서 승인할 수 있는 불일치도 확인했다.

기존 지도 베타의 측정·보고서·워커를 쇼핑몰 완성 기능으로 합산하지 않았다. 가격·결제·구독·지도 베타 화면·계정 설정은 현재 쇼핑몰 프런트 구현계획에서 제외한 항목이므로 필수 미구현으로 세지 않았다.

## 3. 우선 해결할 실제 불일치

### A. 서버 브라우저 실행 위치와 컨테이너가 맞지 않음 — 운영 연결 필수

- `commerce_service.py:291,655,657`은 API 요청에서 직접 브라우저 원본 수집·저장·재조회를 호출한다.
- API용 `backend/Dockerfile:14,17`은 `browser` 의존성 그룹과 Chromium을 설치하지 않는다.
- 브라우저가 있는 이미지는 `Dockerfile.fix`다. 공유 브라우저 프로필 볼륨도 현재 Compose의 `worker-fix`에만 있다.
- 따라서 **현재 배포 파일로 새 쇼핑몰 브라우저 경로를 서비스에 올리려면 실행 위치·의존성·프로필 저장소 연결을 수정해야 한다.** 로컬 PC 성공을 컨테이너 성공으로 볼 수 없다. 이번에 운영 컨테이너를 변경하거나 실제 배포하지는 않았다.
- 완료 조건: 실제 배포 구성에서 전용 세션으로 원본 수집→승인 저장→재조회→복구를 수행하고, 서버 재시작 후 세션 보관과 결과 재조회를 확인한다.

### B. 새 프런트가 배포 대상으로 연결되지 않음 — 서비스 제공 필수

- 개발·운영 Compose는 `infra/nginx/html`을 서비스한다. 이 폴더는 현재 Figma 프로토타입 링크가 있는 자리 표시 페이지다.
- `frontend/dist`를 이 경로로 빌드·전달하는 단계가 없다.
- `deploy-seelo.yml`에는 프런트 `npm test/build` 단계가 없다. 백엔드 검증도 `uv sync --frozen`으로 브라우저 그룹을 설치하지 않는다.
- 완료 조건: 프런트 검사·빌드·정적 파일 배포와 쇼핑몰 브라우저 회귀를 CI에 연결하고 실제 HTTPS에서 API·쿠키·직접 경로 새로고침을 확인한다.

### C. 관리자에게 고객 업무를 전달하는 경로 부족 — 위임 서비스 필수

- `api/commerce.py:66-71`의 스토어 목록은 항상 현재 사용자의 `owner_id`로 필터한다. 관리자라도 고객 전체 목록이 나오지 않는다.
- 관리자에게 스토어 ID를 전달하면 직접 조회·권한 확인·공개 기록은 가능하지만, 고객 목록·초대 대기·작업 할당 화면은 없다.
- `commerce_service.owner()`는 다른 고객의 스토어에 관리자 계정으로 일반 소유자 명령을 실행하면 `FORBIDDEN`을 반환한다. 실제 함수 호출로 확인했다. 이 검사는 고객의 승인을 보호하므로 무조건 제거할 대상이 아니다.
- 완료 조건: 운영자가 고객 스토어를 찾고 위임을 확인하는 경로, 고객 승인과 운영자 작업의 역할 분리, 승인된 작업만 실행하는 흐름을 완성한다.

### D. 화면은 지원하지만 실행기는 거부하는 모바일 설명 — 저장 오류 수정 필수

- `frontend/src/commerce/schemas.ts:53-64`는 카페24 `mobile_description`을 허용한다. 화면은 이 목록으로 선택 항목을 만든다.
- 현재 카페24 브라우저 YAML과 실제 수집 스냅샷에는 모바일 설명이 없다.
- 같은 필드로 정비안을 만들면 `method=api`로 남지만, 브라우저 원본은 브라우저 실행기로 전달된다.
- 실행기를 네트워크 없이 검사했다. `write(..., {mobile_description: ...})`가 **브라우저를 열기 전에 `unsupported_browser_field`를 반환**했다.
- 완료 조건: 브라우저 모바일 입력·재조회·복구를 실제 구현·검증하거나, 현재 모드에서 미지원 필드를 생성·승인 전에 제외한다. 서버 capabilities와 프런트의 실제 지원 목록도 일치시킨다.

### E. 위임 스토어 선택과 고유 식별 — 여러 고객 처리 필수

- 몰별 프로필 분리는 있다. 플랫폼의 위임 스토어 목록에서 특정 스토어를 선택하는 절차는 없다.
- 네이버는 화면의 스토어명을 비교한다. 카페24는 기대한 도메인과 상품번호를 비교하며, `_identity()`에서 최종 쇼핑몰 번호 경로를 별도로 검사하지 않는다.
- 완료 조건: 고객과 확정한 스토어 고유값·카페24 쇼핑몰 번호를 위임 목록과 대조하고, 목록 순서가 바뀌거나 다른 스토어가 선택돼도 저장 전에 중단하는 시험을 통과한다.
- 실제 대행사 매니저·부운영자 계정 시험도 필요하다. 현재 실계정 성공은 대표 계정 결과다.

### F. 쇼핑몰 AI 노출 진단부터 전후 비교까지 연결 — 사용자 목적상 필수

- 기존 측정 엔진은 지도 대상 음식점·지역·음식 종류 중심이다. 질문 생성 프롬프트도 관광객의 음식점 추천용이다.
- 쇼핑몰 모델은 `CommerceShop/Product/Plan/Write` 네 종류다. 쇼핑몰 상품과 진단 질문·실행 결과·전후 비교를 잇는 서비스 경로가 없다.
- `03_실험/쇼핑몰_AI노출_전후비교_20261124`의 B0 등 별도 실험 파일은 서비스 API·화면과 연결돼 있지 않다.
- 완료 조건: 대상 상품·고정 질문·측정 조건·응답·출처·추천 여부·순위·실패 상태·변경 버전을 저장하고, 같은 조건의 전후 비교를 API와 화면에서 조회한다.

### G. AI가 먼저 판단하는 흐름과 상품 정보 구조 — 자동화 범위 보완

- 조사 결과를 저장하는 코드는 있다. 자동 웹 검색으로 자료 URL을 발견하는 동작은 없다.
- 프런트는 `requiredFacts`와 정비 필드를 사용자가 선택한다. `useAi` 체크박스 기본값도 꺼져 있다. 서버의 AI 기본값이 true여도 화면 요청은 false를 명시한다.
- 사실 키는 용도·모델·소재·크기·무게·구성품·전원·호환·관리 등 범용 9개다. 식품 성분·단위당 함량·섭취·알레르기 전용 구조와 검증은 없다. 자유로운 값으로 일부 표현할 수는 있지만 전용 정량 검증과 다르다.
- 완료 조건: 원본 수집 후 AI 조사와 필요한 정보 판단을 기본 경로에 연결하고, 해당 상품에 필요한 누락만 묻는다. 영양소 질문 실험은 검증한 정량 자료를 별도 다룬다.

## 4. 그다음 처리할 프런트 로직

1. **연결 해제:** 기존 서버 endpoint를 Gateway·명령·화면에 연결하고 재수집·실행을 막는 상태를 갱신한다.
2. **과거 정비안:** 상세·쓰기 이력·복구할 정비안을 선택할 수 있게 한다. 현재 `latestPlan`만 작업 대상으로 삼는다.
3. **상품 선택·페이지네이션:** 현재 가져온 최대 100개와 외부 전체 상품 목록을 구분한다. 필요 시 서버 검색·페이지 API와 외부 카탈로그 수집을 추가한다.
4. **진행·복구 안내:** `login_required`·권한 회수·캡차·원본 충돌·결과 미확인 상태를 운영자가 해결하고 다시 확인할 경로로 연결한다. 현재는 오류 표시·수동 재조회 중심이다.
5. **공개 확인:** 현재 관리자 기록 폼은 구현됐다. 자동 PC·모바일 검증을 서비스에 넣을지는 별도 범위다. 이 기능을 자동이라고 표시하지 않는다.

## 6. 완료까지의 권장 순서

1. 서버 브라우저 실행 위치·프로필 저장소·프런트 빌드 배포를 연결한다.
2. 고객·스토어 연결, 운영자 목록·위임 확인, 실제 스토어 고유 식별을 완성한다.
3. 편집 모드별 지원 필드와 화면 선택 항목을 일치시키고 모바일 설명 오류를 해결한다.
4. 원본 수집→AI 판단→필요한 질문→고객 승인→실행·재조회·복구를 기본 이용 흐름으로 연결한다.
5. 쇼핑몰 AI 노출 진단·질문·실행 결과·전후 비교를 서비스 API와 화면에 연결한다.
6. 서로 다른 고객 계정과 실제 위임 역할로 프런트부터 공개 페이지·복구까지 시험한다.

여기까지 완료해야 현재 사용자가 요구한 쇼핑몰 서비스의 로직을 끝냈다고 판단할 수 있다.
