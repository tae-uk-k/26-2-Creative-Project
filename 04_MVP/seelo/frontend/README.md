# seelo 쇼핑몰 프론트엔드

기준일: 2026-11-28. 스마트스토어·카페24의 로직과 화면 디자인을 구현했다. 디자인 기준은 랜딩 새 시안 `dark.html`과 토스 디자인 시스템의 토큰·규칙이다.

구현 순서와 규칙은 [프론트엔드 구현계획](../../../01_기획/개발/프론트엔드_구현계획.md), 화면 목록과 단계별 표시는 [이용 흐름과 화면](../../../01_기획/이용흐름과화면.md)을 따른다.

## 1. 실행

Node.js 22.12 이상이 필요하다. 이 작업에서는 Node.js 24.11.1을 사용했다.

```powershell
cd C:\Users\xodnr\Desktop\26-2-Creative-Project-main\04_MVP\seelo\frontend
npm ci
npm run dev:demo
```

시연 기본 주소: `http://127.0.0.1:5173`.

시연은 메모리의 고정 자료를 사용한다. 실제 로그인·쇼핑몰·상품·AI를 호출하지 않는다. 새로고침하면 시연 자료가 초기화된다. 상단의 시연 띠를 항상 표시한다.

| 시연 띠 | 동작 |
|---|---|
| `사장님 화면` | 모든 시연 스토어를 가진 판매자 계정(기본). 메뉴: 홈·스토어·AI 노출 |
| `운영자 화면` | 스토어가 없는 seelo 운영자 계정. 메뉴: 운영 관리. 고객 스토어·반영·측정은 여기서 한다 |
| `소개 화면` | 랜딩(`/`)을 연다 |
| `처음부터` | 시연 자료와 화면 선택을 처음 상태로 돌린다 |

두 화면은 같은 시연 자료를 쓴다. 사장님 화면에서 승인한 뒤 운영자 화면으로 바꿔 반영할 수 있다. 고른 화면은 새로고침해도 유지한다.

| 시연 스토어 | 확인할 흐름 |
|---|---|
| 카페24 시연 스토어 | 상품 정비 전체 흐름(텀블러), 반영과 보고서가 끝난 상품(보온병) |
| 스마트스토어 시연 스토어 | API 방식 연결, HTML 전환 확인 |
| 권한 위임 전 시연 스토어 | 스마트스토어 위임 안내와 초대 기록 |
| 권한 확인 중 시연 스토어 | 카페24 위임 확인 대기, 운영자 권한 확인 |

실제 백엔드에 연결하려면 다음 명령을 사용한다.

```powershell
npm run dev
```

- 기본 모드는 실제 API다. `/api`를 `http://127.0.0.1:8000`으로 프록시한다. 백엔드는 별도로 실행해야 한다.
- 로컬 HTTP에서 세션을 시험할 때는 백엔드의 로컬 개발 쿠키 설정을 확인한다. 운영 HTTPS 설정과 구분한다.
- 실제 API 실패·미연결을 시연 데이터로 대체하지 않는다.
- `.env.local`의 `VITE_COMMERCE_MODE=demo`로도 시연을 명시할 수 있다. 비밀 키·토큰·판매자 비밀번호는 프론트엔드 환경변수에 넣지 않는다.
- 스마트스토어 초대 대상은 빌드 설정 `VITE_SEELO_MANAGER_NAME`·`VITE_SEELO_MANAGER_PHONE`으로 넣는다. 운영 이미지는 같은 이름의 Docker 빌드 인자로 받는다(`infra/production.env.example`). 비어 있으면 위임 안내에 복사 버튼을 보여 주지 않고, 시연 모드에서는 예시 값을 쓴다.
- `npm run build`는 실제 API 모드의 정적 파일을 `dist/`에 만든다. 이번 작업에서 운영 배포는 하지 않았다.

## 2. 구현한 기능

| 영역 | 내용 |
|---|---|
| 랜딩·약관 | `/`에 dark.html 이식(로그인 버튼·FAQ 답 하나만 변경). 히어로의 `무료 진단받기`는 시안처럼 준비 중 안내만 띄운다, 이용약관·개인정보 처리방침 초안(`/terms`, `/privacy`) |
| 인증·계정 | 이메일 가입·로그인·인증·재전송·비밀번호 재설정, 소셜 시작(`intent` 전달)·가입 마무리, 세션·CSRF. 계정 화면에서 비밀번호 변경·탈퇴 |
| 오늘 할 일 | 상품 목록 `summary`로 답할 질문·승인할 정비안·보고서·연결할 스토어를 카드로 모음 |
| 경로·캐시 | 미로그인 접근 제한, 내부 복귀 경로, 로그아웃·사용자 교체·세션 만료 때 조회 캐시 정리 |
| 메뉴 | 역할별로 나눈다. 판매자: 홈·스토어·AI 노출. 스토어가 없는 운영자: 운영 관리(첫 화면도 운영 관리). 좁은 화면은 같은 항목의 하단 메뉴에 계정을 더한다 |
| 스토어 | 스토어 주소만으로 등록(서버 판별), 관리자 초대와 API 인증의 독립 상태, 연결 해제, 담당자 브라우저 세션 상태 표시. 연결 후 화면은 탭 없이 상품 목록 하나만 둔다. `상품 추가`를 눌러야 입력칸을 연다(`?add=1`). 쇼핑몰 상품 목록에서 고르기(관리자 화면 방식만)와 직접 입력도 상품 추가 안에 둔다. 운영자가 고객 스토어를 열면 판매자 안내 대신 권한 확인 칸을 본다 |
| 원본 | 상품번호·카페24 상품 주소로 수집, 브라우저 수집 작업(202) 상태 조회 후 상품 이동, 판매자 제공 원본, 가져온 상품 서버 검색·페이지 |
| 플랫폼 상품 목록 | 위임 관리 화면에서 읽은 목록을 가져온 상품과 구분해 표시하고 골라 가져오기 |
| 자료·AI | AI가 먼저 조사하고 필요한 정보를 판단해 정비안 생성, 확인하지 못한 정보만 질문, 답변 후 자동 재생성, 함량 수치 표시. 직접 보완·범위 지정은 선택 |
| 정비안 | 서버 `fieldSupport` 기준 자동·수동·미지원 필드, 생성·보류, 이전 정비안 상세·쓰기 이력·복구 선택, 선택한 필드만 승인 |
| 역할 | 판매자만 승인. 적용·복구·공개 확인·측정은 운영자 화면에만 둔다. 운영자는 판매자 승인 기록이 있는 정비안만 실행. `/operator` 탭에서 반영 대기·권한 확인·직접 수정·결과 확인·고객 승인 대기·고객 스토어 조회, 스토어 고유값 기록 |
| 실행 | 서버 쓰기 설정 확인, 작업 대기·실행 중 명령 차단, 적용·재조회·원본 값 복구, 실패 사유 안내 |
| 확인 | 저장·관리 화면 재조회·PC·모바일 공개 확인 분리, 관리자 수동 편집·공개 확인 기록 |
| 상품 화면 탭 | 정비(기본)·AI 노출(`?tab=exposure`). 지난 정비안은 이전 정비안이 있을 때만 정비 탭 아래에 둔다. 반영 방식·정비안 번호·되돌리기·측정 관리는 운영자에게만 보인다 |
| AI 노출 현황 | `/exposure`(판매자): 한 문장 요약과 상품별 ChatGPT·Gemini 상품 발견 비율·%p 변화. 줄을 누르면 상품 AI 노출 탭으로 간다. 줄 안에 배지·버튼을 두지 않는다 |
| AI 노출 진단 | 운영자 측정 화면(`/measure`): 고정 질문 세트, 회차 측정, 정상/무효·발견·추천·인용 집계, 같은 세트·조건 전후 비교 |
| 보고서 | `/report`: 같은 조건의 정비 전·후 회차를 짝지어 공급자별 지표·질문별 표·바뀐 내용·공개 확인 기록을 보여 줌. 인쇄 지원 |

## 3. 시연 확인 순서

1. `/home`에서 오늘 할 일 카드를 본다. 카드 하나를 누르면 해당 화면으로 간다.
2. 카페24 시연 스토어의 **시연용 텀블러 500mL**를 연다. 단계 표시에서 현재 단계를 확인한다.
3. **AI가 조사하고 정비안 만들기**를 누른다. 질문이 나오면 답한다. 답하면 정비안을 다시 만든다.
4. **정비안 확인하기**에서 현재 값과 바뀔 값을 비교한다. 반영할 항목을 고르고 **승인하기**를 누른다.
5. 시연 띠에서 **운영자 화면**으로 바꾼다. **운영 관리 → 반영 대기**에서 그 상품을 열고 **승인한 변경 적용**을 누른다. 저장·재조회와 공개 미확인을 구분해 확인한다.
6. 운영자 영역에 PC·모바일 공개 확인 결과를 기록한다. 시연에서는 고정 자료의 상태만 바뀐다.
7. **수정 전으로 되돌리기**를 확인 대화상자로 실행한다. 공개 확인이 다시 미확인으로 돌아오는지 확인한다.
8. **시연용 보온병 750mL**에서 **보고서 보기**를 누른다. 운영자 화면에서 같은 상품의 **AI 노출** 탭 → **측정 관리**(`/measure`)로 회차를 실행하고 비교한다.
9. 사장님 화면의 메뉴 **AI 노출**에서 상품별 전후 변화(보온병 ChatGPT +44%p)를 본다. 줄을 누르면 상품의 AI 노출 탭이 열린다.
10. **권한 위임 전 시연 스토어**에서 위임 안내를 보고 **초대를 보냈어요**를 누른다. 확인 대기 단계로 바뀌는지 본다.
11. **운영 관리**(`/operator`)의 탭과 `/account`, 좁은 화면(390·320px)의 하단 메뉴를 확인한다.

## 4. API 계약과 확실한 한계

- 현재 백엔드의 `/api/auth/*`·`/api/oauth/*`·`/api/commerce/*`에 연결한다. 쇼핑몰 API·DB 마이그레이션은 별도 백엔드 변경이며 이 프론트엔드 작업의 완료 근거에 합치지 않는다.
- `src/commerce/schemas.ts`는 화면 타입과 런타임 응답 검증을 담당한다. `http-gateway.ts`는 실제 경로·요청 형식을 담당한다.
- 가져온 상품 검색·페이지는 서버가 처리한다. 플랫폼 전체 상품 목록은 별도 화면(위임 관리 화면 조회)이다.
- `applying`과 대기·실행 중 작업만 주기적으로 조회한다. 저장 결과 미확인·반영 대기 상태에서는 자동 재전송하지 않고 재조회만 요청한다.
- AI 조사는 기존 본문·본문 속 공개 자료 링크·지정한 자료 주소를 처리한다. 웹 검색 자료 발견은 서버 설정(`COMMERCE_WEB_DISCOVERY`)을 켠 경우에만 쓴다.
- 카페24 OAuth는 서버가 만든 공식 인증 주소를 사용한다. 인증 뒤 프론트엔드로 돌아와 연결 상태를 다시 확인한다. 백엔드 콜백의 자동 화면 복귀는 별도 통합 대상이다.
- 스마트스토어 공식 판매자 인증은 관리자 백엔드 절차를 사용한다. 개인용 앱 키를 받는 폼은 없다.
- 외부 채널의 전송 필드·수신 값은 현재 서버 계약에 없다. 공개 확인을 전송 완료로 표시하지 않는다.
- 원본 값 복구와 스마트에디터 형식 복구를 구분한다.
- 결제·구독·가격 화면(D11), 메일 알림(D15), 측정 질문 자동 생성(C-13), 재측정 예약(C-14), 지도 베타 화면, 운영 배포는 이번 구현 범위 밖이다.
- 판매자 화면에는 적용·복구 버튼이 없지만 서버 API는 소유자의 적용·복구 요청도 받는다. 화면 권한이 서버 검사를 대신하지 않는다.

## 5. 검증

```powershell

npm run test:contract
npm run typecheck
npm run format:check

```

| 7 | 운영자 측정 질문 세트 → 정비 전 측정 | 통과. 응답 작업 종류 `measure`를 거부하던 문제를 고쳤다 |
| 8 | 운영자 수동 편집 요청 → 결과 기록 → 공개 확인 기록 | 통과 |
| 9 | 정비 후 측정 → 보고서(운영자·판매자) → 홈 "보고서가 준비됐어요" | 통과 |
| 10 | 비밀번호 변경 오류, 비밀번호 재설정 메일, 연결 해제, 탈퇴 | 통과. 탈퇴 뒤 스토어·상품·정비안이 함께 지워짐 |

로컬에서 AI 단계를 돌리려면 `OPENAI_PLAN_MODEL`·`OPENAI_MEASURE_MODEL`·`GEMINI_MEASURE_MODEL`에 아무 이름이나 넣는다. 가짜 AI는 쇼핑몰 사실을 찾지 못한 것으로 답해 판매자 질문 흐름으로 이어진다.

화면 통합 시험은 jsdom에서 실행했다. 실제 브라우저·실계정의 종단 간 성공으로 표시하지 않는다.

## 6. OpenAPI

`openapi.json`은 백엔드가 내보내는 서버 계약이다. 변경이 필요할 때 `backend`에서 실행한다.

```powershell
uv run python scripts/export_openapi.py
uv run python scripts/export_openapi.py --check
```

기존 지도 시연용 `seed_demo.py --scenarios`와 이번 메모리 쇼핑몰 시연은 서로 다른 데이터다.
