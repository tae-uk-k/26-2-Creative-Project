# 10. 재측정·전후 비교 보고서·이메일·운영(F-11·F-12, W-10·W-12)

## 1. 재측정 시작(W-12-1, E19·E20)

`dispatchRemeasures`(10분마다):

```sql
UPDATE remeasure_schedules
   SET status = 'started', started_at = now()
 WHERE status = 'scheduled' AND due_at <= now()
RETURNING id, fix_request_id, triggered_by;
```

- 조건부 UPDATE라 워커 2개가 동시에 돌아도 예약마다 한 번만 시작된다.
- 반환된 예약마다(각각 트랜잭션): 신청 `remeasure_scheduled → remeasuring`(False면 예약을 canceled로 되돌리고 경고), 측정 생성(`kind = remeasure`, `question_set_id` = 신청 `base_run_id` 측정의 `question_set_id`, `trigger` = `scheduler` 또는 `admin`, `fix_request_id`, `is_free = false`), `schedule.run_id`, 같은 트랜잭션에서 `collectStore(store_id, run_id)` 등록.
- `[지금 재측정]`(E20): 예약 `due_at = now()`, `triggered_by = 'admin'`으로 바꾼 뒤 같은 함수를 그 예약 하나에 대해 바로 실행한다.
- 재측정은 질문을 새로 만들지 않는다(`stage`가 collecting → calling_ai로 바로).
- 테스트: `due_at`이 지난 예약만 시작, 동시 2회 실행에 1번만 시작, `question_set_id`가 정비 전과 같음, 탈퇴·가게 변경 때 예약 canceled(탈퇴는 행 삭제).

## 2. 정비 값 비교 `compareFixValues(fix_request_id, run_id)`(E21)

- 재측정 `finalizeRun`이 완료한 뒤 실행한다. **읽기만** 한다.
- 비교 대상: 그 신청의 `fix_logs` 중 `applied`·`manual_done`·`pending_reflection`.
- 지도별 지금 값
  - Google: 재측정 수집에서 새로 받은 Google 스냅샷에서 칸에 해당하는 값(`regular_hours` ← `regularOpeningHours`, `website` ← `websiteUri`, `phone` ← `nationalPhoneNumber`, `attributes` ← 편의 필드). Places로 볼 수 없는 칸(`description`, `menu`)은 연결이 살아 있으면 관리 화면(또는 API)에서 읽고, 아니면 `unknown`.
  - 카카오: 연결이 `connected`면 파트너센터에서 읽는다(브라우저, `lock = fix:kakao`). 아니면 `unknown`.
- 결과: `remeasure_value`(읽은 값), `remeasure_match` = `same_value(...)`면 `match`, 다르면 `differs`, 못 읽으면 `unknown`.
- 카카오에서 읽은 값도 `fix_logs.remeasure_value`(정비 기록)로만 저장한다.
- 오류: 브라우저 차단·읽기 실패는 그 칸 `unknown`으로 두고 계속. 권한 회수 감지는 E18(재측정 흐름은 계속).
- 끝나면 `comparison_reports`(version = 그 신청 최대 + 1, `generating`, `base_run_id`, `after_run_id = run_id`, `interval_days`) 생성 후 `generateComparisonReport(report_id)` 등록.
- `interval_days = floor((schedule.started_at - fix_requests.fix_completed_at) / 1일)`.

구현 메모(2026-10-29, 14단계)
- 코드: `services/remeasure_service.py`. 예약마다 신청 → 예약 순으로 잠그고 `transition()`을 쓴다. 측정·예약·`collectStore`는 같은 트랜잭션이다. 기준 질문이 없으면 새로 만들지 않고 예약을 유지하며 경고한다. 관리자는 409 `base_questions_missing`.
- `defer_compare()`가 실제 관리 화면 읽기가 필요한지 보고 큐를 고른다. 수동 모드·Places 칸만 비교할 때는 plan 큐(기본 워커), 관리 화면 읽기는 fix 큐. 카카오를 읽으면 `fix:kakao`, Google만 읽으면 `fix:google` 잠금. `AUTO_FIX_ENABLED=false` 또는 카카오 플래그가 꺼져 있으면 해당 관리 화면은 열지 않고 unknown.
- Google Places 칸은 **해당 재측정**의 성공 스냅샷만 쓴다. 편의 정보는 승인한 키만 비교하고, 정보 없는 키가 있으면 unknown. 영업시간의 선택 항목 `notes=null`은 비교 실패 사유가 아니다.
- `compareFixValues`는 신청을 다시 잠근 뒤 같은 `after_run_id`의 보고서가 있으면 끝낸다. 값 비교 저장·보고서 생성·다음 작업이 함께 커밋된다. 지도 쓰기 호출은 없다.
- E26 재시도는 기존 예약의 관리자 실행 여부를 유지한다. 경과일은 재시도 측정의 `started_at`을 쓴다(원 예약이 가리키는 측정이면 `schedule.started_at`).

## 3. 전후 비교 보고서 `generateComparisonReport(report_id)`(W-12-2, E22)

### 3.1 흐름

1. 보고서 `generating`이 아니면 끝. `generation_attempts += 1`(커밋).
2. 기준 측정(`base_run_id`)과 재측정(`after_run_id`)의 `metrics`, 두 측정의 `recommendations`, 신청의 `fix_logs`, 질문 세트를 읽는다.
3. `domain/report_builder.build_report(...)`로 `ReportContent`를 만든다(순수 함수).
4. 금지어 검사(3.4). 걸리면 예외(코드 오류) → 실패 처리.
5. `content` 저장, 보고서 → completed(`completed_at`), 신청 `remeasuring → report_ready`, 메일 `report_ready`.
6. 예외: `generation_attempts < 2`면 다시 등록, 아니면 → `generation_failed`(`last_error`). 신청은 remeasuring 유지(S07 "재측정 중"). A01 [다시 생성] → E24.

`RateSummary`·`ProviderRates`는 04 1장과 같다.

### 3.3 계산 규칙

- 공급자별 전·후 `RateSummary`: 각 측정의 target 전체(question NULL) 지표.
- `rateDeltaPp = round((after.rate - before.rate) * 100, 1)`. 어느 한쪽 `rate`가 `None`이면 `None`.
- `noChange`: 두 공급자 모두 `rateDeltaPp`가 `None`이거나 절댓값이 10 미만 `[기획 확인: 기준 10%p]`.
- `headline`(고정 템플릿, 3.4): `noChange`면 "이번 측정에서는 큰 변화가 없었어요." 아니면 변화 절댓값이 더 큰 공급자로 "{AI} 추천 등장률이 {before}%에서 {after}%로 바뀌었어요." 수치는 소수점 1자리. "올랐다·좋아졌다" 같은 평가어를 쓰지 않는다.
- 주변 가게
  - `beforeTop5`: 기준 측정의 주변 가게 5곳(`rank_order`). 재측정 쪽 값은 재측정의 `recommendations`에서 같은 정규화 이름으로 08 5.2 공식을 다시 계산한다(재측정에서 우리 가게로 판정된 추천은 빼고).
  - `newTop5After`: 재측정의 주변 가게 5곳 중 `beforeTop5`에 없는 것.
  - `competitorPosition`: 08 5.5를 각 측정에 적용.
- 질문별: 같은 질문 ID로 짝을 짓는다. 어느 한쪽에서 그 공급자의 `success_count`가 0이면 그 공급자는 `excludedProviders`에 넣고 양쪽 값을 `null`로 둔다(W-12-2 "측정하지 못함"인 질문은 비교에서 뺌).
- 출처: 08 5.6을 각 측정에 적용.
- `changes`: 신청의 모든 `fix_logs`(disconnected 포함), 지도 → 정비안 칸 `order_no` 순. `note`는 `remeasureMatch = differs`일 때만 고정 문구.
- `earlyRemeasure = (schedule.triggered_by == "admin")`. 화면은 "정비 후 {intervalDays}일 만에 측정"을 보여 준다.

구현 메모(2026-10-29, 14단계)
- `schemas/report.py`가 API·저장 JSON 계약이다. 순수 함수 입력은 `RunMetricsView`, `QuestionView`, `ChangeView`(14 2.9). 질문 언어는 기존 질문 세트와 같은 en·ko다.
- `before_value=null`은 보고서에서 고정 문구 "확인하지 못함"으로 표시한다. `remeasure_match`가 없는 연결 끊김 기록 등도 unknown. 원 `fix_logs`는 고치지 않는다.
- 지도 인용은 성공·추출 성공 응답의 URL도 읽어 `map_kind(domain, url)`로 계산한다. `google.com/maps` 경로를 놓치지 않고 같은 응답의 같은 도메인은 한 번 센다. `ResponseView.source_urls`에만 계산 중 전달한다(새 저장 컬럼 없음).
- 생성 실패는 원문 대신 예외 종류 또는 `banned_term`만 남긴다. 1회 재등록 후 두 번째 실패면 generation_failed, 신청은 remeasuring 유지. 관리자의 E24는 실패 행을 보존하고 새 버전을 만든다.

## 4. 이메일(F-12, W-10)

### 4.1 흐름

1. 사건이 생긴 트랜잭션 안에서 `email_service.queue(session, type, user_or_admin, params, secret=None, dedupe_key=None)`:
   - 받는 주소: 사장님이면 `users.email`, 관리자면 `ADMIN_NOTIFY_EMAILS`(쉼표 이은 문자열).
   - `email_logs`(queued, `template_params` = 비밀 아닌 값, `secret_payload` = `encrypt_secret(json(secret))`, `dedupe_key`).
   - `dedupe_key`가 이미 있으면 아무것도 하지 않는다. 고유 위반이 바깥 트랜잭션을 깨지 않도록 `INSERT ... ON CONFLICT (dedupe_key) DO NOTHING RETURNING id`로 넣고, 반환 행이 없으면 끝.
2. 같은 트랜잭션에서 `sendEmail(email_log_id)` 등록(`jobs.defer`). 사건 처리가 롤백되면 메일도 나가지 않는다.
3. `sendEmail`: 행이 `queued`가 아니면 끝. `attempt += 1`. 템플릿 렌더(`templates/email/{type}.txt`·`.html`, Jinja2 `autoescape`) → `aiosmtplib.send`(30초). 성공 → `sent`, `sent_at`, `secret_payload = NULL`. 실패 → 예외를 다시 던져 Procrastinate가 다시 시도(최대 4번 = 처음 + 3회). 마지막 시도 실패면(작업 안에서 `attempt >= 4`로 판단) → `failed`, `error`(가린 메시지), `secret_payload = NULL`.
4. 발송 실패는 측정·정비·보고서 상태를 바꾸지 않는다(W-10-2).

구현 메모(2026-10-29, 15단계)
- 10종 템플릿은 2단계에서 이미 만들었다. `test_w_10_2.py`가 10종의 DB 등록·작업 인자·수신 대상·발송·재실행 건너뛰기, 6개 문구 변형, 사장님 본문의 내용 비공개를 확인한다.
- 인증·재설정은 원래 표대로 dedupe가 없다. 새 요청·재발송은 새 링크를 보내야 한다. 다른 사건은 안정된 사건 키로 중복을 막는다. 같은 키의 동시 INSERT는 1행만 커밋되고 다른 업무 트랜잭션을 깨지 않는다.
- 연결 확인 차단 메일의 키는 `manual_required:verify:{connectionId}:{invited_at 또는 created_at}`. 현재 시각을 넣던 방식은 같은 초대의 재실행에도 새 메일을 만들었다. 같은 초대는 한 통, 새 초대는 다시 한 통이다. 상태가 바뀐 뒤 뒤늦게 끝난 차단 작업은 메일을 만들지 않는다.
- `sendEmail`에 실행 잠금 `email:{id}`를 더했다. 렌더·SMTP 오류는 **예외 종류만** 저장한다. SMTP 재시도 예외도 안전한 `ConnectionError("smtp: <종류>")`로 바꿔 서버가 오류에 되돌려 준 링크·본문·비밀번호가 작업 로그에 남지 않게 한다.
- 단순 텍스트는 autoescape=False, HTML은 autoescape=True·StrictUndefined. HTML은 같은 텍스트 본문을 `_base.html.j2`로 감싼다. 별도 HTML 10개를 만들지 않는 2단계 구현을 유지한다.

## 6. 운영(배포·백업·관측, W-11-2, D-07)

구현 메모(2026-10-29, 16단계)
- `docker-compose.prod.yml`은 개발 파일과 합치지 않는 독립 구성이다. 운영 비밀·도메인·전용 프록시 대역·인증서 경로는 필수 입력이며 값을 채워 넣지 않았다. `infra/production.env.example`, `infra/OPERATIONS.md` 참고.
- TLS 템플릿·외부 HTTPS 건강 확인 스크립트(`backend/scripts/check_uptime.py`)·백업/복구 스크립트를 만들었다. 실제 VM·도메인·인증서 발급/갱신·외부 감시/알림은 미설정이다.
- 백업은 아래 원문과 같은 custom 덤프다. **7일 지난 파일은 지우지 않고 quarantine으로 격리**한다(사용자 삭제 규칙). 따라서 전체 용량이 7일치로 제한되지는 않는다. 영구 삭제는 별도 대상 확인·승인이 필요하다.
- 로컬 개발 DB의 덤프 → 새 검증 DB 복구를 확인했다. 기존 DB 대상 재실행은 createdb 단계에서 거부된다. 외부 저장소·KST 04:00 스케줄은 아직 설정하지 않았다.
- 워커는 기존 60초 정상 종료 대기를 쓰고, 운영 Compose는 75초 동안 기다린다. 기본 수동 모드에 fix 워커는 없다.

- 배포: VM에서 `git pull` → `docker compose build` → `docker compose run --rm migrate` → `docker compose up -d`. 워커는 `SIGTERM`을 받으면 하던 작업을 끝내고 멈추도록 Procrastinate 기본 종료 처리를 쓴다(대기 시간 `shutdown_graceful_timeout`은 60초).
- 백업: 매일 KST 04:00 `pg_dump -Fc`를 VM 밖 저장소에 7일치 보관. 복구 절차를 한 번 시험해 기록한다.
- 관측
  - 구조화 로그를 `docker compose logs`로 보고, `SENTRY_DSN`이 있으면 오류를 보낸다.
  - 비용: `measurement_runs.cost_usd` 일별 합계를 A01 상세(관리자)에서 본다.
  - 건강 확인: `GET /api/health`를 외부 모니터(무료 업타임 서비스)로 5분마다.
- 외부 API 하나가 멈춰도 나머지는 동작해야 한다(W-11-2): 출처별 `try`, 공급자별 큐, 메일 실패 무시 규칙을 지킨다.
