# 06. 작업 큐(Procrastinate)

- 큐 도구는 Procrastinate다. 작업 대기열은 같은 PostgreSQL에 저장된다. Redis는 쓰지 않는다.
- 아래 API는 Procrastinate 공식 문서(레퍼런스, "Using an external database connection", "Retry stalled jobs", "Cancel a job")에서 확인했다(2026-10-23). 설치한 버전과 다르면 설치 버전 문서를 따르고 이 파일을 고친다.

| 쓰는 API | 확인한 형태 |
|---|---|
| 앱 | `App(*, connector, import_paths=None, worker_defaults=None, periodic_defaults=None)` |
| 커넥터 | `PsycopgConnector(**kwargs)` — 키워드 인자는 psycopg `AsyncConnectionPool`로 넘어간다(`conninfo=...`) |
| 작업 정의 | `App.task(*, name=None, retry=False, pass_context=False, queue='default', priority=0, lock=None, queueing_lock=None)` |
| 등록 옵션 | `Task.configure(lock=, queueing_lock=, schedule_at=, schedule_in=, queue=, priority=, connection=)` → `.defer_async(**kwargs) -> int`(job id) |
| 같은 트랜잭션에 등록 | `configure(connection=<psycopg.AsyncConnection>)`. 작업 행이 그 연결의 트랜잭션에 들어가고, 커밋할 때 워커가 깨어난다(NOTIFY는 커밋 때 나감) |
| 중복 | `queueing_lock`이 같은 대기 작업이 있으면 `procrastinate.exceptions.AlreadyEnqueued` |
| 재시도 | `RetryStrategy(*, max_attempts=None, wait=0, linear_wait=0, exponential_wait=0, retry_exceptions=None)`, 대기 = `wait + linear_wait*attempts + exponential_wait**(attempts+1)`초. **`max_attempts`는 재시도 횟수다**(첫 실행 제외. `job.attempts >= max_attempts`이면 멈춤, 3.10.0 소스로 확인) → "1회 재시도"는 `max_attempts=1` |
| 주기 작업 | `App.periodic(*, cron, periodic_id='')` 위에 `@app.task`. 함수는 `timestamp: int` 인자를 받는다 |
| 워커 실행 | `await app.run_worker_async(queues=[...], concurrency=N, shutdown_graceful_timeout=초, ...)` |
| 취소 | `await app.job_manager.cancel_job_by_id_async(job_id, abort=True)` |
| 중단 감지 | async 작업은 다음 `await`에서 `asyncio.CancelledError`가 난다(폴링 불필요). 중단 요청된 작업이 실패하면 재시도하지 않는다 |
| 멈춘 작업 | `await app.job_manager.get_stalled_jobs()`(기본 `seconds_since_heartbeat=30`) → `await app.job_manager.retry_job(job)` |
| 테스트 | `procrastinate.testing.InMemoryConnector` — `jobs`, `reset()` |
| 스키마 | `procrastinate schema --apply`는 빈 DB에만 적용된다(이미 있으면 실패) |

## 1. 앱과 워커 실행

`seelo/worker/app.py`:

```python
from procrastinate import App, PsycopgConnector
from seelo.config import get_settings

app = App(
    connector=PsycopgConnector(conninfo=get_settings().queue_database_dsn),
    import_paths=[
        "seelo.worker.tasks_collect", "seelo.worker.tasks_measure", "seelo.worker.tasks_plan",
        "seelo.worker.tasks_fix", "seelo.worker.tasks_report", "seelo.worker.tasks_email",
        "seelo.worker.periodic",
    ],
)
```

`seelo/worker/run.py`(CLI 옵션 이름 차이를 피하려고 공식 Python API로 직접 띄운다):

```python
import argparse, asyncio
from seelo.logging import setup_logging
from seelo.worker.app import app

def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("--queues", required=True)          # "collect,measure"
    p.add_argument("--concurrency", type=int, default=1)
    p.add_argument("--name", default=None)
    a = p.parse_args()
    setup_logging()
    async def _run():
        async with app.open_async():
            await app.run_worker_async(
                queues=a.queues.split(","), concurrency=a.concurrency, name=a.name,
                shutdown_graceful_timeout=60,
            )
    asyncio.run(_run())

if __name__ == "__main__":
    main()
```

- 실행: `python -m seelo.worker.run --queues collect,measure,plan,report,email,periodic --concurrency 4`(01 5장의 compose 명령도 이 형식).
- API 프로세스: `main.py` lifespan에서 `async with app.open_async():` 안에서 서버를 돌린다(작업 등록용 풀).
- 스키마: `scripts/init_queue_schema.py`가 `SELECT to_regclass('procrastinate_jobs')`가 NULL일 때만 `procrastinate --app=seelo.worker.app.app schema --apply`와 같은 일을 한다(파이썬에서 `subprocess`로 부르거나 `app.schema_manager.apply_schema_async()`를 쓴다. 메서드 이름은 설치 버전에서 확인). Procrastinate를 올릴 때는 그 버전의 마이그레이션 SQL을 순서대로 적용한다.

## 2. 작업 함수 공통 규칙

1. 작업 인자는 **정수 ID만**(그리고 `round` 같은 작은 정수). 이메일·이름·토큰·값을 넣지 않는다(작업 인자는 DB `procrastinate_jobs`에 저장된다).
2. 작업은 몇 번 실행돼도 결과가 같아야 한다(멱등). 시작할 때 대상 행을 다시 읽고, 행이 없거나 상태가 기대와 다르면 `log.info("skip", reason=...)`만 남기고 끝낸다.
3. 상태 변경은 03의 `transition()`만 쓴다.
4. 외부 호출 동안 DB 트랜잭션을 열어 두지 않는다(읽기 트랜잭션 → 닫기 → 외부 호출 → 쓰기 트랜잭션).
5. 제한 시간은 작업 안에서 `async with asyncio.timeout(초):`로 건다(4장 표의 "제한").
6. 모든 작업은 `async def`다. 중단 요청(가게 변경·탈퇴)은 다음 `await`에서 `asyncio.CancelledError`로 온다. **`except BaseException`·`except asyncio.CancelledError`로 삼키지 않는다.** 정리가 필요한 자원(브라우저·HTTP 클라이언트)은 `async with`로 열어 자동으로 닫히게 한다.
7. **다음 작업 등록은 그 작업을 낳는 DB 변경과 같은 트랜잭션 안에서** `jobs.defer(session, ...)`(3장)로 한다. 커밋이 실패하면 작업도 등록되지 않고, 커밋되면 둘 다 남는다.
8. 시작·끝에 구조화 로그: `task`, `job_id`, 대상 ID, `duration_ms`, `result`(ok·skip·failed).

## 3. 작업 등록 도우미(`services/jobs.py`)

```python
from dataclasses import dataclass
from procrastinate import PsycopgConnector
from procrastinate.exceptions import AlreadyEnqueued

@dataclass
class JobLinks:
    store_id: int | None = None
    run_id: int | None = None
    fix_request_id: int | None = None

async def defer(session, task, *, args: dict, links: JobLinks,
                queueing_lock: str | None = None, lock: str | None = None,
                schedule_in: dict | None = None, queue: str | None = None) -> int | None:
    """열린 트랜잭션 안에서만 부른다. 작업 행·job_links 행이 서비스 데이터와 함께 커밋된다.
    같은 queueing_lock 대기 작업이 이미 있으면 None. queue는 callAi처럼 큐를 바꿀 때만."""
    opts = {k: v for k, v in
            {"queueing_lock": queueing_lock, "lock": lock, "schedule_in": schedule_in,
             "queue": queue}.items()
            if v is not None}
    try:
        async with session.begin_nested():                  # SAVEPOINT: 중복 오류가 바깥 트랜잭션을 깨지 않게
            if isinstance(getattr(task.blueprint, "connector", None), PsycopgConnector):
                # SAVEPOINT는 이 블록 안에서 연결을 처음 요청할 때 나간다. 반드시 블록 안에서 꺼낸다.
                sa_conn = await session.connection()
                raw = await sa_conn.get_raw_connection()
                opts["connection"] = raw.driver_connection  # psycopg.AsyncConnection
            job_id = await task.configure(**opts).defer_async(**args)
    except AlreadyEnqueued:
        return None
    session.add(JobLink(procrastinate_job_id=job_id, task_name=task.name,
                        store_id=links.store_id, run_id=links.run_id,
                        fix_request_id=links.fix_request_id))
    return job_id
```

- 테스트의 `InMemoryConnector`는 외부 연결을 받지 않으므로(`ConnectorException`) 위처럼 커넥터 종류를 보고 `connection`을 뺀다. 작업이 속한 앱은 `task.blueprint`다(Procrastinate 3.x).
- **연결은 `begin_nested()` 블록 안에서 꺼낸다.** SQLAlchemy는 SAVEPOINT를 중첩 트랜잭션 안에서 연결을 처음 요청할 때 보낸다. 블록 밖에서 꺼내 두면 SAVEPOINT가 나가지 않아, 중복 등록(`AlreadyEnqueued`) 뒤 바깥 트랜잭션이 `InFailedSqlTransaction`으로 깨진다(2026-10-24 2단계 테스트 ②에서 발견·수정).
- `raw.driver_connection`이 psycopg `AsyncConnection`임을 2026-10-24에 확인했다(SQLAlchemy 2.1.6: `get_raw_connection()` → `_ConnectionFairy`, `.driver_connection` → `psycopg.AsyncConnection`).
- 필수 통합 테스트 `test_defer_transactional.py`: ① 바깥 트랜잭션을 롤백하면 작업 행도 없음 ② 같은 `queueing_lock`을 두 번 등록해도 바깥 트랜잭션의 다른 변경은 커밋됨 ③ 커밋 뒤 워커가 그 작업을 실행.
- 서비스 함수 패턴:

```python
store = Store(...); session.add(store); await session.flush()       # id 받기
run = MeasurementRun(...); session.add(run); await session.flush()
await jobs.defer(session, collect_store, args={"store_id": store.id, "run_id": run.id},
                 links=JobLinks(store_id=store.id, run_id=run.id),
                 queueing_lock=f"collect:{store.id}:{run.id}", lock=f"store:{store.id}")
await session.commit()                                               # 가게·측정·작업이 함께 커밋
```

- `{provider}`는 그 작업이 다루는 지도(`google`·`kakao`)다. 등록하는 쪽이 대상 행에서 읽어 넣는다.
- `compareFixValues`는 카카오 파트너센터를 다시 읽어야 해서 브라우저가 있는 `fix` 큐에서 돈다(명세서 5장은 report 큐. 바꾼 이유는 브라우저 필요).
- 명세서의 중복 방지 키는 `queueing_lock`으로 넣었다. `queueing_lock`은 **대기 중인** 작업만 막으므로, 한 번만 실행돼야 하는 일은 DB로도 막는다: `callAi`는 `ai_executions` 고유 키·상태, `applyFix`는 정비안 승인 조건부 UPDATE + `fix_logs.fix_plan_item_id` 고유, 재측정 시작은 `remeasure_schedules` 조건부 UPDATE.
- `RetryStrategy` 재시도에서 "마지막 시도인지"는 작업 행의 `attempts`로 안다. `pass_context=True`로 받아 `context.job.attempts`를 읽는다(`sendEmail`이 최종 실패를 기록할 때 필요).

## 5. 주기 작업(`worker/periodic.py`)

모두 `periodic` 큐, `queueing_lock`은 자기 이름. 형태:

```python
@app.periodic(cron="5 * * * *")
@app.task(name="cleanupUnverified", queue="periodic", queueing_lock="cleanupUnverified")
async def cleanup_unverified(timestamp: int) -> None: ...

@app.periodic(cron="*/10 * * * *")
@app.task(name="retryStalledJobs", queue="periodic", queueing_lock="retryStalledJobs")
async def retry_stalled_jobs(timestamp: int) -> None:
    for job in await app.job_manager.get_stalled_jobs():
        await app.job_manager.retry_job(job)
```

| 이름 | cron(UTC) | 하는 일 |
|---|---|---|
| `cleanupUnverified` | `5 * * * *` | 24시간 지난 미인증 `users` 삭제. 만료된 `sessions`·`pending_signups`·`identify_sessions` 삭제. 1시간 지난 `rate_limits` 삭제. 사용·만료 뒤 7일 지난 `auth_tokens` 삭제 |
| `purgeSnapshots` | `30 18 * * *`(KST 03:30) | `expires_at < now()`인 `source_snapshots`·`web_evidence` 삭제. 7일 지난 끝난 작업 행(`status IN ('succeeded','failed','cancelled','aborted')`) 삭제와 그 `job_links` 삭제(공식 문서 "Delete finished jobs" 방법) |
| `checkPendingInvites` | `15 * * * *` | E31 |
| `recheckPendingFixes` | `25 * * * *` | 09 10장. 13단계 구현 |
| `dispatchRemeasures` | `*/10 * * * *` | 10 1장, E19 |
| `retryStalledJobs` | `*/10 * * * *` | 위 코드. 워커가 죽어 `doing`으로 남은 작업을 다시 시도(하트비트 30초 기준) |
| `failStuckWork` | `*/10 * * * *` | 아래 |

`failStuckWork`(마지막 안전장치)
- 측정: `status IN ('queued','running','parsing')`, `updated_at < now() - 30분`, `waiting_reason IS NULL`이고, `job_links.run_id = run.id`인 작업 중 `procrastinate_jobs.status IN ('todo','doing')`가 하나도 없음 → 측정 failed(`stuck`). 진단이면 가게 measure_failed + 메일 `diagnosis_result`(failed), 재측정이면 신청 remeasure_failed. 무료 차감 없음.
- 정비안: `generating`이 20분 넘음 → `generation_failed`(`last_error = 'stuck'`).
- 보고서: `generating`이 20분 넘음 → `generation_failed`.
- `procrastinate_jobs`의 상태 값 이름은 설치 버전의 스키마로 확인한다.
- 구현 메모(2026-10-28): `fix_plans`·`comparison_reports`에는 `updated_at`이 없어 "20분"은 `created_at` 기준이다. 다시 생성(E23·E24)한 행이 바로 실패로 바뀌지 않도록 **그 신청(`job_links.fix_request_id`)에 살아 있는 작업(todo·doing)이 없을 때만** 바꾼다. 측정 쪽 "작업 없음" 조건도 같은 `NOT EXISTS (job_links ⋈ procrastinate_jobs)` 문장이다. 코드: `services/maintenance.fail_stuck_work`, 실패 처리는 `services/run_failure.fail_run`(E3·질문 생성 실패와 공용).

## 6. 비용 기록과 하루 상한(W-04-2)

`config/pricing.json`(값은 각 회사 가격표를 보고 사람이 채운다, D-09. 형식은 16 3장):

```json
{
  "openai": { "<model id>": { "inputPer1M": 0.0, "outputPer1M": 0.0, "webSearchPerCall": 0.0 } },
  "gemini": { "<model id>": { "inputPer1M": 0.0, "outputPer1M": 0.0, "groundingPerQuery": 0.0 } }
}
```

- `cost_usd(provider, model, usage)` = 입력 토큰/1e6 × `inputPer1M` + 출력 토큰/1e6 × `outputPer1M` + 검색 횟수 × 건당 요금.
  - OpenAI 검색 횟수 = 응답 `output` 중 `type == "web_search_call"` 개수.
  - Gemini 검색 횟수 = `grounding_metadata.web_search_queries` 개수(Gemini 3 이상은 실행한 검색 질의마다 과금, 월 5,000건 무료 뒤 1,000건당 14달러 — 2026-10 공식 문서. 무료 구간은 계산에 넣지 않고 보수적으로 센다).
  - 모델이 표에 없으면 0을 넣고 경고 로그(측정은 계속).
- 측정에 속한 모든 LLM 호출(측정·추출·질문·웹사이트 정리·AI 웹 검색) 비용을 그 측정의 `measurement_runs.cost_usd`에 더한다(`UPDATE ... SET cost_usd = cost_usd + :c`). 정비안 생성 비용은 로그에만.
- 하루 상한: `runMeasurement` 시작 때 오늘(KST) 만든 측정들의 `cost_usd` 합이 `DAILY_COST_LIMIT_USD` 이상이면
  - 측정 `waiting_reason = 'cost_limit'`, 자신을 `schedule_in={"minutes": 30}`으로 다시 등록(같은 트랜잭션)하고 끝낸다.
  - 시작할 수 있게 되면 `waiting_reason = NULL`.
  - `DAILY_COST_LIMIT_USD = 0`이면 상한 없음(2026-10-28 구현 때 정함).

## 7. 작업 취소(E27 가게 변경, E28 [내 가게가 아니에요], E29 탈퇴)

```python
async def cancel_jobs(session, *, store_ids: list[int]) -> int:
    ids = (await session.scalars(
        select(JobLink.procrastinate_job_id).where(JobLink.store_id.in_(store_ids)))).all()
    n = 0
    for jid in ids:
        try:
            if await app.job_manager.cancel_job_by_id_async(jid, abort=True):
                n += 1
        except Exception:
            log.warning("cancel_failed", job_id=jid)
    return n
```

- 대기 중인 작업은 취소되고, 실행 중인 async 작업은 다음 `await`에서 `CancelledError`로 멈춘다. 중단된 작업은 재시도하지 않는다.
- 취소 요청은 **DB 정리 트랜잭션을 커밋하기 전에** 보낸다(취소 API는 자기 연결로 바로 반영된다). 그다음 DB 쪽 정리(측정 → canceled, 예약 → canceled, 또는 행 삭제)를 커밋한다. 늦게 깨어난 작업도 2장 규칙 2로 아무것도 쓰지 않는다.
- 측정·정비 작업의 `job_links`에는 항상 `store_id`를 넣는다(`callAi`처럼 측정에 딸린 작업도). `sendEmail`은 취소 대상이 아니므로 비워도 된다.
