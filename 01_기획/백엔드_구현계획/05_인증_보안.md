# 05. 인증·보안(F-01, 명세서 2장·9장)

## 1. 공통 함수(`security/`)

| 함수 | 구현 |
|---|---|
| `normalize_email(s)` | `s.strip().lower()` |
| `validate_password(p)` | 길이 8~128, 영문 1자 이상, 숫자 1자 이상: `re.fullmatch(r"(?=.*[A-Za-z])(?=.*\d).{8,128}", p)`. 실패면 `weak_password` |
| `hash_password(p)` / `verify_password(h, p)` | `argon2.PasswordHasher()`(기본값이 Argon2id). `verify` 성공 뒤 `check_needs_rehash(h)`면 새 해시로 바꿔 저장 |
| `new_token()` | `secrets.token_urlsafe(32)` |
| `hash_token(t)` | `hashlib.sha256(t.encode()).hexdigest()` |
| `email_hmac(email)` | `hmac.new(EMAIL_HMAC_KEY, normalize_email(email).encode(), "sha256").hexdigest()` |
| `encrypt_secret(s)` / `decrypt_secret(b)` | `cryptography.fernet.Fernet(MAIL_TOKEN_FERNET_KEY)` |
| `DUMMY_HASH` | 시작할 때 `hash_password(new_token())`로 한 번 만들어 둔 값. 없는 이메일 로그인 때도 `verify`를 한 번 돌려 응답 시간을 맞춘다 |

## 2. 세션

- 쿠키 이름 `seelo_session`, 값은 `new_token()` 원문. DB `sessions.token_hash`에는 해시만 둔다.
- 쿠키 속성: `HttpOnly`, `Secure`(=`COOKIE_SECURE`), `SameSite=Lax`, `Path=/`, `Max-Age = SESSION_TTL_DAYS * 86400`.
- `create_session(user)`: 세션 토큰과 CSRF 토큰을 새로 만들고 `sessions` 행 생성(`expires_at = now + 14일`). 응답에 `seelo_session`과 `seelo_csrf` 쿠키를 설정한다.
- `current_user` 의존성
  1. 쿠키가 없으면 401 `AUTH_REQUIRED`.
  2. `token_hash`로 행을 찾고 `expires_at > now`인지 본다. 아니면 401(만료 행은 지운다).
  3. `last_seen_at`이 5분보다 오래됐으면 `now`로 갱신(매 요청 쓰기를 피함).
  4. 사용자의 `email_verified_at`이 NULL이면 401(미인증 계정은 세션을 만들지 않지만 방어로 둔다). `terms_agreed_at`이 NULL이면 403 `TERMS_REQUIRED`.
- 유지 기간은 로그인 시점부터 14일 고정이다(활동으로 늘리지 않음) `[기획 확인]`.
- 삭제: 로그아웃은 그 행만, 비밀번호 재설정은 그 사용자의 모든 행, 비밀번호 변경은 지금 세션을 뺀 모든 행.

## 3. CSRF

- 쿠키 `seelo_csrf`(`HttpOnly` 아님, `Secure`, `SameSite=Lax`). 값 형식: `<무작위>.<서명>`, 서명 = `HMAC-SHA256(SECRET_KEY, 무작위)` hex 앞 32자.
- 발급
  - 로그인 전: `GET /api/auth/csrf`가 새 값을 쿠키로 준다.
  - 로그인·세션 생성 때: 새 값을 만들고 `sessions.csrf_token_hash = hash_token(값)`으로 세션에 묶는다.
- 검증(`verify_csrf` 의존성, POST·PUT·PATCH·DELETE 모든 라우터에 건다)
  1. 헤더 `X-CSRF-Token`과 쿠키 `seelo_csrf`가 둘 다 있고 같아야 한다.
  2. 서명이 맞아야 한다.
  3. 로그인한 요청이면 `hash_token(값) == session.csrf_token_hash`여야 한다.
  4. 하나라도 틀리면 403 `CSRF_FAILED`.
- CORS는 켜지 않는다(같은 출처).

## 4. 이메일 가입·인증(W-01-2, S02·S03)

### 4.1 `POST /api/auth/signup`

1. 요청 제한: `rate_limit("signup", ip, 5/분)` 넘으면 429 `RATE_LIMITED`.
2. 검증: 이메일 형식(`EmailStr`), 비밀번호 규칙, `password == passwordConfirm`, `agreeTerms and agreePrivacy`. 실패는 `VALIDATION_ERROR`의 필드 코드로.
3. 정규화한 이메일로 `users` 조회
   - 있고 `email_verified_at IS NOT NULL` → 409 `EMAIL_TAKEN`, `details.provider` = 그 사용자 `auth_identities.provider`.
   - 있고 미인증 → 그 사용자 행 삭제(CASCADE).
4. 같은 트랜잭션에서 `users`(미인증, `password_hash`, `terms_agreed_at = now`), `auth_identities`(provider email), `auth_tokens`(verify, `expires_at = now + 24시간`) 생성.
5. 메일: 같은 트랜잭션에서 `email_service.queue(session, "verify_email", user, params={}, secret={"token": 원문})` → `email_logs` 행(`secret_payload` 암호문) + `sendEmail` 등록.
6. 응답 201 `{email, mailTicket}`. `mailTicket` = `email_logs.id`를 `itsdangerous.URLSafeTimedSerializer(SECRET_KEY, salt="mail-ticket")`로 서명한 값(유효 1일).

### 4.2 `GET /api/auth/signup/mail-status?ticket=`

- 티켓을 풀어 `email_logs.status`를 준다. S03은 `failed`면 "메일을 보내지 못했어요. 다시 보내기를 눌러 주세요"를 보여 준다(3번 재시도 뒤 failed가 됨).

### 4.3 `POST /api/auth/verify-email/resend`

1. `rate_limit("resend", ip, 5/분)`.
2. 이메일로 미인증 사용자를 찾는다. 없거나 이미 인증됐으면 아무것도 하지 않고 같은 응답(202, 의미 없는 티켓)을 준다. 의미 없는 티켓(`email_logs.id` 자리에 0)으로 mail-status를 부르면 `sent`를 준다(진짜 티켓과 구별되지 않게).
3. 그 사용자의 가장 최근 verify 토큰 `created_at`이 60초 안이면 429 `RESEND_COOLDOWN`(`retryAfterSeconds`).
4. 이전 verify 토큰을 모두 `used_at = now`로 막고 새 토큰 + 메일.

### 4.4 `POST /api/auth/verify-email`

1. `hash_token(token)`으로 `auth_tokens`(type verify) 조회. 없음·`used_at` 있음·`expires_at <= now` → 410 `TOKEN_EXPIRED`.
2. 같은 트랜잭션: `used_at = now`(조건부 UPDATE `WHERE used_at IS NULL`, 영향 행 0이면 410), `users.email_verified_at = now`.
3. 중복 확인: 같은 이메일로 다른 인증된 사용자가 생겼으면(경쟁 상황) 410으로 막는다.
4. 세션 생성, 200 `{user}` → 화면은 S07.

### 4.5 미인증 계정 정리

`cleanupUnverified`(매시간, 06): `DELETE FROM users WHERE email_verified_at IS NULL AND created_at < now() - interval '24 hours'`.

## 5. 구글·카카오 로그인(W-01-3, S02·S04)

### 5.1 등록(Authlib Starlette 클라이언트)

```python
oauth = OAuth()
oauth.register(
    name="google",
    client_id=s.google_oauth_client_id, client_secret=s.google_oauth_client_secret,
    server_metadata_url="https://accounts.google.com/.well-known/openid-configuration",
    client_kwargs={"scope": "openid email profile"},
)
oauth.register(
    name="kakao",
    client_id=s.kakao_oauth_client_id, client_secret=s.kakao_oauth_client_secret,
    authorize_url="https://kauth.kakao.com/oauth/authorize",
    access_token_url="https://kauth.kakao.com/oauth/token",
    api_base_url="https://kapi.kakao.com/",
    client_kwargs={"scope": "account_email", "token_endpoint_auth_method": "client_secret_post"},
)
```

- Authlib Starlette 통합은 `state`를 `request.session`에 둔다. 그래서 `SessionMiddleware(secret_key=SECRET_KEY, session_cookie="seelo_oauth", max_age=600, same_site="lax", https_only=COOKIE_SECURE)`를 앱에 건다. 이 쿠키는 OAuth `state` 말고는 쓰지 않는다(로그인 세션은 2장의 `seelo_session`).
- **구현(2026-10-27, 3단계)은 위 Starlette 통합 대신 아래처럼 했다.** 가짜 모드(17 1장)와 테스트에서 제공자를 통째로 바꾸려고 제공자 호출을 `Clients.oauth`(`integrations/oauth.py`) 뒤로 숨겼다.
  - `state`: `oauth_service.start`가 `new_token()`을 만들어 `request.session["oauth"] = {provider, state, intent}`(위 `SessionMiddleware`)에 두고, 콜백에서 꺼내(한 번만 쓰임) `hmac.compare_digest`로 비교한다.
  - 인가 주소는 직접 만든다: `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`.
  - 토큰·사용자 정보: Authlib `AsyncOAuth2Client`(httpx, `token_endpoint_auth_method="client_secret_post"`, 10초)로 code → 토큰, 그다음 **userinfo 주소를 액세스 토큰으로 부른다**(구글도 id_token 서명 검증 대신 TLS로 구글에서 직접 받음).
  - 구글 주소(2026-10-27 https://accounts.google.com/.well-known/openid-configuration 확인): 인가 `https://accounts.google.com/o/oauth2/v2/auth`, 토큰 `https://oauth2.googleapis.com/token`, 사용자 정보 `https://openidconnect.googleapis.com/v1/userinfo`(`sub`, `email`, `email_verified`), `token_endpoint_auth_methods_supported`에 `client_secret_post` 있음.
  - 설정(클라이언트 ID·시크릿)이 비었으면 시작 단계에서 `/{intent}?error=oauth_failed`로 보낸다.
- 리디렉션 주소: `{APP_BASE_URL}/api/oauth/{provider}/callback`. 각 개발자 콘솔에 정확히 이 값을 등록한다.
- 카카오 확인 사항(2026-10-23 카카오 로그인 REST API 문서)
  - 인가: `GET https://kauth.kakao.com/oauth/authorize?client_id={REST API 키}&redirect_uri=&response_type=code&scope=account_email&state=`
  - 토큰: `POST https://kauth.kakao.com/oauth/token`, `Content-Type: application/x-www-form-urlencoded;charset=utf-8`, 본문 `grant_type=authorization_code`, `client_id`, `redirect_uri`, `code`, `client_secret`. **REST API 키의 클라이언트 시크릿은 기본으로 켜져 있어** `client_secret`이 사실상 필수다(`KAKAO_OAUTH_CLIENT_SECRET` 필수). Authlib `token_endpoint_auth_method="client_secret_post"`가 본문에 넣는다.
  - 사용자가 동의를 취소하면 콜백에 `error=access_denied`(`error_description=User denied access`).
  - 사용자 정보: `GET https://kapi.kakao.com/v2/user/me`(Bearer). `kakao_account.has_email`은 폐지 예정이라 쓰지 않는다.
  - OIDC도 지원하지만(발급자 `https://kauth.kakao.com`) 베타에서는 쓰지 않고 위 사용자 정보 API만 쓴다.
- 카카오 이메일을 필수 동의로 받으려면 비즈 앱 전환이 필요한지는 `[PoC]`(기획서 13.1). 필수가 아니어도 아래 흐름은 이메일이 없을 때를 처리한다.

### 5.2 `GET /api/oauth/{provider}/start?intent=signup|login`

- `redirect_uri`를 위 주소로 `authorize_redirect`. `intent`는 `request.session["oauth_intent"]`에 둔다(취소·오류 때 S02로 갈지 S05로 갈지).

### 5.3 콜백 처리 순서

1. 쿼리에 `error`가 있으면(사용자 취소는 `access_denied`) → `/{signup|login}?error=oauth_canceled`.
2. `token = await oauth.<p>.authorize_access_token(request)`. 예외(상태 불일치 포함) → `?error=oauth_failed`.
3. 제공자 정보
   - 구글: `token["userinfo"]`에서 `sub`, `email`, `email_verified`. `email_verified`가 true가 아니면 이메일 없는 것으로 보지 않고 **가입을 막는다** → `/signup?error=oauth_failed`(W-01-3 "구글 이메일이 인증되지 않았으면 가입하지 않는다").
   - 카카오: `GET https://kapi.kakao.com/v2/user/me`(Bearer, Authlib `oauth.kakao.get("v2/user/me", token=token)`). `id`(숫자 → 문자열), `kakao_account.email`, `kakao_account.is_email_valid`, `kakao_account.is_email_verified`, `kakao_account.email_needs_agreement`. `email`이 있고 `is_email_valid`와 `is_email_verified`가 모두 true일 때만 "인증된 이메일"로 본다. 그 밖(동의 안 함, `email_needs_agreement = true` 포함)은 이메일 없음.
4. `auth_identities`에서 (provider, provider_user_id)로 기존 연결 조회
   - 있으면: 그 사용자가 인증 완료면 세션 생성 → `/home`. 미인증(카카오 S04에서 인증을 안 마침)이면 `/signup/sent`.
5. 없으면(첫 가입)
   - 인증된 이메일이 있음: `users`에서 그 이메일 조회. 인증된 사용자가 있으면 → `/signup?error=email_taken&provider={기존 가입 방식}`. 미인증 사용자만 있으면 그 행 삭제.
   - `pending_signups` upsert(provider, provider_user_id, email 또는 NULL, 새 토큰 해시, `expires_at = now + 30분`). 쿠키 `seelo_pending`(HttpOnly, 30분)에 토큰 원문.
   - 이메일 있음 → `/signup/terms`, 없음 → `/signup/kakao-email`.

### 5.4 `POST /api/auth/pending-signup/complete`

1. 쿠키 `seelo_pending`으로 행을 찾는다. 없거나 만료면 404.
2. 약관 둘 다 true가 아니면 422 `terms_required`.
3. 이메일
   - 행에 이메일이 있으면 그것을 쓴다(요청의 email 무시).
   - 없으면 요청 `email` 필수. 형식 검사. 그 이메일의 인증된 사용자가 있으면 409 `EMAIL_TAKEN`. 미인증 사용자만 있으면 삭제.
4. 생성
   - 이메일이 제공자 인증 이메일: `users`(email, `email_verified_at = now`, `terms_agreed_at = now`, `password_hash` NULL) + `auth_identities`. 세션 생성 → 200 `{next: "/home"}`.
   - 사장님이 입력한 이메일(카카오): `users`(미인증) + `auth_identities`(kakao) + verify 토큰 + 메일 → 202 `{next: "/signup/sent", mailTicket}`. 인증 링크를 누르면 4.4로 끝난다.
5. `pending_signups` 행 삭제, 쿠키 삭제.

## 6. 로그인·잠금(W-01-4, S05)

`POST /api/auth/login`:

1. 이메일로 사용자 조회. 없으면 `verify_password(DUMMY_HASH, password)` 뒤 401 `INVALID_CREDENTIALS`.
2. `locked_until > now`면 비밀번호를 보지 않고 423 `ACCOUNT_LOCKED`.
3. `password_hash`가 NULL(소셜 가입)이면 409 `SOCIAL_ACCOUNT`(provider).
4. 비밀번호 틀림: `failed_login_count += 1`. 5가 되면 `locked_until = now + 10분`, `failed_login_count = 0`으로 바꾸고 423. 아니면 401. (조건부 UPDATE로 원자적으로)
5. 맞음: 미인증이면 403 `EMAIL_NOT_VERIFIED`(화면은 S03). 인증됐으면 `failed_login_count = 0`, `locked_until = NULL`, 세션 생성, 200.

## 7. 비밀번호 재설정(W-01-5, S06)

`POST /api/auth/password/forgot`:
1. `rate_limit("pwreset", ip, 5/분)`.
2. 항상 202 `{}`. 안에서는:
   - 인증된 이메일 가입 사용자: reset 토큰(`expires_at = now + 1시간`) + 메일 `password_reset`(링크 포함). 이전에 보낸 쓰지 않은 reset 토큰은 `used_at = now`로 막는다(마지막 메일의 링크만 유효, 2026-10-27 구현 때 추가).
   - 소셜 가입 사용자: 메일 `password_reset`(params `{socialProvider}`), 링크 없음, "[구글/카카오]로 로그인하세요".
   - 없거나 미인증: 아무것도 보내지 않음.

`POST /api/auth/password/reset`:
1. 토큰 조회(type reset). 없음·사용됨·만료 → 410.
2. 비밀번호 규칙·확인 검사.
3. 같은 트랜잭션: 조건부로 `used_at = now`, `password_hash` 교체, `failed_login_count = 0`, `locked_until = NULL`, 그 사용자 세션 전부 삭제.
4. 204.

## 8. 계정 설정(S14)

- `POST /api/account/password`: 소셜 가입이면 409 `PASSWORD_LOGIN_UNAVAILABLE`. 지금 비밀번호 확인(틀리면 400 `WRONG_PASSWORD`, 잠금 횟수는 올리지 않음), 새 비밀번호 규칙 검사, 교체, 지금 세션을 뺀 세션 삭제.

## 9. 탈퇴(W-01-6, `account_service.delete_account`)

1. `confirmText` 확인.
2. 이 사용자의 가게 ID 목록을 구한다(보관 포함).
3. **작업 취소**(06 7장): 그 가게들의 `job_links`에 있는 작업을 모두 취소 요청한다. 실패해도 계속한다(작업은 대상 행이 없으면 스스로 끝난다).
4. 같은 트랜잭션
   1. 무료 진단을 쓴 적이 있으면(`free_usage_ledger`에 있거나, 이 사용자 가게에 `is_free AND status='completed'` 측정이 있으면) `free_usage_ledger`에 `email_hmac` 추가(`ON CONFLICT DO NOTHING`).
   2. `audit_logs`(actor NULL, `account.delete`, target user, detail `{}`).
   3. `DELETE FROM users WHERE id = :id`(CASCADE로 나머지 삭제. 재측정 예약도 함께 지워진다).
5. 쿠키 삭제, 204.

- 확인 테스트: 삭제 뒤 모든 테이블에서 그 사용자 ID를 가리키는 행이 0개(`free_usage_ledger` 제외), 그 이메일로 다시 가입한 계정은 `has_used_free = true`.

## 10. 요청 제한(`security/ratelimit.py`)

```sql
INSERT INTO rate_limits (key, window_start, count)
VALUES (:key, :window, 1)    -- :window = 앱 시계(now_utc)를 분 단위로 자른 값
ON CONFLICT (key, window_start) DO UPDATE SET count = rate_limits.count + 1
RETURNING count;
```

- 반환값이 한도를 넘으면 429(`retryAfterSeconds` = 다음 분까지 남은 초).
- 창 시작을 DB `now()` 대신 앱 시계로 정한다: `retryAfterSeconds`와 같은 시계를 쓰고, 테스트가 시간을 멈춰(`frozen_time`) 분 경계에서 나뉘는 일을 막는다(2026-10-27 전체 테스트에서 경계에 걸려 한 번 실패한 뒤 바꿈).
- 키: `signup:{ip}`, `pwreset:{ip}`, `resend:{ip}`, `identify:{userId}`(분당 10).
- IP는 `request.client.host`(uvicorn `--proxy-headers`가 nginx의 `X-Forwarded-For`를 반영). 신뢰 프록시 밖에서 온 `X-Forwarded-For`는 무시된다.

## 11. 권한 검사 도우미(`api/deps.py`)

| 의존성 | 동작 |
|---|---|
| `require_user` | `current_user`. 없으면 401 |
| `require_admin` | `require_user` 후 `role != 'admin'`이면 403 |
| `load_owned_store(store_id)` | `stores.owner_id == user.id` 또는 관리자. 아니면 404 |
| `load_owned_run(run_id)` | 측정 → 가게 → 소유 확인 |
| `load_owned_plan(plan_id)` | 정비안 → 신청 → `user_id` 확인 + 응답 조건(04 7.3) |
| `load_owned_report(report_id)` | 보고서 → 신청 → 소유 + `status = completed` |

- 남의 ID에는 404를 준다(존재를 드러내지 않음). 관리자 전용 경로에 사장님이 오면 403.
- 테스트: 사용자 A·B를 만들고 B의 ID로 A가 모든 GET·POST를 호출해 404·403이고 응답 본문에 B의 내용이 없는지 확인한다(W-11-1).

## 12. 비밀 값과 로그

- 비밀번호·토큰·세션·CSRF 값·OAuth `code`·API 키·이메일 원문은 로그에 남기지 않는다(01 7.5 가림 처리기).
- **접근 로그도 같은 규칙이다**(2026-10-27 Compose 확인에서 uvicorn·nginx 기본 접근 로그가 콜백의 `code=`·`state=`, 메일 티켓을 그대로 남기는 것을 발견).
  - uvicorn은 `--no-access-log`. 앱 미들웨어가 `http_request`(method, path, status, ms, request_id)를 남긴다. **쿼리 문자열은 남기지 않는다.**
  - nginx는 `log_format seelo`로 `$request_method $uri`만 남긴다(쿼리·Referer 없음). 메일 링크 화면 경로(`/verify-email/…`, `/password/reset/…`)는 `***`로 가린다. 응답에 `Referrer-Policy: no-referrer`.
  - 테스트: 콜백 뒤 수집한 로그에 `code`·`state` 값이 없다(`test_w_01_3.py`).
- 작업 인자(Procrastinate가 DB에 저장)에는 ID만 넣는다. 이메일 주소·토큰·이름을 넣지 않는다.
- 메일 링크 토큰은 `email_logs.secret_payload`에 Fernet 암호문으로만 두고, 발송 성공 또는 최종 실패 때 NULL로 바꾼다.
- 확인 테스트(W-01-2, W-11-1): 가입·재설정 시나리오를 돌린 뒤 DB 전체 텍스트 덤프(`pg_dump --data-only`)와 로그에서 토큰 원문·비밀번호 원문 검색 결과가 0건.
