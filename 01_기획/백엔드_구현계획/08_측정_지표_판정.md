### 0.2 영업시간 `WeeklyHours`

```json
{
  "days": { "mon": [{"open": "11:00", "close": "21:00"}], "tue": [], "wed": null, "thu": [], "fri": [], "sat": [], "sun": [] },
  "breaks": { "mon": [{"start": "15:00", "end": "17:00"}] },
  "notes": null
}
```

- 요일 값: `[]` = 쉬는 날, `null` = 정보 없음, 구간 목록 = 영업. `close`가 `open`보다 이르면 다음 날 새벽까지다("18:00"~"02:00").
- Google `regularOpeningHours.periods[]`(`open/close.day` 0=일요일, `hour`, `minute`) → 변환 함수 `from_google_periods`. 24시간 영업(`close` 없음)은 `{"open":"00:00","close":"24:00"}`.
- 비교 `hours_diff(a, b) -> list[day]`: 두 쪽 모두 `null`이 아닌 요일만 비교한다. 구간을 분 단위로 정렬해 다르면 그 요일을 돌려준다.
- 구현 메모(2026-10-28, 13단계): `open_minutes(w, day)` = 그 요일에 실제로 여는 구간(쉬는 시간을 뺌, 새벽까지면 close + 24시간). 칸 값 비교 `same_value("hours", …)`는 이것으로 한다(쉬는 시간을 따로 적었든 구간을 나눴든 같은 영업시간이면 같음).

### 0.4 LLM 출력 스키마 작성 규칙(`schemas/llm.py`)

OpenAI 구조화 출력(엄격 모드)은 모든 필드가 `required`이고 `additionalProperties: false`인 스키마를 기대한다. 그래서 LLM이 채우는 Pydantic 모델은 아래를 지킨다.

1. 모든 필드에 기본값을 주지 않는다. 값이 없을 수 있으면 `X | None`으로 쓰고 모델이 `null`을 넣게 한다.
2. 자유 키 딕셔너리(`dict[str, X]`)를 쓰지 않는다. 키가 정해진 객체나 `list[객체]`로 바꾼다.
3. 선택지는 `Literal[...]`로 쓴다.
4. 중첩은 3단계 이하.
5. 모델 이름 끝에 `Out`을 붙여 API 스키마와 구분한다(예: `ExtractionOut`).

영업시간은 LLM용 별도 형식을 쓰고 코드에서 0.2 `WeeklyHours`로 바꾼다:

```python
Day = Literal["mon", "tue", "wed", "thu", "fri", "sat", "sun"]

class IntervalOut(BaseModel):
    open: str            # "HH:MM"
    close: str           # "HH:MM", 자정 넘으면 다음 날 시각

class DayHoursOut(BaseModel):
    day: Day
    closed: bool         # 쉬는 날
    intervals: list[IntervalOut]
    breaks: list[IntervalOut]

class WeeklyHoursOut(BaseModel):
    days: list[DayHoursOut]   # 텍스트에 나온 요일만. 없는 요일은 넣지 않음(→ WeeklyHours에서 null)
    notes: str | None
```

변환 `to_weekly_hours(out)`: 넣지 않은 요일은 `null`, `closed`면 `[]`, 시각 형식이 `^\d{1,2}:\d{2}$`가 아니면 그 요일을 `null`로 둔다(추측 금지).

### 1.2 생성(LLM, `OPENAI_CHEAP_MODEL`, `structured`)

```text
Write exactly 3 questions that a foreign tourist visiting Korea might ask an AI assistant to find places.
Q1: English. Ask for good {cuisine_en} near {region_en}.
Q2: English. Ask for {feature_en} {cuisine_en} near {region_en}. The condition "{feature_en}" must appear.
Q3: Korean. Ask for good {cuisine_ko} near {region_ko}, casual tone (반말 요청형, e.g. "...추천해줘").
Rules: Do not mention any specific business name. Each question under 20 words. Natural, like a real traveler.
Also give a Korean translation for Q1 and Q2.
```

출력 스키마:

```python
class GeneratedQuestionOut(BaseModel):
    lang: Literal["en", "ko"]
    intent_type: Literal["basic", "conditional"]
    text: str
    text_ko: str | None

class GeneratedQuestionsOut(BaseModel):
    questions: list[GeneratedQuestionOut]
    region_en: str | None
```

### 1.3 검증 `validate_questions(...) -> list[str]`(오류 코드 목록, 비면 통과)

| 규칙 | 오류 코드 |
|---|---|
| 정확히 3개, 순서가 (en, basic), (en, conditional), (ko, basic) | `bad_structure` |
| 가게 이름 없음: 정규화한 질문 문장에 정규화한 이름 후보(2자 이상) 중 하나라도 들어 있으면 실패 | `contains_store_name` |
| 지역 포함: 영어 질문은 정규화한 `region_en`(영숫자만 소문자, 예 "myeongdong"), 한국어 질문은 `region_ko` 또는 끝 "동"을 뺀 형태가 들어 있음 | `missing_region` |
| 업종 포함: 영어 질문에 업종 단어(아래) 하나 이상, 한국어 질문에 한국어 업종 단어 하나 이상 | `missing_category` |
| 질문 2에 조건 표현의 핵심 단어(예: vegetarian, affordable, credit card, reservation) 포함 | `missing_condition` |
| 3개가 서로 다름(정규화 후) | `duplicate` |
| 각 200자 이하 | `too_long` |

업종 단어: restaurant → en `restaurant, restaurants, food, eat, dining, bbq` + cuisine 단어 / ko `식당, 맛집, 음식점, 한식, 일식, 중식, 고깃집, 레스토랑`. cafe → en `cafe, cafes, café, coffee` / ko `카페, 커피`. bar → en `bar, bars, pub, drinks, cocktail` / ko `술집, 바, 펍, 주점`.

### 1.4 흐름

1. 측정 `stage = generating_questions`.
2. 같은 가게의 기존 질문 세트가 있고(다시 시도한 진단), 그 세트의 지역·업종이 지금과 같으면 그 세트를 다시 쓴다. 아니면 새로 만든다.
3. 생성 → 검증. 실패하면 3번까지 다시 생성. 그래도 실패하면 템플릿(1.5), `generated_by = template`. 템플릿도 검증한다(가게 이름이 지역 이름과 같은 드문 경우 실패할 수 있음 → 그때는 측정 failed `collect_insufficient`).
4. 한 트랜잭션: `question_sets`(version = 그 가게 최대 + 1) + `questions` 3행 저장, `measurement_runs.question_set_id` 설정, `stage = calling_ai`, `runMeasurement` 등록.

구현 메모(2026-10-28, 6단계)
- 비교용 정규화: 질문 문장은 NFKC·소문자·한글·영문·숫자만, 이름 후보는 `normalize_name`(지점 표기 삭제). 그래서 "명동 교자"처럼 띄어 써도 걸린다.
- 한국어 지역의 "끝 '동'을 뺀 형태"는 **두 글자 이상 남을 때만** 쓴다("성수동" → "성수", "명동"은 그대로. "명" 한 글자로 통과하는 것을 막음).
- 조건 핵심 단어(`missing_condition`): vegetarian(vegetarian·vegan), budget(affordable·cheap·budget·inexpensive), card_payment(credit card·card), reservation(reservation·reserve·booking), takeout(takeout·take out·takeaway·to go), outdoor_seating(outdoor·terrace·patio), kid_friendly(kid·child·family), group_friendly(group). 코드: `domain/questions.py`의 `CONDITION_WORDS`.
- LLM 호출 오류도 생성 실패 1번으로 센다(3번이면 템플릿). 생성 호출 비용은 측정 `cost_usd`에 더한다.
- `region_en`을 끝내 못 얻은 채 템플릿으로 가면 한글 지역 이름을 그대로 쓴다(추론: Google 영문 응답도 LLM도 실패한 드문 경우).
- 이름 후보(4.2)는 `question_service.target_names`로 모은다(7단계 finalizeRun이 같은 함수를 쓴다).

### 1.5 템플릿

| 업종 | Q1(en) | Q2(en) | Q3(ko) |
|---|---|---|---|
| restaurant | What are good {cuisine_en} near {region_en}? | Where can I find {feature_en} {cuisine_en} near {region_en}? | {region_ko} 근처 맛있는 {cuisine_ko} 추천해줘 |
| cafe | What are nice cafes near {region_en}? | Where can I find a {feature_en} cafe near {region_en}? | {region_ko} 근처 괜찮은 카페 추천해줘 |
| bar | What are good bars near {region_en}? | Where can I find a {feature_en} bar near {region_en}? | {region_ko} 근처 분위기 좋은 술집 추천해줘 |

템플릿의 `text_ko`(Q1·Q2 번역)는 고정 문구: Q1 "{region_ko} 근처 괜찮은 {cuisine_ko}는?", Q2 "{region_ko} 근처 {feature_ko} {cuisine_ko}는 어디야?".

- 구현 메모: Q2의 조건 표현은 영어 어순에 맞춰 붙인다(`with_feature`). `with …`·`that …`로 시작하면 명사 뒤("Korean restaurants with takeout", "a cafe that accepts credit cards"), 그 밖은 앞("vegetarian-friendly Korean restaurants", 관사 a/an 맞춤). 표 그대로면 "Where can I find with takeout Korean restaurants"가 된다.
- `text_ko`의 "는"은 받침에 따라 "은/는"을 고른다("한식당은", "카페는").

## 2. AI 측정(F-06, W-04-2~4)

### 2.1 `runMeasurement(run_id)`

1. 측정이 `running`이고 `question_set_id`가 있어야 한다. 아니면 끝.
2. 비용 상한(06 6장). 넘으면 대기 등록하고 끝.
3. `ai_executions` 만들기: 질문 3 × 공급자 2(`openai`, `gemini`) × `repeat_no` 1~`AI_REPEAT_COUNT`. `INSERT ... ON CONFLICT (run_id, question_id, provider, repeat_no) DO NOTHING`. `progress_total` = 행 수(60), `stage = calling_ai`.
4. 3번과 같은 트랜잭션에서, 상태가 `pending`·`running`인 실행마다 `callAi(execution_id)`를 공급자 큐(`ai_openai`·`ai_gemini`)에 등록(`queueing_lock = callAi:{id}`). 워커가 재시작돼 다시 실행돼도 끝난(succeeded·failed) 실행은 등록하지 않는다(W-04-3).

- 구현 메모: `DAILY_COST_LIMIT_USD = 0`이면 상한 없음(검사하지 않음). 기본값이 0이라 그대로 두면 모든 측정이 대기하게 되므로.

### 2.2 `callAi(execution_id)`

1. 실행·측정·질문을 읽는다. 실행이 끝났거나 측정이 `running`이 아니면 끝.
2. 실행 `status = running`.
3. 시도 최대 3번(처음 1 + 다시 2). 매 시도 `attempt` 저장 후 `web_answer(question.text, model)`을 `asyncio.timeout(60)`으로 부른다.
   - **질문 문장만 보낸다.** 시스템 지시·앞뒤 문장 없음.
   - 다시 시도할 오류: 시간 초과, 429, 5xx, 연결 오류, 빈 답변(`empty_answer`). 대기 2초, 4초(±20% 무작위).
   - 바로 실패할 오류: 400, 401, 403, 404(설정 오류) → 오류 추적(Sentry)에도 보낸다.
4. 성공(한 트랜잭션, 순서 지킴)
   1. **측정 행 먼저 갱신**: `UPDATE measurement_runs SET cost_usd = cost_usd + :c, progress_done = progress_done + 1 WHERE id = :run`(이 UPDATE가 측정 행 잠금을 잡아 같은 측정의 완료 처리들을 한 줄로 세운다).
   2. `ai_responses`: `raw_text`, `raw_json`, `source_urls`, `annotated_text`(3.1).
   3. 실행: `succeeded`, `model_id`, `latency_ms`, 토큰, `web_search_calls`, `cost_usd`, `finished_at`.
   4. `extractRecommendations(response_id)` 등록.
5. 최종 실패(한 트랜잭션): ① 측정 행 `progress_done += 1`(잠금) ② 실행 `failed`, `error_code`(`timeout`·`rate_limited`·`server_error`·`bad_request`·`auth_error`·`empty_answer`·`refused`·`unknown`), `finished_at` ③ `maybe_finalize(session, run_id)`.

`maybe_finalize(session, run_id)`: **측정 행 잠금을 잡은 트랜잭션 안에서만** 부른다(위 ①, 또는 `SELECT ... FROM measurement_runs WHERE id = :run FOR UPDATE`). 그 측정의 실행 중 `pending`·`running`이 0개이고, 성공 실행의 응답 중 `extraction_status = pending`이 0개면 `finalizeRun(run_id)` 등록(`queueing_lock`으로 중복 없음).
- 왜 잠금이 필요한가: 마지막 두 호출이 동시에 끝나면, 잠금 없이는 서로 상대가 아직 `running`으로 보여 아무도 `finalizeRun`을 등록하지 않을 수 있다. 측정 행을 먼저 UPDATE하면 두 번째 트랜잭션은 첫 번째가 커밋될 때까지 기다리고, PostgreSQL 기본 격리 수준(READ COMMITTED)에서 다음 문장부터 첫 번째의 변경을 본다.
- 테스트(W-04-3): 마지막 두 실행을 동시에 끝내는 테스트에서 `finalizeRun`이 정확히 1번 등록된다(실제 PG, 두 세션).

구현 메모(2026-10-28)
- 다시 시도: `timeout`·`rate_limited`·`server_error`(연결 오류 포함)·`empty_answer`. 바로 실패: `bad_request`(400·404)·`auth_error`(401·403)·`refused`·`not_configured`·`unknown`. 설정 오류(400·401·403·404·모델 미설정)는 `log.error`로 오류 추적에 보낸다.
- 호출 중 측정이 끝나거나 취소되면(측정 행이 `running`이 아님) 결과를 저장하지 않고 버린다. 다른 워커가 같은 실행을 먼저 끝냈어도 버린다(조건부 UPDATE).
- 비용 표 조회는 응답의 모델 ID로 한다(없으면 설정한 모델 이름).

### 2.3 공급자 구현(2026-10-23 공식 문서로 확인)

측정 조건 고정: 정비 전·후 비교가 성립하려면 호출 옵션이 늘 같아야 한다. 아래 옵션 값을 상수(`MEASURE_TOOL_OPTIONS`)로 두고, 측정마다 `ai_executions.model_id`와 함께 옵션 버전 문자열(`"openai:web_search/medium/no-location;gemini:google_search"`)을 `raw_json`에 남긴다. 사용자 위치(`user_location`)는 넣지 않는다 `[기획 확인: 관광객 위치를 흉내 낼지]`.

OpenAI(`integrations/openai_client.py`, `AsyncOpenAI`). 도구 이름은 `web_search`(이전 이름 `web_search_preview`는 쓰지 않음):

```python
resp = await client.responses.create(
    model=model,
    input=text,                                                   # 질문 문장 그대로

        search_calls += 1

usage = (resp.usage.input_tokens, resp.usage.output_tokens)

```

- 인용(`url_citation` 주석)만 지표의 "출처"로 쓴다. `web_search_call.action.sources`(참고한 전체 목록, 인용보다 많음)는 `raw_json`에만 남긴다.
- 메시지 내용에 `type == "refusal"`이 있으면 실패(`refused`)로 본다. `answer`가 빈 문자열이면 `empty_answer`.
- 구조화 출력(`structured`): `resp = await client.responses.parse(model=..., input=..., text_format=Schema)` → `resp.output_parsed`. `output_parsed`가 None이거나 거절이면 예외. 웹 검색 도구와 구조화 출력을 한 호출에 섞지 않는다(공식 문서에 조합 언급이 없음). 그래서 정보 수집은 "웹 검색 답변 → 구조화 정리" 두 번 호출이다(07 6.4).

Gemini(`integrations/gemini_client.py`, `google-genai`):

```python
from google import genai
from google.genai import types
client = genai.Client(api_key=key)
resp = await client.aio.models.generate_content(
    model=model, contents=text,
    config=types.GenerateContentConfig(tools=[types.Tool(google_search=types.GoogleSearch())]),

answer = resp.text
cand = resp.candidates[0] if resp.candidates else None
gm = cand.grounding_metadata if cand else None

supports = (gm.grounding_supports if gm else None) or []    # support.segment.{start_index,end_index,text}, support.grounding_chunk_indices

usage = (resp.usage_metadata.prompt_token_count, resp.usage_metadata.candidates_token_count)

```

- 출처 `uri`는 `https://vertexaisearch.cloud.google.com/grounding-api-redirect/...` 형태의 리디렉션 주소이고, `title`이 원래 사이트 도메인(예: `uefa.com`)이다(공식 문서 예시). 그래서 `url = uri` 그대로 저장하고 `domain = domain_of("https://" + title)`로 정한다. `title`이 비었거나 공백을 포함하면 `domain = "unknown"`. 리디렉션을 따라가지 않는다.
- 인용 위치: 공식 예시는 `end_index`를 문자열 위치로 쓰지만 단위가 명시돼 있지 않다. 그래서 위치는 `segment.text`로 찾는다: `pos = answer.find(segment.text)` → 찾으면 `char_end = pos + len(segment.text)`, 못 찾으면 `end_index`가 `len(answer)` 이하일 때만 그 값을 쓰고, 아니면 그 인용은 위치 없이 출처 목록에만 넣는다.
- 그라운딩 메타데이터가 비어 오는 경우가 있다(개발자 포럼 보고). 그때는 출처 `[]`로 저장하고 **실패로 보지 않는다**(답변 원문이 있으면 성공).
- 설치 SDK 확인(2026-10-28, google-genai 2.33.0·openai 3.37.0): `GroundingChunkWeb`에 `uri`·`title` 말고 **`domain`도 있다**. 그래서 도메인은 `web.domain` → `title` 순으로 정한다(둘 다 비거나 공백이 있으면 `unknown`). 모델 ID는 응답의 `model_version`(없으면 요청한 모델). OpenAI `url_citation`의 `url`·`title`·`start_index`·`end_index`, `web_search_call`, `include` 값 `web_search_call.action.sources` 모두 SDK 형식에 있음.
- 비용: Gemini 3 이상은 실행한 검색 질의(`web_search_queries`)마다 과금된다(06 6장).

`source_urls` 저장 형식: `[{"n": 1, "url": "...", "title": "...", "domain": "tripadvisor.com"}]`. 같은 URL은 처음 나온 번호 하나로 묶는다.

## 3. 추천 추출 `extractRecommendations(response_id)`(F-07, W-05-1)

### 3.1 출처 번호 넣기(`domain/annotate.py`, `callAi`에서 저장)

- 인용 위치(OpenAI `end_index`, Gemini `segment.end_index`)마다 그 위치 바로 뒤에 `[n]`을 넣은 문자열이 `annotated_text`다. 뒤에서부터 넣어 앞 위치가 밀리지 않게 한다.
- 인용 위치가 없으면 `annotated_text = raw_text`.

### 3.2 추출(LLM, `OPENAI_CHEAP_MODEL`, `structured`, 60초)

입력: `annotated_text`, 출처 목록(`[n] domain`), 우리 가게 이름 후보 중 **사장님 입력 이름과 Google 이름(ko·en)만**(카카오·네이버 이름은 AI에 보내지 않는다).

```text
You read an AI assistant's answer about places to eat or drink.
1) List every specific, named business the answer recommends, in the order they first appear.
   Do not list areas, streets, dishes, or chains mentioned only in passing.
   For each, give the citation numbers [n] attached to sentences about it,
   and which of these reasons the answer gives for it: {attribute keys with English phrases}.
2) If the answer talks about any of these target places: {target names},
   list its factual claims about opening hours, location, price, or phone, copied from the answer.
If no specific businesses are recommended, return empty lists.
```

```python
class ExtractedRecOut(BaseModel):
    name: str
    order: int                         # 답변에서 처음 나온 순서(1부터)
    source_numbers: list[int]
    mentioned_attributes: list[AttributeKey]   # AttributeKey = Literal[0.1의 키들]

class TargetClaimOut(BaseModel):
    field: Literal["hours", "location", "price", "phone"]
    value: str

class ExtractionOut(BaseModel):
    recommendations: list[ExtractedRecOut]
    target_claims: list[TargetClaimOut]
```

### 3.3 후처리(코드)

1. 이름이 빈 항목 삭제. `order`로 정렬한 뒤 `rank = 1, 2, 3, ...`으로 다시 매긴다(문장형 답변도 언급 순서가 순위).
2. 같은 응답 안에서 `normalize_name`이 같은 항목은 첫 번째만 남긴다.
3. `source_numbers` → `source_urls`(`[{url, domain}]`). 없는 번호는 버린다.
4. `recommendations` 행 저장(`is_target = false`, 판정은 4장), `ai_responses.extraction_json`, `target_claims`, `extraction_status = succeeded`.
5. 추천이 0개인 응답도 성공이다(우리 가게 미등장으로 정상 집계).
6. 실패(스키마 오류·거절·시간 초과): 작업 안에서 1번 다시. 그래도 실패면 `extraction_status = failed`, 측정 `extraction_failed_count += 1`. 원문은 남긴다.
7. 4·6번의 저장은 한 트랜잭션이며, 그 트랜잭션은 **먼저 측정 행을 잠근다**(`SELECT ... FOR UPDATE`, 6번은 `extraction_failed_count` UPDATE가 잠금). 마지막에 `maybe_finalize(session, run_id)`.

구현 메모(2026-10-28, 7단계)
- 프롬프트·후처리는 `domain/extraction.py`(`extraction_prompt`, `postprocess`). 프롬프트 끝에 `Sources:`(`[n] 도메인`)와 `Answer:\n<<<\n{annotated_text}\n>>>`를 붙인다. 조건 키는 `key (영어 표현)`으로 나열한다.
- 후처리 더한 것: 정규화하면 빈 이름(기호만)도 버린다. `order`가 같으면 LLM이 준 순서. 출처 번호·조건 키는 중복을 뺀다.
- 성공 저장의 잠금은 추출 비용을 측정 `cost_usd`에 더하는 UPDATE다(06 6장). 측정이 `running`이 아니면(취소·실패) 결과를 버리고, 응답은 `pending`인 것만 바꾼다(같은 작업이 두 번 돌아도 한 번).
- 측정이 `running`이 아니면 LLM도 부르지 않는다. 시간 초과는 60초(`EXTRACT_TIMEOUT_S`), 실패 사유는 로그에만 남긴다.

## 4. 측정 마무리 `finalizeRun(run_id)`

1. 측정 `running → parsing`(조건부). 실패하면 끝. `stage = finalizing`.
2. 실패율 계산 → 30% 초과면 03 E5(진단)·E7(재측정)로 끝.
3. 한 트랜잭션에서(다시 실행돼도 같도록 이 측정의 `metrics`·diagnosis `findings`를 먼저 지운다)
   1. 우리 가게 이름 후보 모으기(4.2) → 그 측정의 `recommendations.is_target` 갱신.
   2. 지표 계산·저장(5장).
   3. 진단이면 고쳐야 할 점 판정·저장(6장).
   4. `failure_rate` 저장, 측정 `parsing → completed`, `stage = done`, `completed_at`.
   5. 03 E4(진단) 또는 E6(재측정).

구현 메모(2026-10-28, 7단계)
- 1번: 작업이 다시 돌면(`RetryStrategy`) 측정이 이미 `parsing`이므로 거기서 이어 간다. `completed`·`failed`면 끝.
- 2번 실패율: 실패 = 전체 실행 − 성공 실행(끝나지 않은 실행도 실패로 셈). 실패면 `failure_rate`를 저장하고 `run_failure.fail_run(…, "failure_rate")`(E5·E7, 무료 차감 없음).
- 4.2 이름 후보는 카카오·네이버를 다시 부르므로 3번 트랜잭션을 열기 **전에** 모은다(`question_service.target_names` 재사용).
- E4: 가게 `measuring → diagnosed`, `is_free`면 `free_usage_ledger`(사장님 이메일 HMAC), 신청이 `approved`면 `base_run_id`·`connecting`, 메일 `diagnosis_result`(`openai_rate`·`gemini_rate` = 공급자별 전체 등장률, 측정하지 못했으면 null). 정비안 생성(E12)은 10·11단계, 고쳐야 할 점(3.3)은 8단계, E6의 `compareFixValues`는 14단계에서 채운다(지금은 로그).

### 4.2 우리 가게 이름 후보 `collect_target_names(store)`

- 사장님 입력 이름, Google 스냅샷 `displayName`(ko·en), 카카오 다시 부르기 `place_name`, 네이버 다시 부르기 `title`.
- 모두 `normalize_name`하고 2자 미만·빈 값은 뺀다. 집합으로 쓴다.
- 카카오·네이버 이름은 이 판정(코드 비교)에만 쓰고 저장하지 않는다.
- 판정: `recommendation.normalized_name ∈ 후보 집합`이면 `is_target = true`(이름만 맞아도 등장, 기획서 15장).

## 5. 지표(`domain/metrics.py`, W-05-3·4)

### 5.1 입력

```python
@dataclass
class RecView:
    normalized_name: str
    name: str
    rank: int
    is_target: bool
    source_domains: list[str]
    mentioned_attributes: list[str]

@dataclass
class ResponseView:
    response_id: int
    provider: str           # openai|gemini
    question_id: int
    extraction_ok: bool
    recs: list[RecView]
    source_domains: list[str]   # 응답 전체 출처(중복 제거)
```

성공 실행이지만 추출 실패한 응답은 `extraction_ok = False`로 넣는다. 실패 실행은 넣지 않는다.

### 5.2 정의

- 성공한 답변 `S(p)` = 공급자 p의 `extraction_ok`인 응답. `S(p, q)` = 그중 질문 q.
- 대상 x(우리 가게 또는 주변 가게 이름)의 등장: 응답의 추천 중 x에 해당하는 것이 있음. 순위는 해당 추천들의 최소 `rank`.
- `success_count = |S|`
- `appearance_count` = S 중 x가 등장한 응답 수
- `appearance_rate = appearance_count / success_count`(`success_count = 0`이면 `None` = 측정하지 못함)
- `avg_rank` = 등장한 응답들의 순위 평균(등장 0이면 `None`)

### 5.3 저장 행(`metrics`)

| subject_type | provider | question_id | metric_name | value | denominator |
|---|---|---|---|---|---|
| `target` | p | NULL(전체), 각 질문 | `success_count` | \|S\| | — |
| `target` | p | NULL, 각 질문 | `appearance_count` | 등장 수 | \|S\| |
| `target` | p | NULL, 각 질문 | `appearance_rate` | 비율 | \|S\| |
| `target` | p | NULL, 각 질문 | `avg_rank` | 평균 | 등장 수 |
| `competitor` | p | NULL | 위 4개 | | | (+ `rank_order`, `display_name`) |
| `source` | p | NULL | `citation_count` | 그 도메인을 인용한 S(p) 응답 수 | \|S(p)\| |
| `source` | p | NULL | `target_citation_count` | 우리 가게 추천에 그 도메인이 붙은 S(p) 응답 수 | 우리 가게 등장 수 |

- `subject_name`: target은 `"target"`, competitor는 정규화 이름, source는 도메인.
- source 행은 공급자별 `citation_count` 상위 20개 도메인과 `target_citation_count > 0`인 도메인만 저장한다.

### 5.4 주변 가게 5곳(F-07)

1. 두 공급자의 모든 `S` 응답에서, `is_target`이 아닌 추천을 `normalized_name`으로 묶는다.
2. 이름마다 등장 응답 수(응답당 1번)와 평균 순위를 구한다.
3. 정렬: 등장 수 내림차순 → 평균 순위 오름차순 → 정규화 이름 오름차순. 앞 5개(5개 미만이면 있는 만큼).
4. `display_name`: 그 이름으로 묶인 원래 이름 중 가장 많이 나온 것(같으면 먼저 나온 것).
5. 각 주변 가게에 대해 공급자별로 5.3의 4개 지표를 저장한다.

### 5.5 주변 가게와 비교한 위치(S13·S16)

- 우리 가게 + 주변 가게 5곳을 "두 공급자 합산 등장 수 내림차순, 같으면 평균 순위(두 공급자 합산 평균) 오름차순"으로 줄 세운다. 우리 가게의 순서가 `position`, 전체 수가 `total`.

### 5.6 화면용 출처

- S11 `sources.top`: 두 공급자의 `citation_count`를 도메인별로 더해 내림차순 5개(같으면 도메인 이름순).
- S11 `sources.targetSources`: `target_citation_count`를 도메인별로 더한 값, 0보다 큰 것 내림차순.
- 지도 인용(S16): `map_kind(domain)`이 `google_maps`·`kakao_map`인 도메인의 합.

구현 메모(2026-10-28, 7단계, `domain/metrics.py`)
- 공급자 두 곳의 우리 가게 행은 응답이 하나도 없어도 만든다(`success_count = 0`, 비율·평균 `None` = 측정하지 못함).
- 출처 도메인 `unknown`(Gemini에서 원래 사이트를 알 수 없음)은 출처 지표에 넣지 않는다. 남기는 도메인마다 `citation_count`·`target_citation_count` 두 행을 저장한다(0이어도).
- 5.5 `competitor_position`: 등장 수·평균 순위까지 완전히 같으면 우리 가게를 앞에 둔다(안정 정렬). 5.6은 `top_sources`·`target_sources`. 손 계산 사례는 `tests/fixtures/metrics/case_{1,2,3}.json`.
- 지도 인용(S16)은 14단계에서 만든다. 주의: `https://www.google.com/maps/...`의 도메인은 `google.com`이라 도메인만으로는 `map_kind`가 지도로 보지 못한다(경로가 필요).

## 6. 고쳐야 할 점(F-08, W-07)

### 6.1 원칙

- 코드 규칙으로 판정한다. LLM은 6.4 D6(AI가 틀리게 말함)의 문장 비교에만 쓴다.
- 판정에 필요한 출처 값이 없으면 그 규칙은 판정하지 않는다(잘못된 판정 방지).
- Google 지도·카카오맵에서 고칠 수 있는 것만 만든다. 인스타그램·외부 사이트 쪽 문제는 만들지 않는다.
- 진단 단계(`stage = diagnosis`)에서 카카오는 기본정보(이름·주소·전화·업종)만 쓴다. 나머지 카카오 판정은 정비안 단계(`stage = plan`, 6.5).
- **카카오·네이버 값은 `findings.evidence`에 저장하지 않는다.** 근거에는 `{"source": "kakao", "valueStored": false}`처럼 출처만 적는다.

### 6.2 입력(`domain/findings_rules.py`)

```python
@dataclass

    naver_basic: Place | None        # 다시 부르기
```

|---|---|---|---|
| D1 | map_missing | Google에서 가게를 못 찾음 / 카카오에서 못 찾음 | (google, `listing`, `map_missing.listing`) / (kakao, `listing`, ...) |
| D2 | map_missing | Google 스냅샷 ok이고 `regularOpeningHours` 없음 | (google, `regular_hours`) |
| | | `websiteUri` 없음 | (google, `website`) |
| | | `nationalPhoneNumber` 없음 | (google, `phone`) |
| | | `priceLevel`·`priceRange` 둘 다 없음 | (google, `menu`) — 가격은 메뉴·가격 칸으로 고친다 |
| | | 업종별 기본 편의 키(restaurant: vegetarian, card_payment, reservation, takeout / cafe: card_payment, takeout, outdoor_seating / bar: card_payment, reservation, alcohol) 중 Google 필드가 **없는** 것이 1개 이상 | (google, `attributes`) 하나. `evidence.missingKeys` |
| D3 | source_mismatch | 아래 6.3.1 | (google 또는 kakao, `name`·`address`·`phone`·`regular_hours`) |
| D4 | condition_missing | 질문 조건 키 k마다: Google 필드가 **없음**이고(`budget`은 `priceLevel` 없음), 주변 가게 중 그 질문의 답변에서 k를 추천 이유로 받은 가게가 1곳 이상 | k가 `budget`이면 (google, `menu`), 그 밖은 (google, `attributes`) — title_key `condition_missing.{k}` |

- 영문 정보 부족(english_missing)은 진단 단계에서 판정하지 않는다. Places API로는 사장님이 쓴 소개·메뉴를 볼 수 없다(추론. Places `editorialSummary`는 Google이 쓴 요약). 정비안 단계에서 판정한다.
- 같은 (provider, field)에 여러 규칙이 걸리면 행을 따로 만든다(분류가 다름). 화면은 칸(`itemId`)으로 묶어 보여 준다.

#### 6.3.1 출처끼리 정보 다름(D3)

- 지도 값: Google은 스냅샷, 카카오는 다시 부른 기본정보. 지도 값이 없으면 판정하지 않는다(그건 D2).
- 다른 출처 값: 공식 웹사이트(`extract`), AI 웹 검색 사이트들, 네이버 기본정보(이름·주소만. 네이버 API는 전화번호를 주지 않는다).
- 비교: 이름 `not same_name`, 주소 `normalize_address`가 둘 다 있고 다름, 전화 `normalize_phone`이 둘 다 있고 다름, 영업시간 `hours_diff`가 비어 있지 않음(웹사이트 `hours`와 Google만).
- **다름으로 보는 조건**(오탐을 줄이기 위해): ① 공식 웹사이트 값이 지도 값과 다름, 또는 ② 서로 같은 값을 가진 다른 출처가 2곳 이상이고 그 값이 지도 값과 다름. 웹 검색 사이트 1곳이나 네이버 혼자 다르면 만들지 않는다.
- `title_key`: `source_mismatch.{field}`. `evidence`: `{"mapValue": (google만), "sources": [{"source": "website"|"web:<domain>"|"naver", "value": (website·web만), "valueStored": bool}]}`.
- 이름·주소 다름은 seelo가 고치지 않는다. 정비안 칸을 만들지 않고 S13 `ownerOnlyFields`로 안내한다(09 6.4).

### 6.4 AI가 틀리게 말함(D5)

1. 우리 가게가 등장한 응답의 `target_claims`를 모은다.
2. 필드별 정답(truth): 공식 웹사이트 값(`hours`·`phone`·메뉴 가격·`address`). 웹사이트 값이 없으면 판정하지 않는다(정답이 지도 값이면 원인이 지도라고 할 수 없음).
3. 지도 값: Google 스냅샷 값(정비안 단계에서는 카카오 읽은 값도).
4. 비교(LLM, `OPENAI_CHEAP_MODEL`, `structured`): `{field, claim, truth, mapValue}` → `{claimMatchesTruth: bool, claimMatchesMap: bool|None}`. 지시문: "Decide whether the claim states the same fact as the reference. Ignore formatting differences."
5. `claimMatchesTruth = false`이고(`claimMatchesMap = true` 또는 지도 값 없음)이면 finding. 필드 매핑: hours → `regular_hours`, phone → `phone`, price → `menu`, location → `address`.
6. 같은 (지도, 칸)은 하나로 묶고 `evidence.responseIds`, `evidence.providers`(어느 AI가 틀렸는지)를 모은다.
7. 이 LLM 입력에는 네이버·카카오 값을 넣지 않는다(카카오 지도 값 비교가 필요한 정비안 단계에서는 코드 비교만 하고, 코드로 판단하기 어려운 영업시간 문장은 판정하지 않는다).

### 6.5 정비안 단계 추가 규칙(`stage = plan`, 09 6장에서 호출)

연결 뒤 읽은 지금 값(`plan_values`)으로 그 지도에 대해서만 판정을 더한다. 지금 값을 읽지 않은 경우(`AUTO_FIX_ENABLED=false` 등, `plan_values`가 None이거나 모든 값이 None)에는 이 단계 판정을 건너뛴다.

| ID | 지도 | 조건 | finding |
|---|---|---|---|
| P1 | google | `description` 칸이 비어 있음 | (google, `description`, `map_missing.description`) |
| P2 | google | `menu` 칸이 비어 있음(메뉴를 지원하는 가게만) | (google, `menu`, `map_missing.menu`) |
| P3 | google | `description`에 라틴 문자 단어가 5개 미만 | (google, `description`, `english_missing.description`) |
| P4 | google | 메뉴 항목 중 영문 이름이 있는 것이 절반 미만 | (google, `menu`, `english_missing.menu`) |
| P5 | kakao | `intro`·`hours`·`price_items`·`links`·`services`·`tags` 중 빈 칸 | (kakao, 그 칸, `map_missing.{칸}`) |
| P6 | kakao | 카카오 `hours`와 웹사이트 `hours`가 `hours_diff`로 다름 | (kakao, `hours`, `source_mismatch.regular_hours`) |
| P7 | kakao | 질문 조건 키 k가 카카오 `services`·`tags`에 없고(키워드 표 0.1), 주변 가게가 k로 추천됨 | (kakao, `services`, `condition_missing.{k}`) |
| P8 | google | D4와 같은 조건을 지금 값(편의 정보)으로 다시 판정 | (google, `attributes`) |

- 진단 단계 finding 중 같은 (provider, field, category)가 이미 있으면 plan 단계에 다시 만들지 않는다.
- plan 단계 finding은 `fix_plan_id`를 채우고 `run_id`는 정비안의 `base_run_id`.
- 카카오 지금 값은 이 판정에만 쓰고 `evidence`에 넣지 않는다(`valueStored: false`). 그 값은 `fix_plan_items.current_value`로만 저장된다.
- 구현 메모(2026-10-28, 11단계): `findings_rules.judge_plan(inp, provider, existing) -> list[FindingDraft]`. `inp.plan_values`가 그 지도의 지금 값(모두 None이면 None → 빈 목록). P8은 지금 값 `attributes`를 Google 필드 이름으로 바꿔(`_attrs_as_google`) D4 판정을 다시 쓴다. 영향 순서는 6.6 `prioritize`로 매기고 진단 단계 `priority` 최댓값을 더해 진단 단계 뒤에 놓는다. 수동 모드에서는 이 단계가 비어 카카오 정비안 칸이 없다(`[기획 확인]` `03_실험/구현시험/단계11_정비안_20261028.md`).

### 6.6 영향 순서(W-07-2)

- 주변 가게 사실 조회 `lookup_competitor_facts(competitors, store_coords)`(진단 단계, Google만, 실패해도 계속): 주변 가게마다 Text Search(이름 + 지역, 가게 좌표 기준 `locationBias` 반경 2km, 1건) → Place Details(필드 `regularOpeningHours,websiteUri,nationalPhoneNumber,priceLevel,servesVegetarianFood,paymentOptions,reservable,takeout,outdoorSeating,servesBeer,servesWine,servesCocktails,goodForChildren,goodForGroups`). 각 5초, 동시에. 결과는 저장하지 않는다. 비용은 측정 `cost_usd`에 넣지 않고 로그로 남긴다.
- `competitor_count`
  - map_missing·condition_missing: 주변 가게 중 그 정보를 **갖춘** 수(필드가 있음·참). `listing`은 5(모두 지도에 있음).
  - condition_missing: 그 조건으로 추천된 주변 가게 수와 위 값 중 큰 값.
  - source_mismatch·ai_wrong: 0.
  - 조회 실패(`competitor_facts is None`)면 `evidence.insufficient = true`.
- `question_count`
  - listing·regular_hours·phone·website·source_mismatch: 3(모든 질문에 관련).
  - menu: 조건 `budget`인 질문 수 + 1.
  - attributes·condition_missing: 그 조건 키를 가진 질문 수 + 그 키로 주변 가게가 추천된 질문 수(중복 없이).
  - ai_wrong: 근거 응답의 서로 다른 질문 수.
- 정렬: `insufficient`가 거짓인 것 먼저 → `competitor_count` 내림차순 → `question_count` 내림차순 → 분류 순서(map_missing, condition_missing, ai_wrong, source_mismatch, english_missing) → field 이름순. `priority`는 1부터.

- `{지도}`: google → "Google 지도", kakao → "카카오맵". `{출처}`: website → "공식 웹사이트", naver → "네이버 지도", web → "외부 사이트". 여러 출처면 첫 번째. `{AI}`: 한쪽이면 "ChatGPT"·"Gemini", 둘 다면 "AI".
- 분류 라벨: map_missing "지도에 정보 없음", source_mismatch "출처끼리 정보 다름", english_missing "영문 정보 부족", condition_missing "질문 조건 정보 부족", ai_wrong "AI가 틀리게 말함".
- 제목은 API 응답 때 만든다(DB에는 `title_key`와 `evidence`만).

### 6.8 구현 메모(2026-10-28, 8단계)

- 코드: 규칙 `domain/findings_rules.py`(순수), 주변 가게 조회·AI 비교 `services/findings_service.py`, 저장은 `finalize_service`.
- **판정은 finalizeRun의 저장 트랜잭션 전에 한다**(주변 가게 Places 조회·AI 비교 LLM이 외부 호출). 측정이 parsing이면 다른 작업이 결과를 더 쓰지 않으므로 그 사이 바뀌지 않는다. 카카오·네이버 다시 부르기는 4.2 이름 후보와 공용으로 한 번만(`refetch.refetch_basics`).
- 입력 더한 것: `category`(D2 기본 키), `question_ids`, `claims`(`TargetClaim`: 응답·공급자·질문·칸·문장), `name_threshold`. 질문 조건 키는 `question_sets.features`를 conditional 질문에만 붙인다. 웹 근거는 그 측정의 `web_evidence`.
- D3: 웹 근거는 **같은 도메인을 한 출처**로 센다(두 공급자가 같은 사이트를 찾아도 1곳). 묶는 값: 이름은 `normalize_name`, 주소는 `normalize_address`, 전화는 `normalize_phone`. `evidence.sources`에는 지도 값과 다른 출처를 모두 적는다. 영업시간 다름은 `evidence.days`(다른 요일)도 넣는다.
- D4: Google에 칸이 없는 키(`halal`, `english_menu`)는 고칠 수 없어 만들지 않는다. `evidence = {conditionKey, questionIds, competitors(추천된 주변 가게 이름)}`.
- D5: 같은 (칸, 주장 문장)은 한 번만 비교하고, 비교 LLM은 한 번에 묶어 부른다(`ClaimChecksOut`, 번호로 대응). 답에 빠진 번호는 "맞음"으로 본다. LLM이 실패하면 D5만 건너뛴다. 비용은 측정 `cost_usd`에. `evidence = {responseIds, providers, questionIds, claims(최대 3), truth}`.
- 6.6: `listing`의 주변 가게 수는 실제 주변 가게 수(보통 5). 사실 조회는 Text Search 쿼리 `"{화면 이름} {한글 지역}"`, 가게 좌표는 Google 스냅샷(없으면 카카오). 근거 부족(`insufficient`)은 사실에 기대는 map_missing(listing 제외)·condition_missing에만 붙인다. 조회는 하나라도 성공하면 결과를 쓰고(못 찾은 가게는 정보 없음), 모두 실패하거나 좌표가 없으면 None. `COMPETITOR_FACTS_ENABLED=false`도 None.
- 정비안 단계 규칙(6.5, english_missing 포함)은 11단계에서 `judge_plan`으로 더한다.
