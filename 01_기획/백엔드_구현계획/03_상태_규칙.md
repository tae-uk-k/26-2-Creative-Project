# 03. 상태 전이와 판정 규칙

- 상태 값은 `domain/states.py`에 `StrEnum`으로 정의한다. 값 문자열은 02 DDL의 CHECK와 같다.
- 상태는 **반드시 `transition()`으로만** 바꾼다(2장). 허용되지 않은 전이는 코드 오류(`ValueError`)이고, 동시성 때문에 현재 상태가 달라 바꾸지 못한 경우는 `False`를 돌려준다.
- 명세서 7장 대비 구체화
  - 가게 `collected` → (정비 신청 승인) → `collecting`으로 간다(명세서는 `measuring`). 승인까지 시간이 지나 수집 값이 만료될 수 있어 다시 모은다.
  - 정비 신청 `remeasure_scheduled` → `fixing`을 허용한다. 재측정 전에 다른 지도의 정비안이 승인되면 정비 중으로 돌아가고, 끝나면 그 완료일 + 14일로 다시 예약한다(D-16 권장안).
  - 정비안은 `verifyConnection` 성공 때 `generating`으로 먼저 만들고, 그 정비안 ID로 `readCurrentValues` → `generateFixPlan`을 실행한다(명세서의 `readCurrentValues(connectionId)`·`generateFixPlan(fixRequestId, provider)`와 같은 일을 정비안 ID 하나로 묶음). 그래서 S07 "정비안 준비 중"이 연결 직후부터 보인다.

## 1. 상태와 허용 전이

### 1.1 가게 `stores.status`

| 현재 | 다음 | 언제(사건 번호는 3장) |
|---|---|---|
| (생성) | `collecting` | E1 가게 확정 |
| `collecting` | `measuring` | E2 수집 완료(측정이 있음) |
| `collecting` | `collected` | E2 수집 완료(무료 진단 사용 후 바꾼 가게, 측정 없음) |
| `collecting` | `measure_failed` | E3 지역·업종을 얻지 못함, E33 멈춤 |
| `measuring` | `diagnosed` | E4 측정 완료 |
| `measuring` | `measure_failed` | E5 측정 실패, E33 멈춤 |
| `measure_failed` | `collecting` | E25 다시 시도 |
| `collected` | `collecting` | E9 정비 신청 승인(기준 측정 시작) |
| `collecting`·`collected`·`measuring`·`diagnosed`·`measure_failed` | `archived` | E27 가게 변경 |

- 재측정(remeasure)은 가게 상태를 바꾸지 않는다(`diagnosed` 유지). 화면은 정비 신청 상태로 판단한다.
- E28 [내 가게가 아니에요]는 가게 행을 지운다(상태 전이 없음).

### 1.2 측정 `measurement_runs.status`

| 현재 | 다음 | 언제 |
|---|---|---|
| (생성) | `queued` | 측정을 만들 때 |
| `queued` | `running` | `collectStore` 시작 |
| `running` | `parsing` | `finalizeRun` 시작 |
| `parsing` | `completed` | 실패율 30% 이하 |
| `parsing` | `failed` | 실패율 30% 초과(`failure_reason = failure_rate`) |
| `queued`·`running` | `failed` | 지역·업종 없음(`collect_insufficient`), 작업 등록 실패(`enqueue_failed`), 멈춤(`stuck`) |
| `queued`·`running`·`parsing` | `canceled` | 가게 변경, [내 가게가 아니에요], 탈퇴 |

`stage`(S10 단계 표시)는 상태와 따로 바꾼다: `collecting` → `generating_questions`(진단만) → `calling_ai` → `finalizing` → `done`. 재측정은 `generating_questions`를 건너뛴다.

| 현재 | 다음 | 언제 |
|---|---|---|

## 2. 전이 함수(`domain/states.py` + `services/` 공용)

```python
ALLOWED: dict[str, dict[str, set[str]]] = {
    "stores": {
        "collecting": {"measuring", "collected", "measure_failed", "archived"},
        "measuring": {"diagnosed", "measure_failed", "archived"},
        "measure_failed": {"collecting", "archived"},
        "collected": {"collecting", "archived"},
        "diagnosed": {"archived"},
    },
    "measurement_runs": {
        "queued": {"running", "failed", "canceled"},
        "running": {"parsing", "failed", "canceled"},
        "parsing": {"completed", "failed", "canceled"},
    },
    "fix_requests": {
        "requested": {"approved", "rejected"},
        "approved": {"connecting"},
        "connecting": {"fixing"},
        "fixing": {"remeasure_scheduled"},
        "remeasure_scheduled": {"fixing", "remeasuring"},
        "remeasuring": {"report_ready", "remeasure_failed"},
        "remeasure_failed": {"remeasuring"},
    },
    "map_connections": {
        "not_connected": {"invited", "connected", "needs_attention"},
        "invited": {"connected", "needs_attention"},
        "needs_attention": {"invited", "connected", "needs_attention"},
        "connected": {"revoked"},
        "revoked": {"invited"},
    },
    "fix_plans": {
        "generating": {"awaiting_approval", "generation_failed"},
        "generation_failed": {"generating"},
        "awaiting_approval": {"approved"},
    },
    "fix_logs": {
        "queued": {"applied", "pending_reflection", "manual_required", "disconnected"},
        "pending_reflection": {"applied", "manual_required", "disconnected"},
        "manual_required": {"manual_done", "disconnected"},
    },
    "remeasure_schedules": {"scheduled": {"started", "canceled"}},
    "comparison_reports": {"generating": {"completed", "generation_failed"}},
    "email_logs": {"queued": {"sent", "failed"}},
}

async def transition(session, model, row_id: int, *, from_: set[str], to: str, values: dict | None = None) -> bool:
    table = model.__tablename__
    for f in from_:
        if to not in ALLOWED[table].get(f, set()):
            raise ValueError(f"illegal transition {table}: {f} -> {to}")
    stmt = (
        update(model)
        .where(model.id == row_id, model.status.in_(from_))
        .values(status=to, **(values or {}))
        .returning(model.id)
    )
    return (await session.execute(stmt)).scalar_one_or_none() is not None
```

- API에서 `False`면 409 `INVALID_STATE`(이미 처리됨)로 응답한다.
- 작업에서 `False`면 경고 로그를 남기고 조용히 끝낸다(중복 실행·취소된 대상).
- 여러 행을 한꺼번에 바꿀 때(예: 권한 회수로 칸 여러 개 `disconnected`)는 같은 조건부 UPDATE를 `WHERE fix_request_id = :id AND provider = :p AND status IN (...)`로 쓴다.

## 3. 사건별 처리(무엇이 바뀌고 무엇을 등록하는가)

"작업 등록"은 항상 **그 변경과 같은 트랜잭션 안에서** `jobs.defer(session, ...)`(06 3장)로 한다. 커밋되면 변경과 작업이 함께 남고, 롤백되면 둘 다 없다. 표의 "메일"은 `email_service.queue(session, ...)`(10 4장)이며 같은 트랜잭션 안에서 `email_logs` 행을 만들고 `sendEmail`을 등록한다.

## 4. S07 홈 카드 판정(`domain/home_card.py`)

입력: 보관 중이 아닌 가게, 그 가게의 가장 최근 신청, 그 신청의 지도별 최신 버전 정비안, 연결 2행, 수동 처리 칸 존재 여부. 위에서부터 **처음 맞는 카드 하나**를 고른다(명세서 7장 표와 같은 순서).

```python
def pick_card(store, req, plans, connections, has_manual) -> str:
    if store is None:
        return "no_store"
    if req and req.status == "requested":
        return "fix_requested"
    if req and req.status == "rejected":
        return "fix_rejected"
    pre = req is None or req.status == "approved"
    if pre and store.status in ("collecting", "measuring"):
        return "measuring"
    if pre and store.status == "measure_failed":
        return "measure_failed"
    if req is None and store.status == "diagnosed":
        return "diagnosed"
    if req is None and store.status == "collected":
        return "free_used_store_changed"
    statuses = {p.status for p in plans}
    if req.status in ("connecting", "fixing") and "awaiting_approval" in statuses:
        return "plan_needs_approval"
    if req.status == "connecting" and statuses & {"generating", "generation_failed"}:
        return "plan_preparing"
    if req.status == "connecting" and not plans:
        return "connect_needed"
    return {
        "fixing": "fixing",
        "remeasure_scheduled": "remeasure_waiting",
        "remeasuring": "remeasuring",
        "remeasure_failed": "remeasure_failed",
        "report_ready": "report_ready",
    }.get(req.status, "unknown")
```

- `unknown`은 나오면 안 된다. 나오면 오류 로그를 남기고 버튼 없는 카드로 응답한다. 테스트에서 15가지 상태를 만들어 `unknown`이 나오지 않는지 확인한다.
- 카드와 함께 돌려줄 공통 표시
  - `revokedProviders`: 그 신청의 연결 중 revoked인 지도 목록 → "연결이 끊겼어요" + [다시 연결하기]
  - `manualInProgress`: 그 신청에 manual_required 칸이 있으면 true(정비 중 카드 문구)
  - `storeChangeBlocked`: 진행 중인 신청이 있으면 true("정비가 끝나기 전에는 가게를 바꿀 수 없어요")
  - `retriesLeftToday`: 3 − 오늘(KST) 이 가게의 trigger retry 측정 수(최소 0)
- 카드별 데이터는 04의 `GET /api/home` 응답 표를 따른다.
- 구현 메모(2026-10-28): 위 의사 코드는 `req`가 없는데 가게가 diagnosed·collected·measuring·measure_failed·collecting이 아니면(예: archived) 정비안 판정에서 `req.status`를 읽어 오류가 난다. 코드는 그 경우 `unknown`을 돌려준다(`domain/home_card.py`). `approved` 신청 + diagnosed 가게도 `unknown`(E9가 base_run이 있으면 바로 connecting으로 바꾸므로 생기지 않음).

## 5. A01 상태 판정(`domain/admin_filter.py`)

필터마다 조건이 다르고, 한 신청이 여러 필터에 걸릴 수 있다(예: 정비 중이면서 수동 처리 필요).

| 필터 키 | 화면 이름 | 조건 |
|---|---|---|
| `requested` | 대기 | 신청 requested |
| `approved` | 승인 | 신청 approved |
| `connect_waiting` | 연결 대기 | 신청 connecting이고 정비안 없음 |
| `plan_waiting` | 정비안 확인 대기 | awaiting_approval 정비안 있음 |
| `fixing` | 정비 중 | 신청 fixing |
| `manual_required` | 수동 처리 필요 | manual_required 칸 있음 |
| `remeasure_waiting` | 재측정 대기 | 신청 remeasure_scheduled·remeasuring |
| `report_ready` | 보고서 완료 | 신청 report_ready |
| `rejected` | 거절 | 신청 rejected |
| `failed` | 실패 | 최신 정비안·보고서 중 generation_failed가 있거나 신청 remeasure_failed |

목록의 행마다 보여 줄 대표 상태는 위 표에서 다음 순서로 처음 맞는 것이다: `failed` → `manual_required` → `requested` → `rejected` → `approved` → `connect_waiting` → `plan_waiting` → `fixing` → `remeasure_waiting` → `report_ready`.

- 구현 메모(2026-10-28, `domain/admin_filter.py`): "정비안"은 지도별 최신 버전, "보고서"는 최신 버전으로 본다. 어느 필터에도 걸리지 않으면(예: connecting인데 정비안이 생성 중) 신청 상태로 대표 상태를 정한다(connecting → `connect_waiting`, remeasuring → `remeasure_waiting`, remeasure_failed → `failed`). 그래서 정비안 생성 중인 신청은 관리자 목록에 "연결 대기"로 보인다(사장님 홈은 `plan_preparing`). 목록은 베타 규모라 메모리에서 거르고 나눈다.
