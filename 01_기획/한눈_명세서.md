# 한눈 서비스 명세서

- 문서 역할: 기획서의 기능을 어떤 기술로 어떻게 구현하고 검증할지 정의하는 기술 기준 문서
- 기능 기준: [한눈 기획서](./한눈_기획서.md) — 범위(8장), 화면(9장), 기능(10장, F-01~F-10), 작업 분해(11장, W-01~W-11)
- 대상 버전: 13주차 베타
- 우선순위 표기: 기획서 8장과 같다(`P0` 13주차까지 필수, `P1` 일정이 허용되면, `P2` 후속 개발).
- 이 문서는 기능 규칙을 다시 적지 않는다. 기능 규칙이 바뀌면 기획서를 먼저 고치고, 이 문서의 구현 방법을 맞춘다.

## 1. 시스템 구성

### 1.1 기술 스택

| 영역 | 기술 | 용도 |
|---|---|---|
| 웹 | Flask + Jinja2 + HTML/CSS/JavaScript | 서버 렌더링 화면, 폼 처리 |
| 인증 | Flask-Login(세션), Authlib(구글·카카오 OAuth), Argon2id 비밀번호 해시, Flask-WTF(CSRF) | 가입·로그인·세션·접근 제어 |
| 데이터 | SQLAlchemy + Alembic + PostgreSQL | 관계형 데이터, 이력, 마이그레이션. 원본 응답은 JSONB |
| 비동기 작업 | Redis + RQ | 정보 수집, 반복 AI 호출, 보고서 생성, 이메일 발송 |
| AI | OpenAI API(웹 검색 도구), Gemini API(Google 검색 그라운딩) | 측정, 추천 추출, 질문 생성, 정보 수집용 웹 검색, 보고서 생성 |
| 외부 데이터 | Google Places API(New), 카카오 로컬 API, NAVER API HUB 지역 검색, 인스타그램 Graph API(PoC 후) | 가게 식별, 기본정보·상세정보 수집 |
| 이메일 | 트랜잭션 이메일 서비스(SMTP) | 인증, 비밀번호 재설정, 진단·보고서 알림 |
| 배포 | Docker(웹·워커·PostgreSQL·Redis) | 개발·운영 환경 일치 |
| 관측 | 구조화 로그, 오류 추적, 작업별 비용 기록 | 실패 원인, 응답 시간, API 비용 확인 |

- P0에서는 파일 저장소를 쓰지 않는다. 사진은 저장하지 않고(기획서 F-04), P1 보고서 PDF를 만들 때 필요하면 오브젝트 스토리지를 추가한다.

### 1.2 처리 흐름

```text
브라우저
  → Flask 웹 서버 ── PostgreSQL
      → Redis 작업 큐
          → Worker
              → Google Places API / 카카오 로컬 API / NAVER API HUB
              → 가게 공식 웹사이트(robots.txt 허용 시)
              → OpenAI API / Gemini API
              → 인스타그램 Graph API(PoC 통과 시)
              → 이메일 서비스
```

### 1.3 프로세스와 큐

| 프로세스 | 하는 일 |
|---|---|
| web | 화면 렌더링, 폼 검증, 작업 등록, 진행률 조회. 가게 식별(F-03)을 빼고는 외부 API를 직접 호출하지 않는다. |
| worker `collect` | 가게 식별 이후 정보 수집 |
| worker `measure` | 질문 생성, AI 반복 호출, 추천 추출, 지표 계산, 고쳐야 할 점 판정 |
| worker `report` | 유료 보고서 생성 |
| worker `email` | 이메일 발송 |
| scheduler | 미인증 계정 정리, 만료 스냅샷 삭제 |

- 가게 식별(F-03)은 S08에서 결과를 바로 보여 줘야 하므로 웹 요청 안에서 처리하되, 외부 호출마다 5초 제한을 두고 전체 10초를 넘기면 "잠시 후 다시 시도" 오류를 낸다.

## 2. 권한과 보안 모델

| 역할 | 접근 범위 |
|---|---|
| 비회원 | S01, S02~S06 |
| 사장님(`owner`) | 본인 계정·가게·측정·보고서(S07~S14) |
| 관리자(`admin`) | A01(`/admin/...`), 신청 상태 변경, 보고서 재생성 |

- 가게·측정·보고서를 읽거나 바꾸는 모든 요청은 서버에서 소유자(`stores.ownerId = 현재 사용자`) 또는 관리자 여부를 확인한다. URL의 ID만 바꿔서 남의 데이터를 볼 수 없어야 한다.
- 유료 보고서 내용은 `entitlements`가 있을 때만 응답한다. 권한이 없으면 화면뿐 아니라 응답 데이터에도 보고서 내용을 넣지 않는다.
- 무료 진단 화면(S11)에는 고쳐야 할 점의 개수만 응답한다. 판정 내용(`findings`)은 응답에 넣지 않는다.

## 3. 기능별 구현

### F-01 계정

| 구현 요소 | 내용 |
|---|---|
| 라우트 | `/signup`, `/login`, `/logout`, `/verify-email/<token>`, `/signup/kakao-email`, `/password/forgot`, `/password/reset/<token>`, `/oauth/<provider>/start`, `/oauth/<provider>/callback`, `/account`, `/account/delete` |
| 이메일 정규화 | 앞뒤 공백 제거, 소문자 변환 후 저장·비교 |
| 중복 검사 | 인증을 마친 계정(`emailVerifiedAt` 있음)과 이메일이 같으면 가입 차단하고 `authIdentities.provider`로 기존 가입 방식을 안내. 같은 이메일의 미인증 계정만 있으면 그 계정을 지우고 새로 만든다 |
| 비밀번호 | Argon2id 해시만 저장. 소셜 가입 계정은 `passwordHash` 없음 |
| 인증·재설정 토큰 | 32바이트 난수. DB에는 해시만 저장, `expiresAt`(인증 24시간, 재설정 1시간), `usedAt`으로 1회용 처리 |
| 구글 | OpenID Connect. `email_verified=true`인 이메일만 사용 |
| 카카오 | 이메일 동의 항목 요청. 이메일을 받지 못하면 임시 상태로 S04에서 이메일 입력·인증 후 가입 완료 |
| 로그인 잠금 | `failedLoginCount` 5회 연속이면 `lockedUntil = 지금 + 10분`, 성공 시 0으로 초기화 |
| 세션 | 쿠키 `Secure`, `HttpOnly`, `SameSite=Lax`, 유지 14일 |
| 탈퇴 | 한 트랜잭션에서 계정·가게·측정·보고서 삭제. 무료 진단을 쓴 계정이면 `freeUsageLedger`에 `HMAC-SHA256(서버 비밀키, 이메일)`만 남김 |
| 무료 사용 확인 | 가입·측정 시작 때 이메일 HMAC 값이 `freeUsageLedger`에 있으면 무료 사용 완료로 본다 |

### F-02 가게 등록·변경

- 계정당 보관 중이 아닌 가게는 1곳(`stores`에 `archivedAt IS NULL` 조건의 `ownerId` 부분 고유 인덱스).
- 변경: 기존 가게에 `archivedAt`을 기록하고, 진행 중인 측정 작업은 RQ 작업 취소 후 `measurementRuns.status = canceled`.
- 보고서 신청이 `requested`·`approved`·`generating`이면 변경 요청을 409로 거부한다.
- 무료 진단을 이미 쓴 계정은 새 가게의 `collectStore`까지만 실행하고 가게를 `collected`로 둔다. 측정은 보고서가 승인된 뒤 시작한다.
- 업종 판정: Google `primaryType`·`types`, 카카오 `category_group_code`·`category_name`, 네이버 `category`를 음식점·카페·바 목록과 비교한다. 목록(예: Google `restaurant` 계열·`cafe`·`coffee_shop`·`bar`, 카카오 `FD6`·`CE7`)은 8주차 PoC에서 확정한다.
- 무료 차감: `measurementRuns.isFree = true`인 측정이 `completed`가 되는 순간 `freeUsageLedger`에 기록한다. `failed`·`canceled`는 차감하지 않는다.

### F-03 링크 판별과 가게 식별

- 입력 문자열에서 URL을 정규식으로 뽑는다. 공유 문구를 통째로 붙여넣어도 첫 번째 지원 URL만 쓴다.
- 짧은 링크(`maps.app.goo.gl`, `kko.to`, `naver.me`)는 리다이렉트를 자동으로 따라가지 않고 `Location` 헤더만 읽는다. 최대 3번, 한 번에 5초.
- 지도별 식별

| 지도 | 링크에서 얻는 값 | 확인 방법 |
|---|---|---|
| Google | 장소 이름, 좌표(`@위도,경도`) | Places Text Search(가게 이름, 좌표 주변 200m)로 장소 ID 확정 |
| 카카오 | 장소 번호 | 키워드 검색(사장님이 입력한 가게 이름) 결과 중 `id`가 장소 번호와 같은 것. 없으면 이름이 비슷한 결과를 S09 후보로, 그것도 없으면 다른 링크 요청 |
| 네이버 | 장소 번호(API 응답에 장소 번호가 없어 직접 대조 불가) | 지역 검색(가게 이름) 결과 중 정규화한 이름이 같은 결과가 1개면 확정, 여러 개면 S09, 없으면 다른 링크 요청 |

- 다른 지도에서 같은 가게 찾기: 가게 이름으로 검색해 좌표 거리 100m 이내이고 이름 유사도가 기준 이상인 결과를 같은 가게로 본다. 유사도 계산은 F-07 이름 정규화 후 비교하며, 기준값은 8주차 PoC 정확도 측정으로 정한다.
- 결과는 `storeSources`에 지도별 `externalId`, `url`, `matchStatus(found·not_found·candidate)`로 저장한다.

### F-04 정보 수집

- 작업: `collectStore(storeId)`, 전체 30초 목표. 출처마다 따로 실행하고 하나가 실패해도 나머지 결과는 저장한다.
- 출처별 처리

| 출처 | 호출 | 저장 |
|---|---|---|
| Google Places | Place Details(필요한 필드만 field mask로 요청) | 장소 ID는 계속 저장. 나머지는 `sourceSnapshots`(보관 기한은 기획서 15장 미정 3) |
| 카카오 로컬 | 키워드 검색 | 장소 ID·장소 링크만 저장. 화면 표시·비교 때마다 다시 호출 |
| 네이버 지역 검색 | NAVER API HUB 지역 검색 | 결과는 가게 식별, 홈페이지 주소 확인, 기본정보(이름·주소·전화·업종) 비교에만 쓴다. 비교는 코드로 하고 응답 내용은 AI 입력에 넣지 않음(약관 확인 전) |
| 공식 웹사이트 | `robots.txt` 확인(사용자 에이전트 `HanoonBot`) 후 첫 페이지와 메뉴로 보이는 링크 1개, 페이지당 1MB·10초 제한 | 본문 텍스트에서 메뉴·가격·영업시간·소개·영문 페이지 여부를 LLM으로 추출해 저장 |
| AI 웹 검색 | OpenAI·Gemini 각 1회, 웹 검색을 켜고 "가게 이름·주소에 대한 정보"를 구조화 출력(JSON)으로 요청 | `webEvidence`에 사이트 주소·이름·사이트별 가게 정보 저장 |
| 인스타그램 | 기본: AI 웹 검색 결과 중 `instagram.com` 주소 사용. 추가: Business Discovery(기능 플래그, PoC 통과 시 켬) | 계정 주소, 소개글, 최근 게시물 글·게시일 |

- 로그인 세션으로 사이트를 여는 수집 도구, 지도 페이지 크롤링, 차단 우회는 쓰지 않는다.
- (P1) 메뉴판 OCR: Google 사진을 불러와 비전 모델로 메뉴판인지 판별하고 글자만 추출한다. 사진 파일은 저장하지 않는다. Google 약관 확인(기획서 13장 PoC) 전에는 켜지 않는다.

### F-05 질문 생성

- 저가 LLM 1회 호출, JSON 구조화 출력(`lang`, `intentType`, `text` 3개).
- 코드 검증: 가게 이름(한글·영문, 정규화 후 부분 일치) 미포함, 지역 이름·업종 포함, 3개 문장 서로 다름. 실패하면 3번까지 다시 생성하고, 그래도 실패하면 업종별 고정 템플릿 사용.
- `questionSets.version`과 함께 저장하고, 측정 작업은 질문 세트 ID를 참조한다.

### F-06 AI 측정

- 작업: `runMeasurement(runId)`가 60개의 `callAi` 작업을 만든다(질문 3 × AI 2 × 10회).
- 동시 실행: 공급자별 동시 호출 수 제한(기본 5, 환경변수로 조정).
- 호출: 질문 문장만 보내고 시스템 지시는 붙이지 않는다. OpenAI는 웹 검색 도구, Gemini는 Google 검색 그라운딩을 켠다.
- 제한 시간 60초, 실패 시 2번까지 지수 백오프로 다시 시도. `aiExecutions`의 (`runId`, `questionId`, `provider`, `repeatNo`) 고유 키로 중복 호출과 중복 비용을 막는다.
- 저장: `aiExecutions`(모델 ID, 회차, 상태, 지연 시간, 오류 코드, 시도 횟수), `aiResponses`(답변 원문, 원본 JSON, 출처 URL).
- 모든 호출이 끝나면 실패율을 계산해 30%를 넘으면 `failed`, 아니면 다음 단계(F-07)로 넘어간다.
- 다시 시도는 가게당 하루 3회까지다. 그날(한국 시간 기준) 해당 가게의 다시 시도로 만든 `measurementRuns` 수로 판단하고, 넘으면 429로 거부한다.
- 수집에서 지역·업종을 얻지 못하면 측정을 만들지 않고 가게를 `measure_failed`로 둔다(무료 차감 없음).
- 진행률: `measurementRuns.progressDone/progressTotal`을 갱신하고, S10은 `GET /api/runs/<id>/progress`를 3초마다 조회한다.

### F-07 추천 추출과 지표

- 답변마다 저가 LLM으로 추천 목록을 뽑는다. 출력 JSON: `recommendations[{name, rank, sourceUrls}]`. 추출에 실패한 답변은 원문을 남기고 지표 계산에서 뺀 뒤 건수를 기록한다.
- 이름 정규화: 소문자 변환, 공백·기호 제거, 지점 표기("본점", "○○점", "branch" 등) 제거. 대상 가게 이름 후보는 세 지도의 한글·영문 이름이다.
- 대상 가게 판정: 정규화한 이름이 후보 중 하나와 같으면 등장(`recommendations.isTarget = true`).
- 지표는 `metrics`에 공급자·질문·대상(우리 가게·주변 가게)별로 값과 분모를 함께 저장한다. 계산식은 기획서 F-07을 따른다.
- 주변 가게 상위 5곳은 정규화 이름으로 묶어 집계한다.

### F-08 고쳐야 할 점 판정

- 네이버·카카오 기본정보 비교는 정규화(공백·기호·지점명 제거, 전화번호 숫자만) 후 코드로 한다. 카카오 값은 저장하지 않고 판정 때 다시 불러온다.
- 코드 규칙 엔진으로 판정한다(LLM 사용은 "질문 조건 정보 부족", "AI가 틀리게 말함"의 문장 비교에 한정).
- 결과는 `findings`에 분류, 제목 키, 영향 점수, 쉬움 점수, 우선순위, 근거(관련 응답 ID·수집값·주변 가게)를 저장한다.
- S11에는 `count(findings)`만 응답한다.

### F-09 유료 보고서 생성

- 작업: `generateReport(reportRequestId)`. 측정 결과가 없으면 `runMeasurement`를 먼저 실행하고 끝나면 이어서 생성한다.
- LLM 호출은 섹션별(고쳐야 할 점 설명, 영문 문안, 채널별 수정안)로 나누고 JSON 구조화 출력을 쓴다.
- 사실 검사: 출력에 들어간 영업시간·가격·전화·주소가 입력 사실 목록에 없으면 `[ ]`로 바꾸고 "확인 필요" 표시를 붙인다.
- 실패 시 1번 자동 재시도, 그래도 실패하면 `reportRequests.status = generation_failed`.
- 결과는 `reports`(기준 측정 ID, 버전, 생성일, 내용 JSONB)에 저장한다.
- 같은 가게에 `completed` 신청이 있거나 진행 중인 신청이 있으면 새 신청을 409로 거부한다. `rejected`만 있으면 새 신청을 받는다.

### F-10 이메일 알림

- 이벤트가 생기면 `sendEmail` 작업을 등록한다. 템플릿은 기획서 F-10 표의 6종이다.
- 실패 시 3번까지 다시 시도하고 `emailLogs`에 결과를 남긴다.
- 메일 본문 링크에는 로그인이 필요한 화면 주소만 넣고, 진단 결과 숫자 외의 상세 내용은 넣지 않는다.

## 7. 상태 모델

### 가게

```text
collecting → measuring → diagnosed
     │            └→ measure_failed → (다시 시도) → measuring
     └→ collected(무료 진단을 이미 쓴 계정) → (보고서 승인) → measuring
변경 시 → archived
```

- 후보 선택(S09)은 가게를 저장하기 전 단계라 가게 상태에 넣지 않는다.
- 수집에서 지역·업종을 얻지 못하면 `measure_failed`가 된다.

### 측정 작업

```text
queued → running → parsing → completed
                          └→ failed(실패율 30% 초과)
어느 단계에서든 가게 변경·중단 → canceled
```

### 보고서 신청

```text
requested → approved → generating → completed
         │                       └→ generation_failed → (관리자 다시 생성) → generating
         └→ rejected → (사장님 다시 신청) → requested
```

### S07 홈 상태 카드와의 대응

현재 가게에 보고서 신청이 있으면 신청 상태로 카드를 고르고, 없으면 가게 상태로 고른다.

| S07 카드 | 판단 기준 |
|---|---|
| 가게 없음 | 보관 중이 아닌 가게 없음 |
| 수집·측정 중 | 가게 `collecting` 또는 `measuring` |
| 측정 실패 | 가게 `measure_failed` |
| 진단 완료 | 가게 `diagnosed` |
| 무료 사용 후 가게 변경 | 가게 `collected` |
| 보고서 신청됨 | 신청 `requested`·`approved` |
| 보고서 거절됨 | 신청 `rejected` |
| 보고서 생성 중 | 신청 `generating` 또는 `generation_failed` |
| 보고서 완료 | 신청 `completed` |

## 9. 비기능 요구사항

### 보안

- Argon2id 비밀번호 해시, 토큰은 해시로만 저장
- CSRF 방어, 보안 쿠키, 세션 14일
- 로그인 5회 실패 시 10분 잠금, 가입·비밀번호 재설정 요청은 IP당 분당 5회 제한
- API 키는 환경변수로 관리
- 모든 객체에 소유자·관리자 접근 검사
- 로그에 비밀번호, 토큰, 이메일 원문을 남기지 않음

### 안정성

- 외부 호출마다 제한 시간을 둔다(지도·웹사이트 5~10초, AI 60초).
- 비동기 작업은 중복 방지 키를 쓴다.
- 일부 출처·공급자가 실패해도 성공한 결과는 보존한다.
- 실패율이 30%를 넘으면 진단 결과를 확정하지 않는다.

### 성능 목표

- 일반 화면은 외부 API 호출 없이 2초 이내 응답
- 가게 식별 10초 이내, 정보 수집 30초 이내, 측정 5~15분, 보고서 생성 3분 이내
- 긴 작업은 바로 작업 ID를 돌려주고 진행률을 조회하게 한다.

### 추적성

- 질문 세트 버전, 모델 ID, 회차, 실행 시각, 답변 원문을 저장한다.
- 보고서의 고쳐야 할 점마다 근거(응답 ID, 수집값)로 이동할 수 있어야 한다.
- 관리자 권한 부여·거절, 탈퇴, 가게 변경을 `auditLogs`에 남긴다.

### 비용

- 진단 1회 호출 수: 측정 60회 + 정보 수집용 AI 웹 검색 2회 + 추천 추출 최대 60회(저가 모델) + 질문 생성 1회 이상
- 측정 원가 추정은 약 1,400~2,500원이다(웹 검색 포함 저가 모델, 2026년 10월 공개 가격·환율 1,400원 기준). 추출·수집 호출은 별도다.
- `measurementRuns.costUsd`에 실제 비용을 기록하고, 하루 비용 상한(환경변수)을 넘으면 새 측정을 대기시킨다.

## 13. 작업별 기술 완료 조건

기획서 11장의 작업(W-ID)마다 기능 완료 조건에 더해 아래 기술 조건을 만족해야 완료로 본다. 설계 작업(W-01-1, W-02-1, W-04-5, W-06-1, W-08-3, W-09-3)은 기술 조건이 없다.

### 13.1 공통

- 작업마다 `pytest` 자동 테스트를 추가하고, 외부 API는 녹화한 응답(fixture)으로 대체해 CI에서 돌린다.
- 실제 외부 API를 부르는 시험은 `-m live` 표시로 분리하고, 테스트 가게 세트(기획서 11.1)로만 실행한다.
- 시험 결과(정확도, 시간, 비용)는 `03_실험/` 아래 작업 ID 이름의 기록 파일로 남긴다.
