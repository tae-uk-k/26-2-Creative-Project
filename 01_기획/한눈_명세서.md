# 한눈 서비스 명세서

- 문서 역할: 기획서의 기능을 어떤 기술로 어떻게 구현하고 검증할지 정의하는 기술 기준 문서
- 기능 기준: [한눈 기획서](./한눈_기획서.md) — 범위(8장), 화면(9장), 기능(10장, F-01~F-12), 작업 분해(11장, W-01~W-12), 지도별 정비 방법(15장)
- 대상 버전: 베타
- 우선순위 표기: 기획서 8장과 같다(`P0` 베타에 필수, `P1` 일정이 허용되면, `P2` 후속 개발).
- 이 문서는 기능 규칙을 다시 적지 않는다. 기능 규칙이 바뀌면 기획서를 먼저 고치고, 이 문서의 구현 방법을 맞춘다.
- 2026-10-17 개정: 기획서의 자동 정비 구조(무료 진단 → 자동 정비 신청 → Google·카카오 연결 → 정비안 승인 → 자동 정비 → 2주 뒤 재측정 → 전후 비교 보고서)에 맞춰 고쳤다.

## 1. 시스템 구성

### 1.1 기술 스택

| 영역 | 기술 | 용도 |
|---|---|---|
| 웹 | Flask + Jinja2 + HTML/CSS/JavaScript | 서버 렌더링 화면, 폼 처리 |
| 인증 | Flask-Login(세션), Authlib(구글·카카오 OAuth), Argon2id 비밀번호 해시, Flask-WTF(CSRF) | 가입·로그인·세션·접근 제어 |
| 데이터 | SQLAlchemy + Alembic + PostgreSQL | 관계형 데이터, 이력, 마이그레이션. 원본 응답은 JSONB |
| 비동기 작업 | Redis + RQ | 정보 수집, 반복 AI 호출, 정비안 생성, 자동 정비, 재측정, 보고서 생성, 이메일 발송 |
| AI | OpenAI API(웹 검색 도구), Gemini API(Google 검색 그라운딩) | 측정, 추천 추출, 질문 생성, 정보 수집용 웹 검색, 정비안 문장 생성 |
| 외부 데이터 | Google Places API(New), 카카오 로컬 API, NAVER API HUB 지역 검색, 인스타그램 Graph API(PoC 후) | 가게 식별, 기본정보·상세정보 수집 |
| 지도 정비 | 브라우저 자동화(도구는 D-13), Google Business Profile API(승인 후) | Google·카카오 연결 확인, 현재 값 읽기, 정비, 반영 확인 |
| 이메일 | 트랜잭션 이메일 서비스(SMTP) | 인증, 비밀번호 재설정, 진단·정비·보고서 알림 |
| 배포 | Docker(웹·워커·PostgreSQL·Redis) | 개발·운영 환경 일치 |
| 관측 | 구조화 로그, 오류 추적, 작업별 비용 기록 | 실패 원인, 응답 시간, API 비용 확인 |

- P0에서는 파일 저장소를 쓰지 않는다. 사진은 저장하지 않고(기획서 F-04), P1 전후 비교 보고서 PDF를 만들 때 필요하면 오브젝트 스토리지를 추가한다.

### 1.2 처리 흐름

```text
브라우저
  → Flask 웹 서버 ── PostgreSQL
      → Redis 작업 큐
          → Worker
              → Google Places API / 카카오 로컬 API / NAVER API HUB
              → 가게 공식 웹사이트(robots.txt 허용 시)
              → OpenAI API / Gemini API
              → 인스타그램 Graph API(PoC 통과 시)
              → Google 비즈니스 프로필 관리 화면·카카오 파트너센터(브라우저 자동화)
              → Google Business Profile API(승인 후)
              → 이메일 서비스
```

### 1.3 프로세스와 큐

| 프로세스 | 하는 일 |
|---|---|
| web | 화면 렌더링, 폼 검증, 작업 등록, 진행률 조회. 가게 식별(F-03)을 빼고는 외부 API를 직접 호출하지 않는다. |
| worker `collect` | 가게 식별 이후 정보 수집(진단·재측정) |
| worker `measure` | 질문 생성, AI 반복 호출, 추천 추출, 지표 계산, 고쳐야 할 점 판정(진단·재측정) |
| worker `plan` | 정비안 생성·사실 검사 |
| worker `fix` | 연결 확인, 현재 값 읽기, 자동 정비, 반영 확인. 한눈 공용 계정 하나로 동시에 여러 브라우저를 열지 않도록 지도별로 워커 1개만 둔다. |
| worker `report` | 전후 비교 보고서 생성 |
| worker `email` | 이메일 발송 |
| scheduler | 미인증 계정 정리, 만료 스냅샷 삭제, 초대 미도착 확인, 반영 대기 칸 다시 확인, 재측정 예약 실행 |

- 가게 식별(F-03)은 S08에서 결과를 바로 보여 줘야 하므로 웹 요청 안에서 처리하되, 외부 호출마다 5초 제한을 두고 전체 10초를 넘기면 "잠시 후 다시 시도" 오류를 낸다.

## 2. 권한과 보안 모델

| 역할 | 접근 범위 |
|---|---|
| 비회원 | S01, S02~S06 |
| 사장님(`owner`) | 본인 계정·가게·측정·정비 신청·정비안·정비 기록·전후 비교 보고서(S07~S16) |
| 관리자(`admin`) | A01(`/admin/...`): 신청 승인·거절, 연결 확인, 수동 처리 완료, 정비안·보고서 다시 생성, 지금 재측정 |

- 가게·측정·정비안·정비 기록·보고서를 읽거나 바꾸는 모든 요청은 서버에서 소유자(`stores.ownerId = 현재 사용자`) 또는 관리자 여부를 확인한다. URL의 ID만 바꿔서 남의 데이터를 볼 수 없어야 한다.
- 무료 진단 화면(S11)에는 고쳐야 할 점의 개수만 응답한다. 판정 내용(`findings`)은 정비안 화면(S13)에서만 응답한다.
- 정비안(S13)은 그 가게의 정비 신청이 승인되고 해당 지도가 연결된 뒤에만 응답한다. 전후 비교 보고서(S16)는 보고서가 완료된 뒤에만 응답한다. 조건이 맞지 않으면 화면뿐 아니라 응답 데이터에도 내용을 넣지 않는다.
- 자동 정비 작업에는 사장님이 승인한 칸의 승인 값(`fixPlanItems.approvedValue`)만 넘긴다. 승인되지 않은 칸을 고치는 코드 경로를 두지 않는다.
- 사장님 아이디·비밀번호는 받지 않는다. 한눈 공용 Google·카카오 계정의 접속 정보와 Google API 토큰은 환경변수(비밀 값)로만 넣고 코드·DB·로그에 남기지 않는다.

### F-01 계정

| 구현 요소 | 내용 |
|---|---|
| 라우트 | `/signup`, `/login`, `/logout`, `/verify-email/<token>`, `/signup/kakao-email`, `/password/forgot`, `/password/reset/<token>`, `/oauth/<provider>/start`, `/oauth/<provider>/callback`, `/account`, `/account/delete` |
| 이메일 정규화 | 앞뒤 공백 제거, 소문자 변환 후 저장·비교 |
| 중복 검사 | 인증을 마친 계정(`emailVerifiedAt` 있음)과 이메일이 같으면 가입 차단하고 `authIdentities.provider`로 기존 가입 방식을 안내. 같은 이메일의 미인증 계정만 있으면 그 계정을 지우고 새로 만든다 |

| 로그인 잠금 | `failedLoginCount` 5회 연속이면 `lockedUntil = 지금 + 10분`, 성공 시 0으로 초기화 |
| 세션 | 쿠키 `Secure`, `HttpOnly`, `SameSite=Lax`, 유지 14일 |
| 탈퇴 | 진행 중인 측정·정비 작업과 재측정 예약을 먼저 취소한 뒤, 한 트랜잭션에서 계정·가게·측정·정비 신청·정비안·정비 기록·보고서 삭제. 이미 고친 Google·카카오 값은 지도에 남는다. 무료 진단을 쓴 계정이면 `freeUsageLedger`에 `HMAC-SHA256(서버 비밀키, 이메일)`만 남김 |
| 무료 사용 확인 | 가입·측정 시작 때 이메일 HMAC 값이 `freeUsageLedger`에 있으면 무료 사용 완료로 본다 |

### F-02 가게 등록·변경

- 계정당 보관 중이 아닌 가게는 1곳(`stores`에 `archivedAt IS NULL` 조건의 `ownerId` 부분 고유 인덱스).
- 변경: 기존 가게에 `archivedAt`을 기록하고, 진행 중인 측정 작업은 RQ 작업 취소 후 `measurementRuns.status = canceled`.
- 정비 신청이 진행 중(`fixRequests.status`가 `rejected`·`report_ready`가 아님, 7장)이면 변경 요청을 409로 거부한다.
- 무료 진단을 이미 쓴 계정은 새 가게의 `collectStore`까지만 실행하고 가게를 `collected`로 둔다. 측정은 자동 정비 신청이 승인된 뒤 시작한다.
- 업종 판정: Google `primaryType`·`types`, 카카오 `category_group_code`·`category_name`, 네이버 `category`를 음식점·카페·바 목록과 비교한다. 목록(예: Google `restaurant` 계열·`cafe`·`coffee_shop`·`bar`, 카카오 `FD6`·`CE7`)은 사전 확인(PoC)에서 확정한다.
- 무료 차감: `measurementRuns.isFree = true`인 측정이 `completed`가 되는 순간 `freeUsageLedger`에 기록한다. `failed`·`canceled`는 차감하지 않는다.

### F-03 링크 판별과 가게 식별

- 입력 문자열에서 URL을 정규식으로 뽑는다. 공유 문구를 통째로 붙여넣어도 첫 번째 지원 URL만 쓴다.
- 짧은 링크(`maps.app.goo.gl`, `kko.to`, `naver.me`)는 리다이렉트를 자동으로 따라가지 않고 `Location` 헤더만 읽는다. 최대 3번, 한 번에 5초.
- 지도별 식별

| 지도 | 링크에서 얻는 값 | 확인 방법 |
|---|---|---|
| Google | 장소 이름, 좌표(`@위도,경도`) | Places Text Search(가게 이름, 좌표 주변 200m)로 장소 ID 확정 |
| 카카오 | 장소 번호 | 키워드 검색(사장님이 입력한 가게 이름) 결과 중 `id`가 장소 번호와 같은 것. 없으면 이름이 비슷한 결과를 S09 후보로, 그것도 없으면 다른 링크 요청 |
| 네이버 | 장소 번호(API 응답에 장소 번호가 없어 직접 대조 불가) | 지역 검색(가게 이름) 결과 중 정규화한 이름이 같은 결과가 1개면 확정, 여러 개면 S09, 없으면 다른 링크 요청 |

- 다른 지도에서 같은 가게 찾기: 가게 이름으로 검색해 좌표 거리 100m 이내이고 이름 유사도가 기준 이상인 결과를 같은 가게로 본다. 유사도 계산은 F-07 이름 정규화 후 비교하며, 기준값은 사전 확인(PoC)의 정확도 측정으로 정한다.
- 결과는 `storeSources`에 지도별 `externalId`, `url`, `matchStatus(found·not_found·candidate)`로 저장한다. Google·카카오가 `not_found`면 F-08 "지도에 정보 없음"으로 판정하고, 그 지도의 정비안은 만들지 않는다(F-09).

### F-04 정보 수집

- 작업: `collectStore(storeId, runId)`, 전체 30초 목표. 출처마다 따로 실행하고 하나가 실패해도 나머지 결과는 저장한다. 재측정(F-11) 때도 같은 작업을 다시 실행한다.
- 출처별 처리

| 출처 | 호출 | 저장 |
|---|---|---|
| Google Places | Place Details(필요한 필드만 field mask로 요청) | 장소 ID는 계속 저장. 나머지는 `sourceSnapshots`(보관 기한은 기획서 15장 미정 3) |
| 카카오 로컬 | 키워드 검색 | 장소 ID·장소 링크만 저장. 화면 표시·비교 때마다 다시 호출 |
| 네이버 지역 검색 | NAVER API HUB 지역 검색 | 결과는 가게 식별, 홈페이지 주소 확인, 기본정보(이름·주소·전화·업종) 비교에만 쓴다. 비교는 코드로 하고 응답 내용은 AI 입력에 넣지 않음(약관 확인 전) |
| 공식 웹사이트 | `robots.txt` 확인(사용자 에이전트 `HanoonBot`) 후 첫 페이지와 메뉴로 보이는 링크 1개, 페이지당 1MB·10초 제한 | 본문 텍스트에서 메뉴·가격·영업시간·소개·영문 페이지 여부를 LLM으로 추출해 저장 |
| AI 웹 검색 | OpenAI·Gemini 각 1회, 웹 검색을 켜고 "가게 이름·주소에 대한 정보"를 구조화 출력(JSON)으로 요청 | `webEvidence`에 사이트 주소·이름·사이트별 가게 정보 저장 |
| 인스타그램 | 기본: AI 웹 검색 결과 중 `instagram.com` 주소 사용. 추가: Business Discovery(기능 플래그, PoC 통과 시 켬) | 계정 주소, 소개글, 최근 게시물 글·게시일 |

- 카카오의 영업시간·메뉴 등 상세 값은 진단 수집에서 읽지 않는다. 연결 뒤 `fix` 워커가 파트너센터 매장정보 화면에서 읽는다(F-10). 이렇게 읽은 값은 정비안의 칸별 현재 값과 정비 기록의 고치기 전 값으로만 저장하고, 그 밖의 저장 범위는 D-10에서 정한다.
- 로그인 세션으로 사이트를 여는 수집 도구, 지도 페이지 크롤링, 차단 우회는 쓰지 않는다. 정비용 관리 화면 자동화는 F-10의 범위로 한정한다.
- (P1) 메뉴판 OCR: Google 사진을 불러와 비전 모델로 메뉴판인지 판별하고 글자만 추출한다. 사진 파일은 저장하지 않는다. Google 약관 확인(기획서 13장 PoC) 전에는 켜지 않는다.

### F-05 질문 생성

- 저가 LLM 1회 호출, JSON 구조화 출력(`lang`, `intentType`, `text` 3개).
- 코드 검증: 가게 이름(한글·영문, 정규화 후 부분 일치) 미포함, 지역 이름·업종 포함, 3개 문장 서로 다름. 실패하면 3번까지 다시 생성하고, 그래도 실패하면 업종별 고정 템플릿 사용.
- `questionSets.version`과 함께 저장하고, 측정 작업은 질문 세트 ID를 참조한다.
- 재측정은 질문을 새로 만들지 않고 정비 전 측정의 `questionSetId`를 그대로 쓴다.

### F-06 AI 측정

- 작업: `runMeasurement(runId)`가 60개의 `callAi` 작업을 만든다(질문 3 × AI 2 × 10회).
- `measurementRuns.kind`로 진단(`diagnosis`)과 재측정(`remeasure`)을 구분한다. 재측정은 무료 차감 대상이 아니다(`isFree = false`).
- 동시 실행: 공급자별 동시 호출 수 제한(기본 5, 환경변수로 조정).
- 호출: 질문 문장만 보내고 시스템 지시는 붙이지 않는다. OpenAI는 웹 검색 도구, Gemini는 Google 검색 그라운딩을 켠다.
- 제한 시간 60초, 실패 시 2번까지 지수 백오프로 다시 시도. `aiExecutions`의 (`runId`, `questionId`, `provider`, `repeatNo`) 고유 키로 중복 호출과 중복 비용을 막는다.
- 저장: `aiExecutions`(모델 ID, 회차, 상태, 지연 시간, 오류 코드, 시도 횟수), `aiResponses`(답변 원문, 원본 JSON, 출처 URL).
- 모든 호출이 끝나면 실패율을 계산해 30%를 넘으면 `failed`, 아니면 다음 단계(F-07)로 넘어간다.
- 다시 시도는 가게당 하루 3회까지다(진단·재측정 공통). 그날(한국 시간 기준) 해당 가게의 다시 시도로 만든 `measurementRuns` 수로 판단하고, 넘으면 429로 거부한다.
- 수집에서 지역·업종을 얻지 못하면 측정을 만들지 않고 가게를 `measure_failed`로 둔다(무료 차감 없음).
- 진행률: `measurementRuns.progressDone/progressTotal`을 갱신하고, S10은 `GET /api/runs/<id>/progress`를 3초마다 조회한다. 재측정도 같은 API를 쓴다.

### F-07 추천 추출과 지표

- 답변마다 저가 LLM으로 추천 목록을 뽑는다. 출력 JSON: `recommendations[{name, rank, sourceUrls}]`. 추출에 실패한 답변은 원문을 남기고 지표 계산에서 뺀 뒤 건수를 기록한다.
- 이름 정규화: 소문자 변환, 공백·기호 제거, 지점 표기("본점", "○○점", "branch" 등) 제거. 대상 가게 이름 후보는 세 지도의 한글·영문 이름이다.
- 대상 가게 판정: 정규화한 이름이 후보 중 하나와 같으면 등장(`recommendations.isTarget = true`).
- 지표는 `metrics`에 공급자·질문·대상(우리 가게·주변 가게)별로 값과 분모를 함께 저장한다. 계산식은 기획서 F-07을 따른다.
- 주변 가게 상위 5곳은 정규화 이름으로 묶어 집계한다.

### F-08 고쳐야 할 점 판정

- 네이버·카카오 기본정보 비교는 정규화(공백·기호·지점명 제거, 전화번호 숫자만) 후 코드로 한다. 카카오 로컬 API 값은 저장하지 않고 판정 때 다시 불러온다.
- 코드 규칙 엔진으로 판정한다(LLM 사용은 "질문 조건 정보 부족", "AI가 틀리게 말함"의 문장 비교에 한정).
- Google 지도·카카오맵에서 고칠 수 있는 항목만 만든다. 인스타그램·외부 근거처럼 두 지도 밖에서 고쳐야 하는 항목은 판정하지 않는다.
- 결과는 `findings`에 단계(`diagnosis`·`plan`), 분류, 제목 키, 대상 지도·칸, 영향 순서(주변 가게 중 그 정보를 갖춘 수, 관련 질문 수), 근거(관련 응답 ID·수집값·주변 가게)를 저장한다.
- 무료 진단에서는 카카오 기본정보만 쓴다(`stage = diagnosis`). 연결 뒤 읽은 카카오·Google 현재 값으로 정비안을 만들 때 판정을 추가한다(`stage = plan`, F-09).
- S11에는 `stage = diagnosis`인 `findings`의 개수만 응답한다.

### F-09 정비안 생성

- 화면·라우트: S13 `GET /fix/plans/<planId>`, 승인 `POST /fix/plans/<planId>/approve`
- 작업: `generateFixPlan(fixRequestId, provider)`. 지도가 연결되고(`mapConnections.status = connected`) 현재 값 읽기(`readCurrentValues`)가 끝나면 지도별로 실행한다. 진단 결과가 없는 가게(무료 사용 후 가게 변경)는 신청 승인 직후 `collectStore`→`runMeasurement`부터 실행하고, 측정이 끝난 뒤 만든다.
- 입력: `sourceSnapshots`·`webEvidence`, 연결 뒤 읽은 현재 값, 기준 측정(`baseRunId`)의 `metrics`·`findings`
- 처리 순서
  1. 연결 뒤 읽은 현재 값으로 F-08 판정을 추가한다(`findings.stage = plan`).
  2. 칸 사전(지도별 바꿀 수 있는 칸, 칸 이름·글자 수·형식, D-17)에 있는 칸만 대상으로 한다. 가게 이름·주소·업종은 칸 사전에 넣지 않아 만들 수 없게 한다.
  3. LLM은 칸별 바꿀 값 문장(영문 소개, 한 줄 소개, 메뉴 설명 등)만 만든다. JSON 구조화 출력: `items[{field, proposedValue, findingIds, evidence}]`
  4. 코드 사실 검사: 영업시간·가격·전화 같은 사실 값이 입력 사실 목록에 없으면 `[ ]`로 바꾸고 `needsOwnerInput = true`("확인 필요"). 알레르기·할랄 정보는 입력 사실에 있을 때만 남기고 `sensitive = true`("사장님 확인 필요").
  5. 글자 수·형식을 넘는 값은 줄여서 1번 다시 만든다. 칸 사전에 없는 칸이 나오면 버린다.
- 생성 목표 3분. 실패하면 1번 자동 재시도, 그래도 실패하면 `fixPlans.status = generation_failed`로 두고 A01 [다시 생성]으로 다시 실행한다.
- 정비안 준비가 끝나면 `fixPlans.status = awaiting_approval`, 정비안 준비 이메일을 보낸다.
- 승인(S13 [정비 시작])
  - 한 트랜잭션에서 칸별 `approvedValue`(사장님이 고친 값 포함)와 제외 여부를 저장한다. 사장님이 고친 값도 칸 사전의 글자 수·형식 검사를 거친다.
  - `needsOwnerInput` 칸이 비어 있고 제외되지도 않았거나, `sensitive` 칸에 확인 체크가 없으면 400으로 거부한다.
  - `fixPlans.status`를 `awaiting_approval`에서 `approved`로 바꾸는 조건부 UPDATE로 중복 승인을 막는다(영향 행이 0이면 이미 승인된 것). 성공한 요청만 `applyFix`를 등록한다.
- Google·카카오에서 가게를 찾지 못했으면 그 지도의 정비안은 만들지 않고 S13 탭에 등록·인증 방법을 보여 준다. 등록·연결 뒤 `generateFixPlan`을 다시 실행한다.
- 한쪽 지도만 연결된 상태로 승인하면 그 지도만 정비한다. 나중에 다른 지도가 연결되면 그 지도의 `fixPlans`만 새로 만들어 승인받는다(정비 완료 시점은 D-16).
- 정비안은 생성일, 기준 진단(`baseRunId`), 버전, 사장님이 승인한 최종 값을 함께 저장한다.

### F-10 연결과 자동 정비

- 화면·라우트: S15 `GET /fix/connect`, `POST /fix/connect/<provider>/invited`([초대했어요])

#### 연결

| 단계 | 처리 |
|---|---|
| 초대 표시 | 사장님이 [초대했어요]를 누르면 `mapConnections.status = invited`, `invitedAt` 기록 |
| 초대 수락 | 관리자가 한눈 계정으로 초대를 수락하고 A01 [연결 확인]을 누른다. Google API 승인 뒤에는 `fix` 워커가 Account Management API로 초대를 조회·수락한다 |
| 연결 확인 | `verifyConnection(connectionId)`: Google은 프로필 편집 화면이 열리는지(API 승인 뒤에는 `getVoiceOfMerchantState`의 `hasVoiceOfMerchant`), 카카오는 파트너센터에서 매장이 보이고 매장 > 매장정보 화면이 열리는지 확인 |
| 결과 | 정상이면 `connected`, 연결 완료 이메일, `readCurrentValues` → `generateFixPlan`. 인증 필요·검토 중·중복 프로필·대표 권한 없음이면 `needs_attention`과 사유를 저장하고 S15에 안내 |
| 초대 미도착 | scheduler `checkPendingInvites`(매시간): `invitedAt`에서 3일이 지나도 `connected`가 아니면 S15 안내를 다시 띄우고 이메일을 1번 보낸다(`inviteReminderSentAt`) |
| 권한 회수 | 작업이 지도를 열 때(연결 확인·현재 값 읽기·정비·반영 확인·재측정) 가게가 보이지 않거나 API가 403·404를 주면 `revoked`. 그 지도의 남은 칸은 `disconnected`로 끝내고 S07에 "연결이 끊겼어요" |

#### 자동 정비

- 작업: `applyFix(fixPlanId)`. 승인된 정비안 하나(지도 하나)를 브라우저 세션 하나로 처리한다.
- 칸마다 순서: 현재 값을 다시 읽어 `fixLogs.beforeValue`에 먼저 저장 → 승인 값 입력·저장 → 다시 읽어 확인 → `applied` 또는 `pending_reflection`
- 지도별 방법

| 지도 | 방법 | 전환 |
|---|---|---|
| Google 지도 | API 승인 전: `business.google.com` 관리 화면 브라우저 자동화. 승인 후: Business Profile API(Business Information API `locations.patch`에 `updateMask`로 승인한 칸만 지정). 칸별 API 지원 범위는 D-14 | 환경변수 `GOOGLE_FIX_MODE=browser·api` |
| 카카오맵 | 파트너센터 매장 > 매장정보 화면 브라우저 자동화(수정 API 없음) | — |

- 자동화 차단(로그인 화면, 보안 확인, 캡차, 예상하지 못한 화면)이 나타나면 즉시 멈추고 다시 시도하지 않는다. 그 칸과 같은 정비안의 남은 칸을 `manual_required`로 바꾸고 관리자에게 수동 처리 이메일을 보낸다. 차단을 우회하는 설정·도구는 쓰지 않는다.
- 시간 초과 같은 일시 오류는 1번 다시 시도하고, 그래도 실패하면 `manual_required`로 넘긴다.
- 반영 확인: `pending_reflection` 칸은 scheduler `recheckPendingFixes`가 1시간마다 `verifyFix`를 등록해 24시간 동안 다시 읽는다(카카오 반영 30분~1시간, Google 검토). 반영 확인은 읽기만 하고 다시 쓰지 않는다. 24시간이 지나도 반영되지 않은 칸의 처리는 D-15.
- 수동 처리: A01은 `fixLogs.status = manual_required`인 칸을 바꿀 값·관리 화면 바로가기와 함께 보여 준다. 관리자가 직접 고친 뒤 [처리 완료]를 누르면 `manual_done`, `handledBy`·`handledAt`을 기록한다.
- 정비 완료: 칸 상태가 바뀔 때마다 `finalizeFix(fixRequestId)`가 승인된 정비안의 모든 칸이 끝났는지(`applied`·`manual_done`·`disconnected`) 확인한다. 모두 끝나면 `fixRequests.status = remeasure_scheduled`, `fixCompletedAt` 기록, 정비 완료 이메일, `remeasureSchedules(dueAt = fixCompletedAt + 14일)` 생성.
- 덮어쓰기 방지: `applyFix`는 정비안당 한 번만 실행된다(`fixPlanId` 중복 방지 키, `fixLogs`의 `fixPlanItemId` 고유 키). 정비 완료 뒤 지도 값을 다시 쓰는 작업은 없다.

### F-11 재측정과 전후 비교 보고서

- 화면·라우트: S16 `GET /fix/report`
- 예약: `remeasureSchedules`에 저장해 작업 서버가 다시 시작돼도 사라지지 않게 한다. scheduler `dispatchRemeasures`(10분마다)가 `dueAt`이 지난 `scheduled` 예약을 조건부 UPDATE로 `started`로 바꾼 뒤 재측정을 시작한다(중복 시작 방지).
- A01 [지금 재측정]: `dueAt = 지금`, `triggeredBy = admin`. 보고서에는 정비 완료부터 재측정 시작까지의 일수(`intervalDays`)를 "정비 후 N일 만에 측정"으로 표시한다.
- 재측정 순서: `collectStore` → `runMeasurement(kind = remeasure, questionSetId = 정비 전 측정과 같음)` → `finalizeRun`(F-07 지표) → `compareFixValues` → `generateComparisonReport`
- `compareFixValues`: 정비 기록의 바꾼 값을 재측정 때 다시 모은 지도 값과 비교해 `fixLogs.remeasureValue`, `remeasureMatch(match·differs·unknown)`를 저장한다. Google은 Places 재수집 값, 카카오는 연결이 살아 있으면 파트너센터에서 다시 읽은 값을 쓰고, 읽지 못하면 `unknown`.
- 실패율이 30%를 넘으면 `fixRequests.status = remeasure_failed`로 두고 보고서를 만들지 않는다. 다시 시도는 F-06과 같이 하루 3회까지다.
- `generateComparisonReport(fixRequestId)`
  - 전후 지표: AI별 등장률, 평균 등장 순서, 질문별 등장 횟수, 우리 가게 추천에 쓰인 출처, Google 지도·카카오맵 인용 여부(출처 URL 도메인으로 판정)
  - 주변 가게: 정비 전 상위 5곳의 전·후 등장률(재측정 쪽은 `recommendations`에서 정규화 이름으로 다시 계산)과 정비 후 새 상위 5곳
  - 한쪽 측정에서 "측정하지 못함"인 질문은 비교에서 빼고 표시한다.
  - 보고서 문장은 계산값과 고정 문구 템플릿으로 만든다. 순위·노출 보장 표현이 들어가지 않게 LLM 생성 문장은 넣지 않는다.
  - 생성 목표 3분. 실패하면 1번 자동 재시도, 그래도 실패하면 `comparisonReports.status = generation_failed`, A01 [다시 생성].
- 완료되면 `comparisonReports`(정비 전·후 측정 ID, 정비 기록 참조, 내용 JSONB)를 저장하고 `fixRequests.status = report_ready`, 보고서 완료 이메일을 보낸다.

### F-12 이메일 알림

- 이벤트가 생기면 `sendEmail` 작업을 등록한다. 템플릿은 기획서 F-12 표의 10종이다.

| 템플릿 | 발송 시점 | 받는 사람 |
|---|---|---|
| `verify_email` | 이메일 가입, 카카오 이메일 입력 | 사장님 |
| `password_reset` | 재설정 요청(소셜 가입 계정은 가입 방식 안내) | 사장님 |
| `diagnosis_result` | 무료 진단 `completed`·`failed` | 사장님 |
| `fix_requested` | 자동 정비 신청 `requested` | 관리자 |
| `fix_decided` | 신청 승인·거절 | 사장님 |
| `map_connection` | 지도 `connected`, 초대 미도착 3일 | 사장님 |
| `fix_plan_ready` | 정비안 `awaiting_approval` | 사장님 |
| `manual_required` | 칸이 `manual_required`가 됨(같은 정비안은 한 번에 묶어 발송) | 관리자 |
| `fix_completed` | 정비 완료(`remeasure_scheduled`) | 사장님 |
| `report_ready` | 전후 비교 보고서 완료 | 사장님 |

- 실패 시 3번까지 다시 시도하고 `emailLogs`에 결과를 남긴다. 발송 실패는 측정·정비·보고서 상태에 영향을 주지 않는다.
- 사장님 메일에는 로그인이 필요한 화면 링크와 기획서 F-12 표의 요약만 넣는다. 정비 완료 메일의 바꾼 내용은 지도별 칸 이름으로 요약하고, 바꾼 값 원문과 고쳐야 할 점 내용은 넣지 않는다.

## 7. 상태 모델

### 가게

```text
collecting → measuring → diagnosed
     │            └→ measure_failed → (다시 시도) → measuring
     └→ collected(무료 진단을 이미 쓴 계정) → (정비 신청 승인) → measuring
변경 시 → archived
```

- 후보 선택(S09)은 가게를 저장하기 전 단계라 가게 상태에 넣지 않는다.
- 수집에서 지역·업종을 얻지 못하면 `measure_failed`가 된다.

### 측정 작업

```text
queued → running → parsing → completed
                          └→ failed(실패율 30% 초과)
어느 단계에서든 가게 변경·중단 → canceled
```

### 정비 신청

```text
requested → approved → connecting → fixing → remeasure_scheduled → remeasuring → report_ready
    └→ rejected → (사장님 다시 신청: 새 requested 행)
remeasuring → remeasure_failed → (다시 시도) → remeasuring
```

- `approved` → `connecting`: 기준 진단(`baseRunId`)이 있으면 바로, 없으면 측정이 `completed`된 뒤
- `connecting`(연결·정비안 생성·승인 대기) → `fixing`: 첫 정비안이 승인될 때
- `fixing`(승인한 칸 정비, 수동 처리 포함) → `remeasure_scheduled`: 정비 완료(F-10), 14일 대기
- `remeasure_scheduled` → `remeasuring`: 예약 시각 도래 또는 A01 [지금 재측정]. 보고서 생성까지 `remeasuring`에 둔다.
- 지도별 진행은 `mapConnections`·`fixPlans`·`fixLogs` 상태로 따로 관리한다.

### 지도 연결·정비안·칸

```text
[연결]
not_connected → invited → connected
                   └→ needs_attention(인증 필요 등) → (조치 후 연결 확인) → connected
connected → revoked(권한 회수) → (다시 초대) → invited

[정비안]
generating → awaiting_approval → approved
    └→ generation_failed → (다시 생성) → generating

[칸]
queued → applied
    ├→ pending_reflection → applied(반영 확인) / D-15
    └→ manual_required → manual_done
어느 단계에서든 권한 회수 → disconnected
```

### S07 홈 상태 카드와의 대응

현재 가게에 정비 신청이 있으면 신청 상태로 카드를 고르고, 없으면 가게 상태로 고른다. 위에서부터 처음 맞는 카드 하나를 보여 준다.

| S07 카드 | 판단 기준 |
|---|---|
| 가게 없음 | 보관 중이 아닌 가게 없음 |
| 정비 신청됨 | 신청 `requested` |
| 신청 거절됨 | 가장 최근 신청 `rejected` |
| 수집·측정 중 | 신청 없음 또는 `approved`이면서 가게 `collecting`·`measuring` |
| 측정 실패 | 신청 없음 또는 `approved`이면서 가게 `measure_failed` |
| 진단 완료 | 신청 없음, 가게 `diagnosed` |
| 무료 사용 후 가게 변경 | 신청 없음, 가게 `collected` |
| 정비안 확인 필요 | 신청 `connecting`·`fixing`이고 `awaiting_approval` 정비안 있음 |
| 정비안 준비 중 | 신청 `connecting`이고 `generating`·`generation_failed` 정비안 있음 |
| 연결 필요 | 신청 `connecting`이고 정비안 없음 |
| 정비 중 | 신청 `fixing` |
| 재측정 대기 | 신청 `remeasure_scheduled` |
| 재측정 중 | 신청 `remeasuring` |
| 재측정 실패 | 신청 `remeasure_failed` |
| 보고서 완료 | 신청 `report_ready` |

- 연결 끊김: 어느 카드든 `mapConnections.status = revoked`인 지도가 있으면 "Google(또는 카카오) 연결이 끊겼어요"와 [다시 연결하기]를 함께 보여 준다.
- 정비 중 카드의 "일부 칸은 한눈 팀이 직접 고치고 있어요"는 `manual_required` 칸이 있을 때 보여 준다.

### A01 상태 필터와의 대응

| A01 상태 | 판단 기준 |
|---|---|
| 대기 | 신청 `requested` |
| 승인 | 신청 `approved` |
| 연결 대기 | 신청 `connecting`이고 정비안 없음 |
| 정비안 확인 대기 | `awaiting_approval` 정비안 있음 |
| 정비 중 | 신청 `fixing` |
| 수동 처리 필요 | `manual_required` 칸 있음 |
| 재측정 대기 | 신청 `remeasure_scheduled`·`remeasuring` |
| 보고서 완료 | 신청 `report_ready` |
| 거절 | 신청 `rejected` |
| 실패 | 정비안·보고서 `generation_failed` 또는 신청 `remeasure_failed` |

### 보안

- Argon2id 비밀번호 해시, 토큰은 해시로만 저장
- CSRF 방어, 보안 쿠키, 세션 14일
- 로그인 5회 실패 시 10분 잠금, 가입·비밀번호 재설정 요청은 IP당 분당 5회 제한
- API 키, 한눈 공용 Google·카카오 계정 접속 정보, Google API 토큰은 환경변수로 관리
- 모든 객체에 소유자·관리자 접근 검사
- 로그에 비밀번호, 토큰, 이메일 원문, 계정 접속 정보를 남기지 않음
- 자동 정비는 사장님이 초대한 가게의 승인한 칸만 고치고, 자동화 차단을 우회하는 설정·도구를 쓰지 않음

### 안정성

- 외부 호출마다 제한 시간을 둔다(지도·웹사이트 5~10초, AI 60초, 관리 화면 작업 3~15분).
- 비동기 작업은 중복 방지 키를 쓴다.
- 일부 출처·공급자가 실패해도 성공한 결과는 보존한다.
- 실패율이 30%를 넘으면 진단·재측정 결과를 확정하지 않는다.
- 자동 정비는 칸마다 고치기 전 값을 먼저 저장한 뒤 수정한다.
- 재측정 예약은 DB에 두어 작업 서버가 다시 시작돼도 유지한다.

### 성능 목표

- 일반 화면은 외부 API 호출 없이 2초 이내 응답
- 가게 식별 10초 이내, 정보 수집 30초 이내, 측정 5~15분, 정비안 생성 3분 이내, 전후 비교 보고서 생성 3분 이내
- 긴 작업은 바로 작업 ID를 돌려주고 진행률을 조회하게 한다.

### 추적성

- 질문 세트 버전, 모델 ID, 회차, 실행 시각, 답변 원문을 저장한다.
- 정비안의 칸마다 근거(고쳐야 할 점, 응답 ID, 수집값)로 이동할 수 있어야 한다.
- 정비 기록에 칸별 정비 방법(브라우저·API·수동), 고치기 전 값, 바꾼 값, 시각, 반영 확인 결과를 남긴다.
- 관리자 신청 승인·거절, 연결 확인, 수동 처리 완료, 다시 생성, 지금 재측정, 사장님 정비안 승인, 탈퇴, 가게 변경을 `auditLogs`에 남긴다.

### 비용

- 진단 1회 호출 수: 측정 60회 + 정보 수집용 AI 웹 검색 2회 + 추천 추출 최대 60회(저가 모델) + 질문 생성 1회 이상
- 측정 원가 추정은 약 1,400~2,500원이다(웹 검색 포함 저가 모델, 2026년 10월 공개 가격·환율 1,400원 기준). 추출·수집 호출은 별도다.
- 정비 1건: 정비 전·후 측정 2번(진단이 없던 가게도 승인 후 측정 1번 + 재측정 1번) + 지도별 정비안 생성
- `measurementRuns.costUsd`에 실제 비용을 기록하고, 하루 비용 상한(환경변수)을 넘으면 새 측정을 대기시킨다.

## 13. 작업별 기술 완료 조건

기획서 11장의 작업(W-ID)마다 기능 완료 조건에 더해 아래 기술 조건을 만족해야 완료로 본다. 설계 작업(W-01-1, W-02-1, W-04-5, W-06-1, W-08-3, W-09-3, W-12-3)은 기술 조건이 없다.

### 13.1 공통

- 작업마다 `pytest` 자동 테스트를 추가하고, 외부 API는 녹화한 응답(fixture)으로 대체해 CI에서 돌린다.
- 관리 화면 자동화는 저장해 둔 관리 화면 HTML(fixture)을 로컬에서 띄워 테스트한다. 로그인 화면·보안 확인 화면 fixture도 함께 둔다.
- 실제 외부 API를 부르는 시험은 `-m live` 표시로 분리하고, 테스트 가게 세트(기획서 11.1)로만 실행한다. 실제 지도를 고치는 시험은 동의하고 한눈을 초대한 지인 가게에서만 실행한다.
- 시험 결과(정확도, 시간, 비용)는 `03_실험/` 아래 작업 ID 이름의 기록 파일로 남긴다.
