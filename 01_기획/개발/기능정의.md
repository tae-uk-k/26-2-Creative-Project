# 기능 정의

기준일: 2026-11-25. 스마트스토어·카페24 상품 정비 서비스의 기능을 F-01~F-13으로 나눠 입력·처리·결과·예외를 정한다. 화면은 [이용 흐름과 화면](../이용흐름과화면.md)의 P01~P06, 진행 상태는 [운영 현황](../운영/운영현황.md)의 C-01~C-11을 따른다. 이 문서의 기능은 2026-11-18 이전 지도 베타의 F-01~F-12와 번호가 같아도 다른 기능이다.

| ID | 기능 | 화면 | 운영 현황 |
|---|---|---|---|
| F-01 | 계정·인증 | P01 | U9 |
| F-02 | 스토어 등록·주소 판별 | P02 | C-03 |
| F-03 | 관리자 위임·스토어 식별 | P02, P06 | C-05, C-07, C-11, D14 |
| F-04 | 상품 원본 수집·상품 목록 | P03 | C-03, C-06, C-07 |
| F-05 | AI 자료 조사·사실 확인 | P04 | C-08 |
| F-06 | 필요한 사실 판단·질문·답변 | P04 | C-08 |
| F-07 | 정비안 생성 | P04 | C-01, C-08 |
| F-08 | 항목 선택 승인 | P04 | C-05 |
| F-09 | 저장·재조회·공개 반영·수동 편집 | P04 | C-06, C-10 |
| F-10 | 복구·쓰기 이력 | P04 | C-02 |
| F-11 | AI 노출 진단·전후 비교 | P05 | C-09, D6, D8 |
| F-12 | 운영자 고객 업무 | P06 | C-05 |
| F-13 | 연결 해제·선택 API 연결 | P02 | C-02, D10 |

## F-01 계정·인증

| 구분 | 내용 |
|---|---|
| 입력 | 이메일·비밀번호 또는 Google·카카오 인증, 약관 동의 |
| 처리 | 서버 세션과 CSRF 쿠키(`seelo_csrf`)를 발급한다. 이메일 가입은 인증 링크를 확인해야 완료된다. |
| 결과 | 로그인 세션. 관리자 역할 계정은 운영자 기능을 쓴다. |
| 예외 | 카카오에서 이메일을 받지 못하면 이메일을 따로 받는다. 세션 만료·사용자 교체 때 화면 캐시를 비운다. |

지도 베타 때 구현한 계정·인증 코드를 그대로 쓴다.

## F-02 스토어 등록·주소 판별

| 구분 | 내용 |
|---|---|
| 입력 | 스토어 주소. 판별이 안 되면 플랫폼과 몰 ID |
| 처리 | 주소에서 플랫폼, 스토어 ID, 카페24 쇼핑몰 번호를 판별한다. 스마트스토어 예약 경로(`main`·`search` 등)는 스토어 ID로 받지 않는다. |
| 결과 | 고객 소유의 스토어. 관리자 권한·API 인증 상태는 각각 초기값이다. |
| 예외 | 연결 도메인은 `custom_domain_requires_mall_id`로 몰 ID 직접 입력을 요구한다. |

## F-03 관리자 위임·스토어 식별

| 구분 | 내용 |
|---|---|
| 입력 | 고객의 초대 전달 기록, 운영자의 권한 확인·회수 기록, 스토어 이름·고유 ID |
| 처리 | 관리자 권한 상태를 `not_requested → invited → verified → revoked`로 바꾼다. 고객은 `invited`만 기록한다. `verified`·`revoked`와 고유값은 운영자만 기록한다. |
| 결과 | `verified` 스토어에서만 관리 화면 수집·저장을 실행한다. 실행기는 기록한 스토어 이름·고유 ID와 화면 값을 정확히 대조한다. |
| 예외 | 비슷한 이름은 다른 스토어로 본다. 위임 목록에서 같은 값이 0곳·2곳 이상이면 멈춘다. 카페24는 최종 화면 주소의 쇼핑몰 번호도 대조한다. 회수하면 고유값을 지운다. |

위임 목록 전환(`store_switch`)은 몰별 화면 설정이 있을 때만 쓴다. 실제 대행사 매니저·부운영자 화면 확인 전이라 기본 설정에 넣지 않았다. 연결 화면에서 플랫폼별 초대 방식과 상품 권한을 안내한다(C-11). 실제 담당자 연락처와 접속 정보 전달 방법은 운영 현황에서 관리한다.

## F-04 상품 원본 수집·상품 목록

| 구분 | 내용 |
|---|---|
| 입력 | 상품번호, 카페24는 같은 몰의 상품 주소도 가능. 또는 판매자가 제공한 원본 |
| 처리 | 고객이나 운영자가 요청한다. 브라우저 수집 작업을 등록하고 202를 돌려준다. 작업은 관리 화면에서 스토어와 상품번호를 확인하고 상품명·정비 칸·보호 칸을 읽는다. |
| 결과 | 원본(필드 값·보호 칸·해시·수집 시각·출처 `browser`)을 저장한다. |
| 예외 | 스마트스토어 공개 주소의 번호는 원상품번호가 아니므로 받지 않는다. 판매자 제공 원본은 자동 저장 근거로 쓰지 않는다. 같은 상품 수집 중복 등록을 막는다. |

플랫폼 상품 목록(`catalog`)은 몰별 화면 설정이 있을 때만 관리 화면의 상품번호·이름을 읽는다. 가져온 상품 목록은 서버가 `query`·`page`·`pageSize`로 검색한다.

## F-05 AI 자료 조사·사실 확인

| 구분 | 내용 |
|---|---|
| 입력 | 수집한 원본, 지정한 공식 자료 주소(최대 3개) |
| 처리 | 원본 본문, 지정 자료, 본문 속 공개 링크, (설정 시) 웹 검색 인용 주소를 읽고 사실을 추출한다. |
| 결과 | 인용문 검사를 통과한 사실만 저장한다. 사실마다 출처·인용문·모델 ID를 남긴다. |
| 예외 | 인용문이 원문에 없으면 거부한다. 단위 없는 함량은 저장하지 않는다. 충돌 값은 채택하지 않는다. AI 모델이 없거나 55초 안에 끝나지 않으면 `COMMERCE_AI_UNAVAILABLE`이다. |

세부 규칙은 [AI 수집과 최소 질문](../AI수집과최소질문.md) 2~4절을 따른다.

## F-06 필요한 사실 판단·질문·답변

| 구분 | 내용 |
|---|---|
| 입력 | 상품 원본과 확인한 사실, 판매자 답변 |
| 처리 | AI가 필요한 사실 종류를 최대 8개 고른다. 확인하지 못한 것 중 답하지 않은 질문이 최대 2개가 되도록 묻는다. |
| 결과 | 질문 목록과 보류(`fact:{키}`). 답변은 판매자 답변 출처로 저장한다. |
| 예외 | 묻지 않은 사실의 답변은 `answer_not_requested`로 거부한다. 누적 질문 상한은 설정한 경우에만 적용한다. |

## F-07 정비안 생성

| 구분 | 내용 |
|---|---|
| 입력 | 필드 선택(선택), 필수 사실 지정(선택), 사실 순서 |
| 처리 | 필드를 고르지 않으면 기본 범위를 쓴다. 지원 필드를 검사하고 확인한 사실로 값을 만든다. |
| 결과 | `draft` 정비안(항목별 현재 값·변경 값·근거·실행 방법) 또는 `no_changes` |
| 예외 | 미지원 필드는 `field_not_supported`, 자동 필드가 하나도 없으면 `no_automatic_fields`로 거부한다. 스마트스토어 API 모드에서 편집기 전환을 허용하지 않으면 상세설명을 수동 항목으로 만든다. |

값을 만드는 규칙은 [상품정보 정비 기준](../상품정보정비기준.md) 2~3절을 따른다. 정비안 목록은 최근 50개를 돌려준다.

## F-08 항목 선택 승인

| 구분 | 내용 |
|---|---|
| 입력 | 정비안 ID, 원본 해시, 승인할 필드, (스마트스토어 API 모드) 편집기 전환 확인 |
| 처리 | 스토어 소유자인지, 원본 해시와 정비안이 최신인지 확인하고 승인자(`approvedBy`)를 기록한다. |
| 결과 | `approved`. 승인한 필드·편집기 전환 확인·승인자를 정비안에 저장한다. |
| 예외 | 운영자 계정은 승인할 수 없다(403). 원본이 바뀌었으면 `COMMERCE_SOURCE_CHANGED`로 거부한다. 같은 상품에 진행 중인 정비안이 있으면 승인하지 않는다. |

## F-09 저장·재조회·공개 반영·수동 편집

| 구분 | 내용 |
|---|---|
| 입력 | 고객 또는 운영자의 적용·재조회 요청, 운영자의 공개 확인 결과(PC·모바일 주소와 관찰 결과)·수동 편집 결과 |
| 처리 | 요청자가 스토어 소유자이거나, 고객 승인 기록이 있는 정비안의 운영자인지 확인한다. 서버 쓰기 설정을 확인한다. 브라우저 작업이 원본·보호 칸을 다시 대조하고 승인 필드만 저장한 뒤 다시 읽는다. |
| 결과 | `applied`·`pending_reflection`·`uncertain`·`conflict`·`rejected`. 승인 항목에 수동 항목이 있으면 적용 요청 때 `manual_required`로 바꾸고 작업 지침을 제공한다. 공개 확인과 수동 편집(`manual_recorded`)은 운영자 기록으로 남긴다. |
| 예외 | `COMMERCE_WRITES_ENABLED=false`면 저장하지 않는다. 위임 회수 뒤에는 `rejected`(`connection_revoked`)다. 결과가 불명확하면 재전송하지 않고 재조회만 받는다. |

## F-10 복구·쓰기 이력

| 구분 | 내용 |
|---|---|
| 입력 | 고객 또는 운영자의 복구 요청(별도 확인). 운영자는 고객 승인 기록이 있는 정비안만 |
| 처리 | 승인한 필드의 수정 전 값만 저장하고 다시 읽는다. |
| 결과 | `rolled_back`. 저장·복구마다 쓰기 이력(작업 종류·상태·오류 코드·시각)을 남긴다. |
| 예외 | 이후 같은 칸이 바뀌었으면 원본 충돌로 중단하고 기존 `applied` 상태를 유지한다. |

## F-11 AI 노출 진단·전후 비교

| 구분 | 내용 |
|---|---|
| 입력 | 고객 또는 운영자의 질문 세트(질문 ID·질문, 대상 상품명·주소. 상품명을 비우면 상품명 사용), 회차 이름·공급자·반복 수 |
| 처리 | 질문마다 새 요청으로 공급자별 AI 큐에서 실행한다. 원문·출처·발견·추천 순위·링크 인용을 판정한다. |
| 결과 | 회차별 정상·무효·발견·추천(상위 3)·상품 링크 인용. 측정 당시 원본 해시와 마지막 반영 정비안을 함께 저장한다. |
| 예외 | 질문에 대상 상품명·주소가 있으면 거부한다. 호출 실패는 1회만 다시 실행하고 무효로 남긴다. 조건이 다른 회차는 비교를 거부한다. |

## F-12 운영자 고객 업무

| 구분 | 내용 |
|---|---|
| 입력 | 관리자 권한 상태 필터, 검색어, 페이지 |
| 처리 | 고객 스토어와 정비안 상태별 대기 수를 조회한다. |
| 결과 | 작업 대기(실행·수동 편집·결과 확인)와 고객 승인 대기 목록 |
| 예외 | 관리자 역할만 볼 수 있다. 조회만 제공하며 고객 승인을 대신하지 않는다. |

## F-13 연결 해제·선택 API 연결

| 구분 | 내용 |
|---|---|
| 입력 | 고객의 연결 해제 확인. API 모드에서는 카페24 OAuth 시작, 스마트스토어 공식 판매자 ID(운영자) |
| 처리 | 해제하면 수집·저장을 멈추고 보관한 토큰을 폐기하고 대기 작업을 취소하고 담당자 세션을 지운다. 카페24 OAuth는 계정·쇼핑몰에 묶인 10분짜리 일회용 state를 쓴다. |
| 결과 | API 인증 상태 `authorized → read_verified → write_verified` 또는 `revoked` |
| 예외 | 플랫폼 쪽 매니저·부운영자·앱 권한 삭제는 판매자가 직접 한다. 개인용 스마트스토어 앱 키는 받지 않는다. |

API 경로는 `COMMERCE_EDIT_MODE=api`에서만 쓴다. 기본 경로에 넣을지는 D10에서 정한다.
