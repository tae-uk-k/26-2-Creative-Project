# 09. 자동 정비(F-09·F-10, W-08·W-09)

## 1. 정비 신청(S12, W-08-1)

`POST /api/fix/requests`
1. 보관 중이 아닌 가게가 없으면 409 `NO_STORE`.
2. `can_request_fix(store)`(03 7장) 아니면: rejected가 아닌 신청이 있으면 409 `ALREADY_REQUESTED`, 가게 상태가 맞지 않으면 409 `NOT_ELIGIBLE`.
3. 03 E8. `base_run_id` = 그 가게의 가장 최근 `completed` 진단 측정(없으면 NULL). 동시 요청은 부분 고유 인덱스 `uq_fix_request_store_active` 위반 → 409 `ALREADY_REQUESTED`로 바꾼다.

관리자 승인·거절(W-08-2): 04 8장, 03 E9·E10. 이미 처리된 신청이면 `transition`이 False → 409 `INVALID_STATE`.

구현 메모(2026-10-28, 9단계, `services/fix_request_service.py`)
- 신청: 가게 행을 `FOR UPDATE`로 잡아 같은 가게 신청을 한 줄로 세우고, 그래도 겹치면 부분 고유 인덱스 위반을 409 `ALREADY_REQUESTED`로 바꾼다. 확인 순서: 가게 없음 → rejected가 아닌 신청 있음(`ALREADY_REQUESTED`) → 가게 상태(`NOT_ELIGIBLE`).
- 메일 `fix_requested`는 `ADMIN_NOTIFY_EMAILS`로 간다. 비어 있으면 메일 행을 만들지 않고 경고 로그만 남긴다(10 4장).
- 승인: requested → approved와 연결 2행(not_connected)을 만들고, 기준 측정이 있으면 같은 트랜잭션에서 approved → connecting. 없으면 가게 collected → collecting, 진단 측정(무료 아님, `fix_request_id`, trigger initial) + `collectStore`. 가게가 collected가 아니면 409. 응답 `{status}`는 마지막 상태.
- 거절: 사유는 앞뒤 공백을 지우고 비면 422 `REJECT_REASON_REQUIRED`. 감사 기록 `detail.reason`에 사유.
- E26 재측정 다시 시도(`POST /fix/requests/current/remeasure/retry`)도 이 단계에서 만들었다. 질문 세트는 기준 측정의 것.

| google | `phone` | 전화번호 | phone | — | 사실 | `phoneNumbers.primaryPhone` |
| google | `menu` | 메뉴·가격 | menu | 항목 100개 | 사실(이름·가격·단위) + 필요한 구성·주문 조건만 담은 짧은 설명. 번역은 필요한 항목만 | 없음(Food Menus API 확인 전 수동) |

## 5. 연결 확인 `verifyConnection(connection_id)`(F-10, E12)

1. 연결 상태가 `not_connected`·`invited`·`needs_attention`이고 신청이 approved 이후 진행 중 상태일 때만.
2. 지도·모드별 확인

| 지도·모드 | 확인 | 결과 |
|---|---|---|
| google, api | ① 계정마다 초대 목록 → 이 가게 초대 수락(9.1) ② 위치 목록에서 `metadata.placeId == 가게 Google place id`인 위치 ③ `VoiceOfMerchantState` | 위치 있음 + `hasVoiceOfMerchant` 참 → connected(`external_ref` = `locations/{id}`). 위치 없음 → needs_attention `store_not_visible`. VoM 거짓 → 응답의 조치로 사유(`verify` → verification_required, `waitForVoiceOfMerchant` → under_review, `resolveOwnershipConflict` → duplicate_profile, `complyWithGuidelines` → guideline_violation, 그 밖 other) |
| google, browser | 관리자가 초대를 직접 수락한 뒤 누른다. 관리 화면에서 가게 목록 → 가게 찾기(Google 이름·주소) → 정보 편집 화면 열림 | 열림 → connected(`external_ref` = 화면 주소의 위치 식별값 `[PoC]`). "인증 필요" 표시 → needs_attention verification_required. 목록에 없음 → store_not_visible |
| kakao, browser | 관리자가 초대를 직접 수락한 뒤 누른다. 파트너센터 매장 목록 → 가게 찾기 → 매장 > 매장정보 화면 열림 | 열림 → connected. 매장 없음 → store_not_visible. 정보 수정 권한 없음 → no_owner_authority |

3. `AutomationBlocked`(8.3)면 연결 상태를 바꾸지 않고 감사 기록 `detail.result = "blocked"`, 관리자 메일 `manual_required`(params: 연결 확인 차단). 관리자가 브라우저 로그인을 다시 한 뒤 [연결 확인]을 다시 누른다.
4. 성공 뒤 처리는 03 E12.

**수동 확인 모드**(`AUTO_FIX_ENABLED=false`일 때, 또는 자동 확인이 막혔을 때): 관리자가 직접 관리 화면에서 확인한 결과를 `POST /api/admin/connections/{id}/verify` 본문 `{manualResult: "connected"|"needs_attention", attentionReason?, externalRef?}`로 보낸다. 본문에 `manualResult`가 있으면 작업을 등록하지 않고 API 안에서 바로 E12를 처리한다(감사 기록 `detail.mode = "manual"`). 본문이 없으면 `verifyConnection` 작업을 등록한다. `AUTO_FIX_ENABLED=false`인데 본문이 없으면 422 `VALIDATION_ERROR`.

구현 메모(2026-10-28, 10단계, `services/connection_service.py`)
- 연결 확인을 받는 신청 상태: approved·connecting·fixing·remeasure_scheduled·remeasuring·remeasure_failed(report_ready는 409). 연결이 not_connected·invited·needs_attention이 아니면 409.
- 수동 결과 `needs_attention`이면 `attentionReason`이 필수(02 DDL의 7가지 값, 없으면 422). 연결 성공 때 `attention_reason`은 비운다. 감사 기록 `detail = {result, attentionReason, mode}`.
- 작업 인자에 확인을 누른 관리자 id(`requested_by`)를 넣어 `confirmed_by`·감사 기록 actor로 쓴다.
- 자동 확인은 지도별 `MapAdmin.open_store(StoreRef, external_ref)`로 한다. 결과: 돌려준 값 → connected(`external_ref`), `StoreNotVisible` → needs_attention `store_not_visible`, `AttentionNeeded(사유)` → needs_attention 그 사유, `TransientAutomationError`는 1번 다시(두 번이면 상태 그대로, 오류 로그), `AutomationBlocked`는 다시 시도 없이 3번 처리(메일 `manual_required` items `[{provider, field_label: "연결 확인", reason: "automation_blocked"}]`).
- 연결 성공의 정비안 만들기: 같은 지도에 approved·awaiting_approval·generating 정비안이 있으면 만들지 않는다. generation_failed만 있으면 다음 버전을 만든다. E4로 신청이 connecting이 되면 이미 연결된 지도마다 같은 단계를 부른다(`plans_for_connected`).
- `readCurrentValues`는 fix 큐(`lock fix:{provider}`)라 정비 워커(worker-fix, compose 프로필 fix)가 있어야 돈다. `AUTO_FIX_ENABLED=false`에서는 브라우저가 필요 없으므로 11단계에서 실행 큐를 다시 정한다. → 11단계: 읽지 않는 모드는 plan 큐(6.1 구현 메모).

## 6. 정비안 만들기(F-09, W-09-2)

### 6.1 `readCurrentValues(fix_plan_id)`(E13)

1. 정비안 `generating`, 연결 `connected`일 때만.
2. 칸 사전의 그 지도 칸을 모두 읽는다(`MapAdmin.read_fields`, api 모드는 GET). `AUTO_FIX_ENABLED=false`이거나, 카카오이고 `KAKAO_FIX_ENABLED=false`면 읽지 않고 모든 `current_value = null`(이때 08 6.5 정비안 단계 판정은 건너뛴다).
3. 칸마다 `fix_plan_items`(field, `current_value`, `order_no` = 사전 order) 행을 만든다(이미 있으면 `current_value`만 갱신).
4. 오류: `AutomationBlocked` → 정비안 `generation_failed`(`last_error = automation_blocked`). `StoreNotVisible`·API 403·404 → E18. 일시 오류 1회 재시도 후 실패 → `generation_failed`(`read_failed`).
5. 성공 → `generateFixPlan(fix_plan_id)` 등록.

구현 메모(2026-10-28, 11단계, `services/fix_plan_service.py`)
- 등록 큐는 `defer_read`가 고른다. 실제로 읽는 모드(`reads_current_values(provider)` = `AUTO_FIX_ENABLED` 그리고 google이거나 `KAKAO_FIX_ENABLED`)는 fix 큐·`lock fix:{provider}`, 읽지 않는 모드는 plan 큐·lock 없음(기본 워커가 돈다. 정비 워커는 compose 프로필 fix에만 있음).
- 칸 행은 `uq_plan_item_field`로 upsert한다(관리자 다시 생성 때 `current_value`만 갱신).
- `StoreNotVisible`은 `connection_service.revoke`(E18) 뒤 `generation_failed`(`store_not_visible`).

### 6.2 사실 목록 `build_facts(...)`

LLM과 사실 검사에 쓰는 "입력 사실"이다. 출처 우선순위(높은 것부터): 공식 웹사이트 → 연결 뒤 읽은 지금 값(두 지도) → Google 스냅샷 → 인스타그램 BD → AI 웹 검색 사이트(2곳 이상이 같은 값일 때만).

```python
@dataclass
class Fact:
    id: str              # "f1", "f2", ...
    kind: str            # hours|phone|website|instagram|menu_item|intro_text|attribute|cuisine|region|landmark
    value: object        # kind별 형식(08 0장)
    source: str          # website|google_current|kakao_current|google|instagram|web
    text: str            # 사실 검사용 평문(숫자 포함)
```

- **네이버 값과 카카오 로컬 API 값은 넣지 않는다.** 카카오는 연결 뒤 파트너센터에서 읽은 지금 값(`kakao_current`)만 넣는다.
- attribute 사실: Google 스냅샷·지금 값의 참인 편의 필드, 카카오 지금 값 `services`의 키워드(08 0.1 표), 웹사이트 본문에서 08 0.1 한글 라벨·영어 표현이 그대로 나오는 경우.

### 6.3 `generateFixPlan(fix_plan_id)`(E14)

현재 정비안 생성의 요구사항은 [AI 수집과 최소 질문](../../AI수집과최소질문.md)과 [지도정보 정비 기준](../../지도정보정비기준.md)을 따른다. 다음 항목은 아래 날짜별 구현 메모와 구분해 구현·검수해야 한다.

- 기존 소개·메뉴·공식 안내·허용된 판독 자료의 사실을 지점·메뉴·단위·조건별로 통합한다. 출처·해당 위치·확인 시각·적용 시점을 연결하고, AI가 적용 조건과 공식 근거로 채택값을 결정한다.
- 근거 전체와 실제 공개할 값을 구분한다. 지원되는 기존 칸에 필요한 정보만 넣고, 정확한 기존 소개는 보존하거나 부분 수정한다. 최소 주문·필수 비용·판매 시간은 축약으로 누락하지 않는다.
- 내부 미확인 목록과 실제 질문 목록을 분리한다. 질문은 누락 중심 기본 0~2개·신청 전체 최대 3개다. S09 이력을 승계하고 두 지도·추가 연결·재생성·동시 생성에도 공통 누적 한도를 서버에서 검사한다.
- 한도 밖·미응답·미확인 필수값·미확인 민감 주장이 있는 새 변경은 시스템 보류한다. 사실이 다른 기존 공개 값의 삭제와 새 변경 보류를 구분한다. 문장·길이·번역 문제는 AI 재작성 또는 관리자 검토로 처리한다.
- 승인 시 보류 제외 상태를 서버가 계산·검증한다. 사장님이 칸별 제외 요청을 만들도록 강제하지 않는다. 아래 과거 승인 절차의 전체 items 집합 대조도 시스템 보류 상태와 일관되게 개정해야 한다.
- 준비된 실행 대상은 사실·형식·필수 조건·필요한 확인을 검증한다. 실행 대상 0개면 finalizeFix로 자동 완료하거나 새 재측정을 예약하지 않고 유지/보류·A01 검토로 구분한다.
- 검수에는 누락 10개에서 질문 3개 이하, 지점 확인 후 남은 2개, 두 지도 동시 생성, 나중 연결·재생성의 누적 유지, 숨은 다중 입력 거부, 미응답 상태의 나머지 승인, 실행 0개에서 완료 방지를 포함한다.

### 6.6 사실 검사(`domain/fact_check.py`, W-09-2)

입력: 만든 문장, 사실 목록. 출력: 고친 문장, `needs_owner_input`, `sensitive`.

1. **숫자 규칙**: 문장 안의 숫자 덩어리(정규식 `\d[\d,.:]*`)마다, 쉼표·점을 뺀 숫자가 사실들의 `text`에서 뽑은 숫자 집합에 없으면 그 숫자를 포함한 표현을 `[ ]`로 바꾼다. 바꿀 표현 범위: 시간(`\d{1,2}(:\d{2})?\s?(am|pm|시)?(\s?~\s?\d{1,2}(:\d{2})?\s?(am|pm|시)?)?`), 가격(`[₩]?\d[\d,]*\s?(원|won|KRW)?`), 전화(`0\d{1,2}-?\d{3,4}-?\d{4}`), 그 밖 숫자 단독. 하나라도 바꾸면 `needs_owner_input = true`.
2. **민감 정보**: 문장에 민감 단어(ko `알레르기|알러지|할랄|글루텐|견과|땅콩|유제품|갑각류`, en `allerg|halal|gluten|peanut|tree nut|dairy-free|shellfish|kosher`, 대소문자 무시)가 있으면, 같은 단어가 사실 `text`에 있을 때만 남기고 `sensitive = true`. 사실에 없으면 그 문장을 지운다.
3. **조건 주장**: 문장에 08 0.1의 영어 표현·한글 라벨(예: vegetarian, 채식, credit card, 카드 결제, reservation, 예약)이 있으면 그 키의 attribute 사실이 참이어야 한다. 아니면 그 문장을 지운다.
4. **금지 내용**(google description): URL(`https?://\S+|www\.\S+`), 이메일, 전화 패턴, 가격 표현(1번 규칙의 가격 정규식, 사실에 있어도), 할인·이벤트 단어(`할인|이벤트|쿠폰|프로모션|discount|sale|coupon|promo`)가 든 문장 → 지운다.
5. 근거 표시: `SentenceRef.fact_ids`에 없는 id는 무시한다. 검사는 1~4가 최종이다(LLM이 붙인 id를 믿지 않는다).
6. 테스트: 일부러 틀린 값을 넣은 문장 20개(`tests/fixtures/fact_check/wrong_20.json`: 없는 영업시간·가격·전화·연도·할랄·알레르기·없는 편의 주장)가 모두 `[ ]`로 바뀌거나 지워진다.

async def guard(page, provider: str, ready_selector: str) -> None:
    host = urlparse(page.url).hostname or ""
    if host in LOGIN_HOSTS[provider]:
        raise AutomationBlocked("login_required")
    if await page.locator(CAPTCHA_SELECTOR).count() > 0:
        raise AutomationBlocked("captcha")
    body = (await page.locator("body").inner_text(timeout=3000)).lower()
    if any(t in body for t in BLOCK_TEXTS):
        raise AutomationBlocked("security_check")
    try:

    except PlaywrightTimeoutError:
        raise AutomationBlocked("unexpected_screen")

## 9. 자동 정비 `applyFix(fix_plan_id)`(W-09-5·6)

1. 정비안 `approved`, 연결 `connected`일 때만. 그 정비안의 `queued` 칸을 `order_no` 순으로 읽는다. 없으면 `finalizeFix` 등록 후 끝.
2. `MapAdmin` 만들기: google이고 `GOOGLE_FIX_MODE=api`면 `GoogleAdminApi`, 아니면 브라우저 세션 하나를 열어 모든 칸에 쓴다. `open_store(store, connection.external_ref)`.
3. 칸마다(중단 요청은 다음 `await`에서 `CancelledError`로 와서 멈춘다. 06 2장 규칙 6)
   1. `read_fields([field])` → **한 트랜잭션으로 `before_value`, `attempt += 1` 저장 후 커밋**(쓰기 전에 반드시 먼저).
   2. `write_field(field, applied_value)`.
   3. `read_fields([field])`로 다시 읽기. `same_value(type, 읽은 값, applied_value)`이고 `pending_review`가 거짓이면 → `applied`(`applied_at`, `verified_at = now`). 아니면 → `pending_reflection`(`applied_at = now`, `last_checked_at = now`).
   4. 칸 상태를 바꾸는 트랜잭션마다 `finalizeFix` 등록을 함께 넣는다.
4. 예외
   - `AutomationBlocked`: 그 칸과 이 정비안의 남은 queued 칸 모두 → `manual_required`(`automation_blocked`, `error_code` = 사유). **다시 시도하지 않고** 멈춘다. 관리자 메일 `manual_required`(dedupe `manual_required:plan:{plan_id}:blocked`).
   - `TransientAutomationError`·시간 초과: 그 칸만 3.1~3.3을 1번 더. 그래도 실패 → 그 칸 `manual_required`(`write_failed`), 다음 칸으로 계속. 관리자 메일(같은 정비안은 작업 끝에 한 번에 묶어 보냄).
   - `StoreNotVisible`, API 403·404 → 03 E18(남은 칸 disconnected), 멈춤.
5. `same_value(type, a, b)`: text는 앞뒤 공백 제거·연속 공백 하나로, url은 host 소문자·끝 `/` 제거, phone은 `normalize_phone`, hours는 구조 비교, menu는 (이름, 가격) 집합, attributes는 b의 키가 a에 같은 값으로 있음, links·services·tags는 집합.
6. 덮어쓰기 방지: `applyFix`는 정비안당 한 번(`queueing_lock`, 정비안 승인 조건부 UPDATE). queued가 아닌 칸은 쓰지 않는다. 정비 완료 뒤 지도에 쓰는 코드 경로는 없다(`verifyFix`·`compareFixValues`는 읽기만).

구현 메모(2026-10-28, 13단계, `fix_apply_service.apply`)
- 칸마다 읽기 → `before_value`·`attempt` 커밋 → 쓰기 → 다시 읽기를 한 묶음(제한 180초)으로 하고, 일시 오류·시간 초과면 묶음 전체를 1번 더 한다. 다시 할 때 `before_value`는 처음 읽은 값을 지킨다.
- `FieldWriteFailed`(셀렉터 없는 칸·API가 받지 않는 값·영업시간에 정보 없는 요일) → 그 칸만 manual_required(write_failed, `error_code` = 사유), 다음 칸 계속.
- `AttentionNeeded`(인증 필요 등)도 차단과 같이 처리한다(남은 칸 모두 `automation_blocked`, `error_code` = 사유).
- 가게 화면을 두 번 모두 열지 못하면(일시 오류) 남은 칸 모두 write_failed(`transient`).
- 메일 dedupe: 차단 `manual_required:plan:{id}:blocked`, 저장 실패 묶음 `manual_required:plan:{id}:write_failed`.
- 정비안이 approved가 아니면 화면을 열지 않는다. 연결이 끊겼거나 queued 칸이 없으면 finalizeFix만 등록한다(정비 완료 뒤 다시 불러도 쓰기 0번).
- 작업 전체 15분 제한(06 4장)은 칸별 제한으로 대신했다.

## 10. 반영 확인(W-09-6, E32)

- `recheckPendingFixes`(매시간): `pending_reflection` 칸마다
  - `now - applied_at >= 24시간` → `manual_required`(`not_reflected_24h`, D-15), 관리자 메일(dedupe `manual_required:log:{id}`), `finalizeFix` 등록.
  - 아니고 `last_checked_at`이 55분보다 오래됐으면 `verifyFix(fix_log_id, round = verify_count + 1)` 등록.
- `verifyFix`: **읽기만 한다**(쓰기 함수를 부르지 않음, 테스트로 확인). 같으면 → `applied`(`verified_at`), 아니면 `verify_count += 1`, `last_checked_at = now`. `StoreNotVisible` → E18. `AutomationBlocked` → 상태 그대로, 경고 로그(다음 시각에 다시).
- 구현 메모(2026-10-28, 13단계): `fix_apply_service.verify(fix_log_id, round)`·`recheck_pending(session, now)`. verifyFix는 `fix:{provider}` lock, queueing_lock `verifyFix:{id}:{round}`(같은 시각에 두 번 돌려도 1개). 반영되면 applied(`verified_at`) + finalizeFix 등록. 연결이 connected가 아니면 건너뛴다. 일시 오류·차단·인증 필요는 상태 그대로(다음 시각에 다시). 24시간 판정은 `applied_at` 기준.

## 11. 정비 완료 `finalizeFix(fix_request_id)`(W-09-7, E17)

1. 신청이 `fixing`이 아니면 끝.
2. 그 신청의 approved 정비안이 0개면 끝.
3. approved 정비안들의 칸에 딸린 `fix_logs`가 모두 끝 상태(`applied`·`manual_done`·`disconnected`)면 E17. 칸이 0개인(모두 제외한) 정비안은 끝난 것으로 본다.
4. 확인 테스트: 모든 칸 자동 완료 / 일부 수동 처리 / 연결 끊김 3가지에서 `remeasure_scheduled`, `remeasure_schedules` 1행, `due_at = fix_completed_at + 14일`.

구현 메모(2026-10-28, 12단계, `services/fix_apply_service.py`)
- `finalize(fix_request_id)`: 신청 행을 FOR UPDATE로 잠그고 다시 읽는다. 그래서 여러 번·동시에 불러도 예약은 1행이다. 한 트랜잭션에서 신청 전이(`fix_completed_at = now`)·예약(scheduled, scheduler, `due_at = now + 14일`)·메일 `fix_completed`(dedupe `fix_completed:{schedule_id}`)를 처리한다.
- 메일 `changed_fields`: applied·manual_done 칸만 "지도 라벨 + 칸 라벨". 순서는 지도(google → kakao), 그다음 칸 순서. 모든 칸이 연결 끊김이거나 칸이 0개면 빈 목록이고, 본문에는 "없음"이 나간다.
- 다른 지도의 정비안이 승인 대기·생성 중이어도 막지 않는다(E17 조건 그대로). 그 정비안을 나중에 승인하면 D-16으로 fixing이 되고(예약 canceled), 끝나면 새 예약을 만든다.
- `finalizeFix`는 DB만 쓰므로 plan 큐(기본 워커)에서 돈다. lock은 `request:{id}`. 등록은 `defer_finalize(session, request_id, *, store_id)`로 모았다(승인·처리 완료·권한 회수, 13단계 applyFix·verifyFix도 이 함수).

## 12. 권한 회수(E18)

- 감지 지점: `readCurrentValues`, `applyFix`, `verifyFix`, `compareFixValues`에서 `StoreNotVisible` 또는 API 403·404.
- 처리: 연결 → revoked, 그 신청·지도의 queued·pending_reflection·manual_required 칸 → disconnected, `finalizeFix` 등록. S07·S15에 "연결이 끊겼어요"(03 4장 `revokedProviders`).
- 다시 초대(E11 → E12)해도 그 지도에 approved 정비안이 이미 있으면 새 정비안을 만들지 않는다(정비는 신청 1건당 1번). 다시 연결은 재측정 때 카카오 값 다시 읽기(10 2장)에만 쓰인다.
- 구현 메모(2026-10-28, 10단계): 처리 함수 `connection_service.revoke(session, request_id, provider) -> bool`(connected일 때만, 감지한 작업이 커밋). 남은 칸 disconnected는 한 번의 조건부 UPDATE. `finalizeFix`(12단계 본문)를 `lock request:{id}`로 등록한다. 감지 지점(읽기·쓰기·반영 확인·값 비교)은 11~14단계에서 이 함수를 부른다.

## 13. 수동 처리(A01, E30)

- `GET /api/admin/manual-items`: `fix_logs.status = manual_required` 전체, 승인 값과 관리 화면 바로가기.
- `POST /api/admin/fix-logs/{id}/manual-done`: manual_required → manual_done, `method = manual`, `handled_by/at`. 관리자는 직접 고친 뒤 누른다. `before_value`가 비어 있으면 관리자가 고치기 전 값을 알 수 없으므로, 요청 본문에 선택 필드 `beforeValue`를 받아 저장한다 `[기획 확인]`.
- 구현 메모(2026-10-28, 12단계): `fix_apply_service.manual_done`
  - 칸 행을 잠그고 manual_required가 아니면 409 `INVALID_STATE` `{currentStatus}`, 없으면 404를 낸다. 본문은 생략할 수 있다.
  - `beforeValue`는 `before_value`가 비어 있을 때만 저장한다(이미 있으면 받은 값을 버린다).
  - 감사 기록 `fix_log.manual_done` detail `{provider, field, beforeValueGiven}`.
  - 같은 트랜잭션에서 `finalizeFix`를 등록한다. 대기 중인 것이 있으면 queueing_lock으로 하나로 합쳐진다.
  - 수동 칸 목록은 `admin_service.manual_items`(9단계, 신청 상세와 공용, 오래된 것 먼저)를 쓴다.
