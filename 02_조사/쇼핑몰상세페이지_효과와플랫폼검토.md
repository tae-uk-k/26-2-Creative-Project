## 1. 효과는 얼마나 커질 수 있는가?

### 1.1 구매 효과: 설명이 부족한 상품에서 직접적인 실험 근거가 있다

[온라인 소매의 무작위 실험 연구](https://arxiv.org/html/2510.12049v6)는 약 45,000개 상품·4,772,937명의 소비자를 대상으로 기존 설명에 AI 설명을 추가했다. 한국어를 포함한 5개 언어에서 2023년 12월 각각 1주 동안 실험했다. 아래 수치는 2026-06-29 공개된 v6의 표 C5·C6에 있다.

| 측정 지표 | 관찰 결과 |
|---|---:|
| 소비자당 매출 | 상대 +2.05% |
| 구매 여부로 측정한 전환율 | 상대 +1.27% |
| 주문 수 | 상대 +1.08% |
| 기존 설명이 없거나 짧은 상품의 매출 | 상대 +6.50% |
| 기존 설명이 충분한 상품의 매출 | 상대 +0.03%, 통계적으로 유의한 변화 없음 |

설명 길이에 따른 마지막 두 결과는 **영어 실험만의 분석**이다. 표 C6은 50단어 이하와 초과로 구분한다. 이 경계를 한국어 상품 선정 기준으로 그대로 사용하지 않는다. 전체 구매 효과는 상세페이지에 들어온 소비자를 대상으로 측정한 결과다. 외부 AI 검색에서 유입이 늘었다는 수치는 아니다. [실험 방법 §2.2, 표 C5·C6](https://arxiv.org/html/2510.12049v6)

전환율의 +1.27%는 +1.27%p와 다르다. 예를 들어 기존 전환율이 4%라면 상대 +1.27%는 약 4.051%가 되는 계산이다. 이 예시는 비율의 의미를 설명한 것이며 우리 서비스의 예상 실적이 아니다.

**기획 해석:** 초기 고객은 이미 상세한 상품보다 구매 판단에 필요한 사실이 빠져 있는 상품을 가진 판매자가 적합하다. 위 연구의 다른 기능까지 합친 최대 매출 효과를 상세페이지 정비의 효과로 사용하지 않는다.

### 1.2 AI 추천 효과: 상품 설명을 바꾼 실험은 있지만 자연 검색과 구분해야 한다

[E-GEO v3](https://arxiv.org/html/2511.20867v3)는 상품 후보 10개를 고정하고 2,000개 질문에서 설명을 다시 썼을 때의 순위 변화를 비교했다. 단순 재작성에서도 GPT-5·Claude는 평균 약 0.56~0.57순위 상승했지만, GPT-4o-mini는 평균 0.36순위 하락했다. 설명을 길게 만드는 것과 순위 상승의 관계는 거의 없었다. 방법·결과는 §4.1~4.2와 부록 C.8에 있다.

이 결과는 **이미 후보에 들어간 상품의 재정렬**에 관한 것이다. 실제 웹에서 상품을 새로 발견하는 비율, ChatGPT·Gemini 서비스의 자연 추천률, 매출 증가율로 바꿔 읽지 않는다. **우리의 정비 대상은 글의 길이가 아니라 구매 조건과 관련된 확인 가능한 정보여야 한다**는 판단에 참고한다.

### 1.3 현재 서비스보다 몇 배 뛰어난지는 아직 계산할 수 없다

현재 식당 지도 정비와 쇼핑몰 정비를 같은 조건에서 비교한 실험을 확보하지 못했다. 두 방식의 효과를 나눠 비교 배율을 계산할 자료도 없다. 따라서 ‘지도 정비보다 AI 추천 효과가 몇 배’라는 수치 대신, **쇼핑몰은 구매 효과의 직접 실험 근거와 매출 측정 수단이 있다는 점**을 확장 판단에 사용한다.

## 2. 현재 식당 지도 정비와 무엇이 다른가?

아래 비교는 현재 기획과 이번에 확인한 플랫폼 기능을 종합한 판단이다.

| 비교 항목 | 현재 식당 지도 정비 | 쇼핑몰 상세페이지 정비 |
|---|---|---|
| 고칠 정보 | 소개·메뉴·가격·영업시간·방문 조건 | 상품 설명·규격·소재·구성품·호환성·사용 조건·이미지·상품 속성 |
| 표현과 구조의 제어 | 지도가 제공하는 입력 칸에 맞춤 | 자사몰은 본문 HTML과 일부 SEO 정보까지 관리 가능 |
| 사실의 원자료 | 지도·공식 채널·메뉴판·공지 | 판매자 상품 DB·제조사 자료·설명서·옵션별 스펙 |
| 효과 측정 | AI 추천 결과, 사실 정확도 | AI 추천 결과와 별도로 방문·장바구니·구매·환불 측정 가능 |
| 수정 자동화 | 플랫폼별 권한·편집 경로 확인 필요 | 아래 주요 플랫폼에 공식 상품 수정 API가 있음 |
| AI가 해결할 핵심 문제 | 같은 지점의 사실과 시점 확인 | 같은 모델·옵션의 사실 확인, 구매 조건의 누락 보완 |
| 초기의 어려운 부분 | 지점 식별과 지도 반영 확인 | 상품 식별·카테고리별 스펙·기존 편집기 보존·재고 및 원가 체계와의 충돌 방지 |

**유리한 점은 ‘더 많이 쓸 수 있다’보다 ‘구매에 필요한 정보를 보완하고 주문 데이터로 평가할 수 있다’는 것이다.** 자사몰에서 만든 사실 기준을 다른 판매 채널의 지원 항목에 맞춰 배포하는 후속 확장도 검토할 수 있다.

## 3. 실제로 무엇을 고칠 것인가?

| 정비 대상 | 예시 | 필요한 근거 |
|---|---|---|
| 상품 식별 | 브랜드·모델명·모델번호·옵션을 구분한다. | 판매자 상품 DB, 제조사 모델 자료 |
| 구매 판단에 필요한 누락 정보 | 크기·무게·소재·구성품·전원 조건·호환 모델을 보완한다. | 동일 모델의 설명서·인증 자료·확정 스펙 |
| 이미지에만 있는 정보 | 이미지 속 규격을 읽고 확인한 값을 본문·표·상품 속성으로 옮긴다. | 이미지 원본과 실제 상품·옵션의 일치 확인 |
| 읽기 쉬운 설명 | 주요 용도 → 조건·규격 → 구성품 → 사용·관리 순서로 정리한다. | 확인된 사실 목록 |
| 상품 속성과 검색 정보 | 카테고리·브랜드·모델·색상·규격·제목·메타 설명을 정비한다. | 플랫폼별 지원 필드 |
| 검색 시스템에 전달하는 상품 데이터 | 자사몰의 Product·Offer 구조화 데이터와 상품 피드를 대조한다. | 실제 페이지의 가격·재고·옵션과 일치하는 판매자 데이터 |

Google은 웹페이지의 상품 구조화 데이터와 Merchant Center 상품 데이터를 상품 이해에 사용하는 별도 경로로 설명한다. 따라서 본문 편집, 구조화 데이터 정비, 상품 피드 연결은 각각 작업과 측정 항목을 나눈다. **본문 수정 API가 있다고 해서 페이지 전체나 검색 시스템의 모든 데이터를 제어하는 것은 아니다.** [Google 상품 데이터 안내](https://developers.google.com/search/docs/specialty/ecommerce/share-your-product-data-with-google), [상품 구조화 데이터](https://developers.google.com/search/docs/appearance/structured-data/product)

AI는 자료를 먼저 모으고 같은 모델·옵션인지 판단한다. 수집되지 않은 호환성·인증·성능을 추정해 추가하지 않는다. 가격·재고는 판매자의 운영 데이터에 맞추고, 설명 개선 작업에서 임의 변경하지 않는다. 사장님에게는 여러 상품의 질문을 묶어 꼭 필요한 누락만 요청한다. 이미 자료가 있는 상품마다 확인 질문을 반복하지 않는다.

## 4. 기술적으로 가능한 플랫폼은 어디인가?

### 4.1 플랫폼별 판단

‘가능’은 공식 문서에 상품 정보를 쓰는 경로가 있다는 뜻이다. 이번 조사에서는 판매자 계정 연결·실제 상품 수정·고객 화면 반영 시험은 실행하지 않았다.

| 플랫폼 | 기술적 판단 | 수정할 수 있는 범위와 확인 사항 | 초기 우선순위 |
|---|---|---|---|
| **카페24** | 가능 | 상품 상세·모바일 상세·요약 정보를 관리하고, 상품 SEO는 별도 API로 수정한다. 기존 스킨·Edibot·외부 상품 관리 앱과의 연동 상태를 확인한다. | **국내 자사몰 우선** |
| **Shopify** | 가능 | GraphQL로 HTML 설명·SEO 제목/설명·추가 상품 정보를 수정한다. 테마 변경은 별도 작업이며 가격·옵션은 상품 본문 수정과 분리한다. | **해외 판매 자사몰 우선** |
| **WooCommerce** | 가능 | REST API로 상세/짧은 설명·이미지·속성을 수정한다. WordPress 구성과 플러그인이 쇼핑몰마다 달라 실제 화면 검수가 필요하다. | 자사몰 확장 후보 |
| **아임웹** | 가능, 신규 앱 연동 조건 확인 필요 | 현행 API에 상품·SEO 수정 경로가 있다. 상세설명 필드는 구 API 문서에서 확인했다. 신규 구현은 현행 요청 스키마와 앱 승인 조건을 맞춰야 한다. | 승인·스키마 확인 후 |
| **네이버 스마트스토어** | 가능 | 커머스API의 상품 상세 정보·속성을 수정한다. 스마트에디터 상세를 API로 덮어쓰면 HTML 방식으로 전환되므로 화면 구성 보존을 먼저 시험한다. | 자사몰 실험 다음 |
| **쿠팡 마켓플레이스** | 가능, 승인 후 반영 | 판매자 상품의 상세 콘텐츠와 속성을 수정한다. 조회한 전체 상품 JSON에서 필요한 값만 바꿔 제출하며, 수정 승인과 실제 노출 내용을 확인한다. | 승인·화면 검증 후 |

스마트스토어·쿠팡에서는 판매자가 제공하는 본문·속성을 정비 대상으로 잡는다. 플랫폼 공통 화면·페이지 head·검색 시스템까지 자사몰처럼 수정하는 기능으로 설계하지 않는다.

### 4.2 개발 검토를 위한 공식 수정 경로

| 플랫폼 | 공식 경로·입력 | 연동 조건·주의점 |
|---|---|---|
| 카페24 | `PUT /api/v2/admin/products/{product_no}`. 상세설명 계열 필드: `description`, `mobile_description`, `summary_description`. SEO: `PUT /api/v2/admin/products/{product_no}/seo`. | 쇼핑몰 OAuth와 상품 쓰기 권한. 최신 문서는 `WRITE_PRODUCT`, 기존 문서는 `mall.write_product`로 표기한다. [상품 수정](https://apidocs.cafe24.com/docs/admin/put-products-by-product-no), [SEO 수정](https://apidocs.cafe24.com/docs/admin/put-products-by-product-no-seo), [상세 필드의 기존 공식 명세](https://developers.cafe24.com/docs/ko/api/admin/?version=2025-12-01) |
| Shopify | GraphQL `productUpdate` → `descriptionHtml`, `seo`, `metafields`. | `write_products`와 상품 수정 권한. 옵션·가격은 별도 변형 상품 API 영역이다. [수정 작업](https://shopify.dev/docs/api/admin-graphql/latest/mutations/productUpdate), [입력 필드](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/ProductUpdateInput) |
| WooCommerce | `PUT /wp-json/wc/v3/products/{id}` → `description`, `short_description`, `images`, `attributes`. | 쓰기 권한을 가진 REST API 키와 사용자 권한. SEO 플러그인 전용 필드는 별도 연동을 확인한다. [REST API v3](https://woocommerce.github.io/woocommerce-rest-api-docs/#update-a-product) |
| 아임웹 | 현행 서버 `https://openapi.imweb.me`의 `PATCH /products/{prodNo}`, `PATCH /products/{prodNo}/seo`. 구 v2는 `PATCH /v2/shop/products/{상품번호}`에 `content`, `simple_content`, `mobile_content`를 제공한다. | 현행 OAuth·상품 권한과 앱 승인 경로 확인. 구 v2 필드를 현행 API에 그대로 전송하지 않는다. [현행 API](https://developers-docs.imweb.me/reference), [구 상세설명 명세](https://old-developers.imweb.me/items/add), [앱 사용·승인 조건](https://developers-docs.imweb.me/guide/%EC%A4%80%EB%B9%84%ED%95%98%EA%B8%B0) |
| 스마트스토어 | `PUT /v2/products/origin-products/{originProductNo}` → `originProduct.detailContent`. | 판매자·애플리케이션 인증. 스마트에디터 작성 상태를 조회하고 기존 화면과 HTML 결과를 대조한다. [원상품 수정](https://apicenter.commerce.naver.com/docs/commerce-api/current/update-origin-product-product), [공식 운영팀의 에디터 전환 안내](https://github.com/commerce-api-naver/commerce-api/discussions/1539) |
| 쿠팡 | `PUT /v2/providers/seller_api/apis/api/v1/marketplace/seller-products` → `items[].contents[].contentDetails[].content`. | 판매자 Open API 인증. 전체 상품 정보를 보존한 제출과 승인 상태 확인이 필요하다. [상품 수정 공식 명세](https://developers.coupang.com/ko/api/products/modify-product) |

카페24의 최신 페이지에서는 수정 경로·권한을, 검색으로 확인한 기존 공식 명세에서는 상세설명 필드를 확인했다. 아임웹 현행 문서는 상품·SEO 수정 경로까지 확인했으며, 상세 본문 필드의 현행 요청 구조는 추가 확인 대상이다. 이 둘을 실제 연동 완료 상태로 기록하지 않는다.

## 5. 어디서 시작하고 어떻게 효과를 검증할 것인가?

### 5.1 초기 대상

**국내 판매자는 카페24, 해외 판매자는 Shopify를 첫 연동 대상으로 권한다.** 아래 조건이 맞는 쇼핑몰을 먼저 찾는다. 플랫폼 순서는 시장점유율 순위가 아니라 이번 조사에서 확인한 수정 범위와 실험 편의에 따른 제안이다.

- 정상적으로 판매 중이고 방문·주문 데이터를 측정할 수 있다.
- 설명이 짧거나 이미지에만 핵심 정보가 있으며, 원자료로 누락을 채울 수 있다.
- 같은 상품·옵션의 설명서나 제조사 스펙을 확보할 수 있다.
- 규모·소재·호환성·구성 차이가 구매에 영향을 주는 상품을 보유한다.

주방·생활용품, 수납·소형 가구, 사무용품, 기기 액세서리를 후보로 검토할 수 있다. 이는 실험 대상 제안이며 업종별 효과가 확인됐다는 뜻은 아니다. 시작 단계에서는 문구만 바꾸는 기능보다 **근거 수집 → 빠진 사실 보완 → 채널별 반영 → 성과 측정**을 하나의 서비스로 묶는다.

### 5.2 구매 효과와 AI 발견 효과의 실험을 분리한다

| 검증 목적 | 적용 방법 | 우선 측정 지표 |
|---|---|---|
| 설명 개선이 구매에 도움이 되는가? | 동일 상품의 방문자를 기존/개선 설명에 무작위 배정한다. 같은 방문자는 같은 버전을 보며 가격·광고·재고·프로모션을 맞춘다. | 구매전환율, 방문자당 매출. 보조: 장바구니, 문의, 취소·환불 |
| AI가 상품을 더 자주 발견하는가? | 비슷한 상품을 정비군/유지군으로 나누고 공개 반영·수집 상태를 확인한 뒤 반복 측정한다. 검색 로봇과 사용자에게 같은 상품 정보를 제공한다. | 상품명·URL을 미리 주지 않은 질문의 추천 등장률·출처·조건 적합성 |
| 이미 후보인 상품을 더 잘 판단하는가? | 후보 목록과 질문을 고정하고 설명만 바꾼다. 후보 순서도 바꿔 검사한다. | 순위 변화, 사실 정확도. 자연 발견 효과와 별도 기록 |

처음부터 표본을 3~4개 군으로 잘게 나누지 않는다. 우선 기존 설명과 **검증된 누락 사실을 보완한 설명**의 두 집단을 비교한다. 문체만 바꾸는 효과를 추가로 알고 싶을 때 별도 실험한다. 구조화 데이터·피드 변경도 본문 변경과 구분해 기록한다.

기간과 표본 수는 기존 전환율·방문자 수·검출할 최소 개선 폭을 보고 정한다. 같은 상품의 방문·측정 반복을 서로 다른 상품 표본으로 세지 않는다. 전후 비교만 진행했다면 광고·계절·가격·모델 변경의 영향을 함께 기록한다.

### 5.3 개발 착수 전 확인할 최소 항목

1. 테스트 상품 하나를 읽고 설명만 수정한 뒤 다시 조회한다. 누락 필드나 전체 데이터 덮어쓰기가 없는지 확인한다.
2. PC·모바일 공개 페이지에서 본문·옵션·이미지·가격을 대조하고 기존 상태로 복구할 수 있는지 시험한다. 작업별 변경 전 값을 보관하는 기능은 운영 복구용으로 설계한다.
3. 외부 상품 관리 앱이 내용을 다시 덮는지 확인한다. 같은 상품의 동시 편집을 감지하고 최신 값을 다시 비교한다.
4. 방문·주문 측정과 실험 배정을 연결한다. 공식 API의 수정 성공, 고객 화면 반영, 구매 효과, AI 추천 효과를 각각 기록한다.

위 항목은 다음 구현에서 검증할 계획이다. 이번 조사로 확정한 것은 공식 수정 경로와 외부 연구의 관찰 결과다.
